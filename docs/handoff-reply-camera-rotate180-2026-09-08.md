# 회신 — 카메라 영상 180° 회전(설치 방향 보정) 요청 (2026-09-08)

> **회신 대상**: 앱(Flutter) `handoff-camera-rotate180-2026-09-08.md`
> **작성**: FB2_P4_CAM 펌웨어 + terra-server 담당 (양쪽 모두 이쪽에서 처리)
> **성격**: 펌웨어·서버 코드 실측 대조 결과 회신 + 앱이 따를 최종 계약.
> **결론 먼저**: **R1~R6 전부 수용.** 센서 레벨 180° 회전은 이미 V4L2 경로가 있어 구현 부담이 작고, 전달 경로는 앱 선호대로 **(a) `cameras.rotate_180` 컬럼 = 선언적 설정**으로 갑니다. 단 문서에 없던 **2건(ROI 좌표 변환, Bayer 색 검증)**은 이쪽에서 흡수하므로 앱은 신경 안 써도 됩니다.

## 1. R1 — 회전 방식 (센서 레벨)

- 이 카메라는 esp_camera(OV2640 DVP)가 아니라 **ESP32-P4 + OV5647(MIPI-CSI) + esp_video(V4L2)** 구조입니다. 그래도 결과는 같습니다: `V4L2_CID_VFLIP` + `V4L2_CID_HFLIP` 를 동시에 켜면 센서 readout 단계에서 180° 회전된 픽셀이 나오고, 이후 ISP → H.264/JPEG 인코더 → 라이브/클립/썸네일이 전부 회전본을 받습니다.
- 앱 문서의 경고(vflip 하나만 켜면 거울상)도 동일하게 해당되며, 펌웨어에서 **두 컨트롤을 항상 한 쌍으로만** 다룹니다. 앱은 `rotate_180: bool` 하나만 보내면 됩니다.
- 재인코딩·CPU 부하 없음. 해상도·fps·비트레이트 영향 없음.

**이쪽에서 추가로 처리하는 것 (앱 무관)**
1. **모션 감지 ROI 자동 변환** — 사용자가 잡아둔 모션 제외/집중 영역이 센서 픽셀 좌표로 저장돼 있어, 회전하면 반대편으로 갑니다. 회전 시 펌웨어가 좌표를 자동 변환합니다. ROI 를 다시 잡을 필요 없음.
2. **회전 순간 모션 오탐 억제** — 화면이 통째로 바뀌는 순간 모션 감지를 1~2초 멈춰 가짜 모션 이벤트/클립이 생기지 않게 합니다.
3. **Bayer 색 검증** — OV5647 은 raw 센서라 flip 시 컬러 필터 배열 순서가 바뀔 수 있습니다. 실기에서 색이 틀어지면 ISP 재설정을 넣어 해결합니다. 이게 유일한 리스크이며, **결과에 따라 R6 계약이 "즉시" → "스트림 재시작 후"로 바뀔 수 있습니다** (§6 참고). 확인 즉시 공유하겠습니다.

## 2. R2 — 영속화

- NVS `terra-cam` 네임스페이스에 `rotate` 키 저장. 기본값 false(정방향).
- 부팅 시 센서 스트림 시작 직후 적용하므로 첫 프레임부터 회전본입니다.
- 서버 DB(`cameras.rotate_180`)와 NVS 가 어긋난 경우(오프라인 중 앱에서 토글 등)는 §5 동기화 규칙으로 서버 값이 이깁니다.

## 3. R3 — 적용 범위

확인 결과 파이프라인이 갈리지 않습니다.

```
OV5647 → ISP → [YUV 캡처 버퍼] ─┬─ H.264 → WebRTC 라이브
                                  ├─ H.264 → 모션 클립(mp4) → R2
                                  └─ JPEG  → 썸네일 / 스냅샷
```

회전은 맨 앞 센서에서 일어나므로 세 경로 모두 자동 적용. 커뮤니티 공유·기기 저장·내보내기도 원본이 회전본이라 전부 맞습니다.

## 4. R4 — capabilities

- `cameras` 테이블에 `capabilities JSONB` 컬럼 신설. `GET /cameras`, `GET /cameras/{id}` 응답(`CameraOut`)에 `capabilities` 필드 추가.
- 값은 펌웨어가 **MQTT 연결 직후 텔레메트리로 매번 보고**하고 서버가 컬럼에 반영합니다. 페어링 시 1회 보고가 아니라서, 기존 카메라도 펌웨어만 올리면 다음 재연결 때 자동으로 `rotate_180: true` 가 됩니다.
- 구 펌웨어 카메라: `capabilities` 가 `null` 이거나 `rotate_180` 키가 없음 → 토글 숨김.

```jsonc
// CameraOut 발췌
{
  "id": "…",
  "camera_id": "p4cam-a1b2c3d4",
  "rotate_180": false,                    // 신규. 현재 설정값(선언적)
  "capabilities": { "rotate_180": true }, // 신규. null 이면 구 펌웨어
  ...
}
```

LED 건(devices.capabilities)은 이미 서버에 반영돼 있고, 카메라 capabilities 는 이번에 같은 형태로 맞춥니다.

## 5. R5 — 전달 경로: (a) 선언적 설정 채택

앱 선호대로 갑니다. 앱은 **REST 한 번**만 호출하면 됩니다.

### 앱이 하는 것
```
PATCH /cameras/{camera_uuid}
Authorization: Bearer <user JWT>
{ "rotate_180": true }
→ 200 CameraOut (rotate_180 갱신됨)
```

- `CameraUpdate` 에 `rotate_180: bool | None` 추가. 다른 필드와 함께 보내도 됨.
- 응답은 DB 반영 즉시 돌아옵니다. 카메라 적용 완료를 기다리지 않습니다(온라인이면 보통 1초 내 적용).

### 서버·카메라가 하는 것 (앱 무관, 참고)
1. 서버가 `cameras.rotate_180` 갱신 후 `esp32/{camera_id}/command` 로 `{"action":"set_rotation","rotate_180":true}` 발행.
2. 카메라가 적용 → NVS 저장 → ack.
3. **동기화 보정**: 카메라는 MQTT 연결 직후 텔레메트리에 현재 `rotate_180` 값을 실어 보냄. 서버가 DB 와 다르면 명령을 재발행. → 오프라인 중 토글해도 다음 재연결 때 맞춰짐. 명령 유실·재부팅·펌웨어 교체 모두 이 경로로 수렴.

앱은 ack 나 텔레메트리를 볼 필요 없고, `CameraOut.rotate_180` 이 곧 토글 상태입니다.

## 6. R6 — 적용 시점 (앱 안내 문구용)

| 상황 | 적용 시점 |
|---|---|
| 카메라 온라인, 라이브 시청 중 | **즉시.** 다음 프레임부터 뒤집힘. WebRTC 재연결 없음. 화면이 한 번 "탁" 바뀜 |
| 카메라 온라인, 라이브 아님 | 즉시(1초 내). 이후 모션 클립·썸네일부터 회전본 |
| 카메라 오프라인 | 다음 부팅/재연결 시 자동 적용 |
| 구 펌웨어 | 토글 미노출(capabilities 없음). PATCH 는 DB 에만 저장되고 카메라는 무시 |

권장 문구: **"잠시 후 적용돼요. 카메라가 꺼져 있으면 다시 켜질 때 적용돼요."**

⚠️ §1-3 Bayer 검증 결과 스트림 재시작이 필요해지면 "라이브 시청 중 → 약 2~3초 끊겼다 복귀"로 바뀝니다. 문구는 그대로 써도 되도록 "잠시 후"로 두는 걸 권합니다.

## 7. 알고 있는 한계 (앱 문서 §5 동의)

- 이미 R2 에 올라간 과거 클립·썸네일은 소급되지 않음. 동의합니다. 필요해지면 그때 앱 로컬 표시 플립을 별도 검토.
- 90°/270° 미지원. 180° 만.
- 페어링 직후 첫 부팅은 항상 정방향(NVS 기본값). 앱에서 토글하면 그때부터 유지.

## 8. 작업 항목 및 순서

**펌웨어 (FB2_P4_CAM)**
1. 실기 Bayer 검증 (`/ctrl?var=vflip` + `hmirror` 동시 적용 후 색 확인) — **가장 먼저**, R6 계약 확정용
2. NVS `rotate` 저장/복원, 부팅 시 적용
3. MQTT `set_rotation` action + ack
4. 텔레메트리에 `rotate_180`, `capabilities` 포함
5. 모션 ROI 좌표 자동 변환 + 회전 직후 모션 억제
6. 로컬 `/ctrl` 페이지 체크박스를 "180° 회전" 단일 토글로 정리(디버그용)

**서버 (terra-server)** — 별도 작업 문서로 진행
1. `cameras.rotate_180`, `cameras.capabilities` 마이그레이션
2. `CameraUpdate`/`CameraOut` 필드 추가, PATCH 시 MQTT 명령 발행
3. 텔레메트리 핸들러: capabilities 반영 + rotate_180 불일치 시 재발행

**앱**
- 서버 배포 후 `CameraOut.capabilities.rotate_180` 유무로 토글 노출, `PATCH /cameras/{id}` 호출. 이것 외 추가 작업 없음.

순서: 펌웨어 1번(검증) → 서버 → 펌웨어 나머지 → 앱. 서버 배포 시점에 이 문서를 갱신해 알리겠습니다.

## 9. 회신 요청 항목 정리 (앱 문서 §7)

1. R1~R4 수용. 일정은 §8 순서대로, Bayer 검증 결과 공유 후 확정.
2. R5 = **(a)**. 스키마: `cameras.rotate_180 BOOLEAN DEFAULT false`, `cameras.capabilities JSONB`. API: `PATCH /cameras/{id}` body `rotate_180`, `CameraOut` 에 두 필드 추가. 토픽/명령은 서버↔카메라 내부 사항.
3. R6 = 온라인 즉시 / 오프라인 다음 연결 시 (§6 표).
4. capabilities 보고 = 카메라는 MQTT 연결 시마다 텔레메트리로 보고. LED(devices) 건은 이미 적용돼 있음.
