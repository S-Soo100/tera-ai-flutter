# 카메라 라이브 안정성 — 앱 개선 범위와 외부 작업의 경계

작성일: 2026-09-24 · 대상: 기획·앱·펌웨어·서버 담당자 · **갱신: 2026-09-24 Galaxy S21+ 실기기 시험·`0.133.12` 반영**

## 1. 결론

**앱에서 할 수 있는 일은 적지 않다. 앱이 만드는 불필요한 연결 종료를 줄이고, 끊어진 영상을 더 빨리 복구하면 실제 시청 안정성이 좋아진다.** 다만 카메라가 영상을 생성·전송하지 못하는 문제까지 앱만으로 해결할 수는 없다.

현재 전체 끊김 중 앱·펌웨어·네트워크가 차지하는 비율은 측정되지 않았다. 따라서 “앱 개선 효과는 작다”거나 “중계 서버를 도입하면 해결된다”고 단정하지 않는다. 앱 개선을 진행하면서 남는 장애를 로그로 구분해 다음 투자 대상을 정한다.

이 문서는 개선 범위를 설명하는 판단 자료다. 구체적인 구현·시간 기준은 아래 기존 기획과 구현 계획을 따르며, 여기서 새로 변경하지 않는다.

## 2. 출발점과 현재 확인 수준

고객이 겪는 문제는 두 가지다.

1. 앱을 켜면 연결이 완료되기도 전에 끊겼다는 안내가 나온다.
2. 시청 중 영상이 보이다 멈추기를 반복하다가 복구되지 않는 경우가 있다.

사용자는 **카메라와 같은 Wi-Fi에서도 발생**한다고 확인했다. 이것만으로 앱 또는 펌웨어 문제라고 확정할 수는 없다. 같은 Wi-Fi에서도 무선 품질·기기 부하·연결 관리 문제가 발생할 수 있고, 실제 영상 경로가 직접 연결인지 중계 경로인지도 확인해야 한다.

[검증 결과](../design-audits/2026-09-24-camera-live-pre-firmware/RESULTS.md)의 현재 수준:

- **완료:** 자동 테스트, 시뮬레이터 확인, **Android 실기기 1대(Galaxy S21+) 릴리즈 빌드 시험**(RESULTS §5). 강한 같은 Wi-Fi에서 첫 화면 3~4.4초, 약 32분 연속 재생 중 약 6초 정지 2회(재연결 없이 자체 회복), 앱 복귀 2.7초, 휴대폰 망 단절 후 자동 복구 3.1초.
- **실기기에서 찾아 고친 결함:** 휴대폰 망 끊김을 "카메라 오프라인"으로 안내하고, 망 복귀 후 수동 재연결이 필요했다 → `0.133.11` 수정, `0.133.12`에서 재확인.
- **미완료:** 약한 신호(시험 환경 Wi-Fi가 강해 재현 못 함), 카메라 쪽 약한 Wi-Fi, iOS 실기기, 녹화·업로드 경합, 수 시간 시청.

**구현 완료와 고객 환경에서의 안정성 입증은 구분한다.** 표본이 기기 1대·카메라 1대라 성공률·정지율 같은 비율은 산출하지 않는다.

## 3. 개선 효과를 세 가지로 구분한다

| 구분 | 의미 | 예시 |
|---|---|---|
| 끊김 자체 감소 | 정상적으로 볼 수 있던 연결을 유지한다 | 중복 재접속 요청 때문에 현재 영상을 종료하지 않음 |
| 끊긴 시간 감소 | 장애 이후 영상이 돌아오는 시간을 줄인다 | 영상 정지를 감지하고 적절한 시점에 자동 복구 |
| 상태 안내 개선 | 현재 상황을 정확하게 알려 불안을 줄인다 | 최초 연결 중·자동 복구 중·최종 실패를 구분 |

세 가지 모두 필요하지만, 안내 문구가 좋아진 것을 연결 안정성 향상으로 계산하지 않는다. 마지막 수신 사진을 표시하는 경우에도 실시간 영상처럼 오인시키지 않고 사진·갱신 시점을 구분해야 한다. 사진 표시 자체는 끊김을 해결하지 않는다.

## 4. 앱에서 실제 안정성을 높일 수 있는 일

아래는 앱의 책임 범위다. **현재 상태**는 `0.133.12` 기준이다(✅ 구현 · ◐ 일부 · ✗ 미구현).

| 개선 영역 | 앱이 할 일 | 기대 효과와 한계 | 현재 상태 |
|---|---|---|---|
| 중복 연결 방지 | 자동 재시도·사용자 재시도·네트워크 이벤트가 겹쳐도 연결 시도를 하나로 조정 | 연결 시도끼리 충돌하거나 카메라에 요청이 몰리는 상황 감소 | ✅ 재시작 병합(`restart-merged`) |
| 이전 연결 정리 | 이전 세션의 늦은 응답·종료 처리가 새 세션에 영향을 주지 않도록 격리 | 복구 직후 다시 끊기는 앱 내부 경쟁 상태 방지 | ✅ 세대 분리 + 늦은 백그라운드 정리 격리 |
| 정상 연결 유지 | 네트워크 변경 알림만으로 연결을 즉시 버리지 않고 실제 영상 진행과 상태를 확인 | 불필요한 재연결 감소. 실제 경로 단절이면 복구 필요 | ✅ 1초 디바운스 + 영상 중이면 3초 유예 |
| 앱 복귀 처리 | 백그라운드 진입·복귀 때 타이머와 연결 생명주기를 일관되게 관리 | 복귀 후 연결 누락·중복 생성 감소 | ✅ 실기기 확인(복귀 2.7초) |
| 연결 절차 조정 | 연결 후보 주소(ICE) 수집·교환과 대기 시간을 상대방 지원 범위 안에서 조정 | 지나치게 빠른 실패 판정이나 후보 누락 가능성 감소. 시간만 늘리는 것으로 해결되지는 않음 | ✗ 보류 — 실측 비교 후 채택(기획 A6) |
| 영상 정지 감지 | 연결 상태뿐 아니라 수신·프레임 진행을 확인하고 통계 부재를 별도로 취급 | 연결됐다고 표시되지만 영상이 멈춘 상태 감지. 통계 조회 실패만으로 정상 연결을 끊지 않아야 함 | ✅ 5초 안내·15초 재연결, 통계 부재는 표시만 |
| 재시도 정책 | 짧은 장애와 지속 장애를 구분하고, 안정적으로 재생된 뒤 재시도 간격을 초기화 | 과도한 재접속과 복구 포기 감소. 너무 잦은 재시도는 오히려 부하 증가 | ✅ 90초 자동 복구 → 60초 저빈도, 30초 안정 후 초기화 |
| 진단 기록 | 연결 시작·첫 프레임·정지·종료 주체·재접속 사유를 시간순으로 기록 | 후속 개선의 원인 판단 근거 확보. 기록 자체가 장애를 고치지는 않음 | ◐ 앱 내부 기록 + 마이페이지 내보내기. 원격 기록은 기존 스키마(결과 행)만 — 정지 원인·재접속 사유는 원격에 없음 |

앱은 수신·재생 쪽 구현도 책임진다. 영상 데이터가 도착하는데 디코딩이나 화면 표시가 멈췄다면 앱·플레이어·코덱 호환성까지 확인해야 하며, 곧바로 펌웨어 문제로 넘기지 않는다.

## 5. 앱 단독으로 해결하기 어려운 일

| 문제·기술 | 앱에서 가능한 역할 | 함께 필요한 작업 |
|---|---|---|
| 카메라 메모리 부족·인코더 정지 | 감지·복구 시도·진단 제공 | 펌웨어의 자원 관리와 영상 생성 경로 수정 |
| 녹화·클립 업로드와 라이브의 자원 경합 | 발생 시점과 시청 영향을 기록 | 펌웨어의 작업 우선순위·메모리·전송량 조정 |
| 카메라 Wi-Fi 품질 불량 | 상태 안내와 재연결 | 기기 무선 진단, 설치 환경 개선, 펌웨어 대응 |
| TURN 중계 경로 | 서버가 제공하는 설정·인증정보를 사용하고 실제 선택 경로 확인 | 중계 서버 운영, 접근성·인증·용량·네트워크 설정 검증 |
| 미디어 서버 도입 | 서버를 통해 수신하도록 앱 변경 | 카메라 송출 방식·서버 운영·인증·비용을 포함한 구조 변경 |
| 가변 화질 | 지원되는 저화질 스트림 선택 또는 송신 측에 품질 조정 요청 | 카메라의 비트레이트·해상도 제어 또는 서버의 변환 기능. 앱 화면 크기만 줄여서는 전송량이 줄지 않음 |
| 키프레임 요청·ICE 재시작 | 사용하는 SDK·상대방이 지원하면 복구 절차 수행 | 펌웨어·시그널링의 지원과 호환성 확인 |
| 카메라 재부팅·전원 차단 | 상태를 정확히 표시하고 복귀 후 연결 | 전원이 없거나 영상 송출이 멈춘 시간 자체는 앱에서 제거 불가 |

중계 서버는 연결 경로 문제에 도움이 될 수 있지만 카메라가 보내지 않는 영상을 만들어주지는 않는다. 웹뷰 역시 수신 구현을 바꾸는 선택지이며, 같은 카메라·전송 경로의 장애가 자동으로 사라지는 것은 아니다.

## 6. 다음 담당자를 결정하는 데 필요한 증거

| 관측한 상황 | 우선 확인할 내용 | 판단 시 주의점 |
|---|---|---|
| 정상 프레임이 진행되는데 앱이 먼저 연결을 닫음 | 앱 종료 사유, 네트워크·생명주기 이벤트, 중복 요청 | 사용자 이탈 등 의도된 종료는 제외 |
| 앱 수신 패킷이 멈춤 | 카메라 송신량·인코더 상태, 실제 선택 경로, 서버 기록 | 앱 로그만으로 카메라와 네트워크 중 어느 쪽인지 확정 불가 |
| 영상 데이터는 수신되지만 프레임이 진행되지 않음 | 손실·키프레임·코덱 호환성·디코더·렌더러 | 수신량만으로 정상 영상이라고 판단하지 않음 |
| 녹화·업로드와 끊김 시각이 반복해서 겹침 | 카메라 메모리·CPU·전송량과 작업 시각 | 시간상 일치는 원인 후보이며, 비교 시험으로 확인 필요 |
| 특정 네트워크 또는 경로에서만 실패 | 직접 연결/중계 여부, ICE 실패 단계, TURN 접근성 | 같은 Wi-Fi라는 이름만으로 실제 경로를 추정하지 않음 |

**앱이 지금 판정할 수 있는 범위(`0.133.12`):** 영상 정지 때 그동안의 수신 바이트·손실 패킷 증가량으로 `no-data`(수신 멈춤)와 `data-no-decode`(수신은 되는데 프레임 정지)를 구분해 기록한다. 플랫폼이 수신량을 주지 않으면 `unknown`으로 남기고 추측하지 않는다. 실기기에서 휴대폰 망 단절을 `no-data`로 정확히 판정했다. 단 `no-data`만으로 카메라 송출 중단과 경로 단절을 가를 수는 없다(위 표 둘째 줄) — 휴대폰 망 상태(`network-none`)와 카메라·서버 로그를 함께 본다.

앱과 서버·카메라 로그는 가능한 범위에서 동일 세션과 시각으로 대조한다. 민감한 인증정보나 원본 SDP를 그대로 수집하는 방식은 피하고, 필요한 진단 항목은 기존 계약을 따른다.

## 7. 권장 진행 순서와 성공 판단

1. **기존 앱 개선을 실기기에서 검증한다.** 같은 Wi-Fi 장시간 시청, 앱 복귀, 네트워크 전환, 짧은 단절을 확인한다. 별도 구현을 중복 착수하지 않는다.
2. **펌웨어 확인을 병행한다.** 이미 전달한 요청서를 기준으로 자원 경합·송신 중단·세션 처리와 앱 로그의 시각을 대조한다.
3. **남는 장애 유형에 맞춰 다음 작업을 정한다.** 앱이 먼저 끊으면 연결 관리, 카메라 송신이 멈추면 펌웨어, 특정 경로만 실패하면 TURN·네트워크를 우선 검토한다. 미디어 서버 도입은 해결하려는 장애와 비용을 정한 뒤 별도 검증한다.

전후 비교는 가능한 한 같은 카메라·펌웨어·앱 기기·네트워크·녹화/업로드 조건에서 수행한다. 다음 지표를 함께 본다.

- **첫 영상 표시 시간과 연결 성공률:** 진입부터 첫 프레임까지. 실패한 시도도 포함해 별도 집계한다.
- **시청 시간당 정지 횟수와 총 정지 시간:** 초기 연결 대기와 재생 중 중단을 구분하고, 재접속 중 영상이 없는 시간도 빠뜨리지 않는다.
- **자동 복구 시간과 복구 실패 횟수:** 복구된 사례만으로 평균을 내서 장기 장애를 숨기지 않는다.
- **재접속 사유와 통계 누락:** 재접속 횟수만 줄어도 화면이 계속 멈췄다면 개선으로 보지 않는다. 통계가 없는 구간도 정상으로 처리하지 않는다.

현재 계측의 한계: 앱의 단계 시간(`t_ms`)은 **연결 시도마다 0부터** 잰다. 재시도가 끼면 “진입부터 첫 프레임까지” 고객이 기다린 전체 시간은 진단 기록의 UTC 시각을 이어 계산해야 한다. 원격 기록은 망 장애 중 유실될 수 있다(실기기에서 1건 확인).

목표는 “재접속을 덜 한다”가 아니라 **고객이 실제로 영상을 더 오래, 더 적은 중단으로 본다**이다. 현재는 개선 효과의 비율을 제시할 근거가 없으므로 실측 전 효과를 수치로 약속하지 않는다.
