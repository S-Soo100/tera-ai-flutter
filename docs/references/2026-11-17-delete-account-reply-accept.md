## 2. 남은 쟁점

### (a) 탈퇴자 커뮤니티 글 노출 — ③ RLS로 결정·**운영 적용 완료(2026-11-17)**

**현상:** 소프트 삭제라 `community_posts`·`community_comments`가 그대로 남는다. 앱 피드·댓글은 Supabase 직결 조회이고 작성자 이름은 `public_profiles` 뷰(`user_profiles`의 3컬럼)에서 가져오므로, 탈퇴자 글이 **30일 동안 이름·사진과 함께 계속 보인다.** 회신은 "앱 쪽 RLS·쿼리에서 처리"로 앱에 넘겼다(커뮤니티는 서버 API 밖). 앱이 30일 요청서 §4에서 서버에 고르라고 한 (a)(b)(c)는 이 회신으로 **앱 몫**이 됐다.

| 선택지 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| ① 그대로 둠 | 없음. 30일 하드 삭제 때 사라짐 | 작업 0 | 30일간 탈퇴자 글·이름 노출. 하드 삭제 작업이 아직 없어 사실상 무기한 |
| ② 앱 쿼리에서 거름 | `public_profiles`에 탈퇴 여부 컬럼 추가(뷰 변경) → 앱이 피드·댓글·작성자 화면에서 제외 | 앱이 표시 방식("탈퇴한 사용자")을 고를 수 있음 | **이미 깔린 앱(0.180.x 이하)은 계속 보임**, 앱 배포 필요, 조회 지점 여러 곳 |
| ③ **RLS로 제외 (추천)** | `community_posts`·`community_comments` SELECT 정책에 "작성자가 탈퇴하지 않음" 조건(`auth.users.deleted_at`을 보는 SECURITY DEFINER 함수) | 한 곳에서 모든 앱 버전에 즉시 적용, 앱 배포 불필요, 서버 탈퇴·운영자 대행 탈퇴 모두 덮음 | **운영 DB 변경**(사용자 승인 필요), 좋아요·댓글 수 집계가 숨긴 글과 어긋날 수 있어 함께 확인 |

- 추천은 ③. 진행하려면: `supabase/drafts/`에 SQL 초안 → 격리 DB 검증 → 사용자 승인 후 운영 반영(앱 운영 규칙). 좋아요(`community_likes`)·신고는 숨긴 글을 가리키므로 집계 표시도 같이 본다.
- 숨기기로 정하기 전까지 처리방침·탈퇴 화면에 "탈퇴 즉시 글 숨김"을 쓰지 않는다(30일 요청서 §4와 같음).

**결정과 진행(2026-11-17):** 사용자 결정 "③ DB에서 숨기기". 운영 DB 적용은 아직 승인 전이다.

- 초안: [`supabase/drafts/20261117_community_hide_deleted_authors.sql`](../../supabase/drafts/20261117_community_hide_deleted_authors.sql) — `public.community_author_active(uuid)`(SECURITY DEFINER, `auth.users.deleted_at`만 봄, anon 실행 불가)를 만들고 `posts_select`·`comments_select`·`likes_select`를 `USING (true)`에서 `USING (community_author_active(작성자))`로 바꾼다. 되돌리기 SQL은 초안 머리말에 있다. 파일은 검토용이라 `ROLLBACK`으로 끝난다.
- 좋아요도 넣었다: 앱의 좋아요 수(`community_likes(count)`)에서 탈퇴자 좋아요를 빼야 30일 뒤 하드 삭제 때 숫자가 갑자기 줄지 않는다.
- 관리자 예외는 두지 않았다: 앱에 신고 검토 화면이 없고(`community_reports`는 insert만), 예외를 두면 관리자 피드에만 탈퇴자 글이 보인다. 검토가 필요하면 SQL 콘솔로 본다.
- 운영 읽기 확인(쓰기 없음): 세 SELECT 정책이 마이그레이션과 같게 `true`. 소프트 삭제 계정 31개(테스트 계정 정리분)가 쓴 글·댓글·좋아요·신고는 모두 0개라 **적용 즉시 사라지는 행은 없다.**
- 격리 검증: `tools/verify_community_hide_sql.py`(네트워크 없는 `supabase/postgres:17.6.1.104` 컨테이너, 운영 마이그레이션 §3.1~3.3 → 초안 → `test/sql/community_hide_deleted_assertions.sql`, 전부 ROLLBACK). 21개 통과, 초안을 빼면 첫 숨김 검증에서 실패하는 것도 확인했다.
  - 탈퇴 전: 글 2·좋아요 3·댓글 2가 모두 보임(일반 글 영향 없음 기준선)
  - 탈퇴 후: 피드·단건·작성자 화면에서 탈퇴자 글 0, 일반 글 댓글 수 2→1, 좋아요 수 3→2
  - 일반 사용자의 댓글 작성, 좋아요 취소·재등록 정상. 관리자에게도 숨김
  - 신고: 신고자·관리자 모두 신고 행은 계속 봄(대상 글만 안 보임)
  - 없는 uid는 true(하드 삭제 뒤엔 FK CASCADE로 글이 같이 사라짐), 되돌리기 SQL로 원복됨
- 남는 것(이번 범위 밖):
  - 숨긴 글에 일반 사용자가 단 댓글 행은 남지만 글이 안 보여 앱에 나올 경로가 없다.
  - `public_profiles` 뷰는 탈퇴자 이름을 계속 준다. 다만 글·댓글이 숨겨져 그 이름을 볼 경로는 차단 목록 정도다.

- **운영 적용(2026-11-17):** 백승수가 Supabase SQL Editor에서 초안 본문을 `BEGIN … COMMIT`으로 직접 실행했다(MCP `apply_migration`은 승인 창에서 거절돼 쓰지 않음 — 그래서 `supabase_migrations` 이력에는 없다). 적용 뒤 확인:
  - `pg_policies`: `posts_select`·`comments_select` = `community_author_active(author_id)`, `likes_select` = `community_author_active(user_id)`
  - 함수: anon 실행 불가, authenticated 실행 가능, SECURITY DEFINER
  - 기존 데이터: 글 6개·좋아요 7개 모두 계속 보임(탈퇴자 몫 0이라 영향 없음)

- 원래 적어 둔 적용 절차: 초안 본문을 `apply_migration`으로 적용 → 운영에서 위 정책 3개 `qual` 다시 읽기 → 앱으로 피드·댓글이 정상인지 확인. 문제가 생기면 머리말의 되돌리기 SQL을 실행한다.

### (c) 회신 §5 확인 체크리스트 — 누가 어떻게

**`push_devices` 기대값 정정:** 앱의 로그아웃 정리는 `deactivate_push_device` RPC(마이그레이션 `20260915000000_fcm_notifications.sql`)로 **행을 지우지 않고 `enabled=false`**만 바꾼다. 발송 함수는 `enabled = true`만 고르므로 그 폰에는 더 안 간다. 그래서 "행이 사라졌음"은 설계상 실패한다. 확인할 것은 "**그 설치(installation_id) 행이 `enabled=false`**"이고, 행 삭제는 30일 하드 삭제 몫이다.

**같은 계정의 다른 폰 문제(서버 요청):** 앱이 끄는 건 탈퇴를 누른 폰 한 대뿐이다. 다른 폰·태블릿의 행과 **운영자 대행 탈퇴**(`X-Act-As-User`, 앱이 정리를 못 함)의 행은 `enabled=true`로 남아, 다른 사용자가 탈퇴자 글에 댓글·좋아요를 달면 푸시가 갈 수 있다.

| # | 확인 | 누가 | 방법 |
|---|---|---|---|
| 1 | 앱 탈퇴 → 200 → 로그인 화면 | 백승수(앱) | 0.180.2 빌드, 테스트 계정 a(기기 없음)·b(사육장·카메라+영상). **실제 탈퇴 실행은 사용자 승인 뒤** |
| 2 | 같은 메일·비번 로그인 실패 | 백승수 | 같은 폰에서 로그인 시도 |
| 3 | b의 기기·카메라를 다른 계정에 재등록 | 백승수 | 예비 계정으로 기기 추가 흐름 |
| 4 | 그 폰의 `push_devices` 행 `enabled=false` (위 정정) | 앱 세션(Claude, 읽기 SQL) 또는 이관훈님 | `select installation_id, enabled from push_devices where user_id = <uid>` — 읽기만, 사용자 승인 뒤 |
| 5 | 같은 토큰으로 두 번 연속 호출 → 둘 다 200 | 이관훈님(서버) | 앱은 첫 200 뒤 바로 로그아웃해서 두 번 부를 수 없다. 탈퇴 직전 토큰으로 curl 2회 |
| 6 | `auth.users.deleted_at` 기록 확인 | 이관훈님 또는 앱 세션(읽기 SQL) | — |

테스트 계정 a·b는 아직 정하지 않았다 — 기존 테스터 계정을 쓰지 말고 새로 만든다(실사용 데이터 손실 방지).

## 3. 서버에 다시 요청할 것

1. **탈퇴 때 그 사용자의 `push_devices`를 모두 끄기(`enabled=false`) 또는 삭제** — 다른 폰·운영자 대행 탈퇴를 덮으려면 서버가 해야 한다. 회신 §3 끝의 "안 지워지면 서버에서 지우도록 바꿀게요"를 받아들이는 요청이다.
2. 회신 §5의 `push_devices` 기대값을 "행 삭제"가 아니라 "`enabled=false`(하드 삭제 때 행 삭제)"로 고쳐 주세요.
3. 30일 요청서 §1의 "404면 웹 삭제 안내"는 0.180.2에서 없앴다(정정 알림).
4. 30일 요청서의 남은 회신: 30일 삭제 작업 일정·실행 방식, 라벨링 데이터(삭제/익명화), `auth.users` DELETE 트리거 500 수정 계획.
5. 체크리스트 #5(같은 토큰 두 번 호출)는 서버 쪽에서 curl로 확인해 주세요.
