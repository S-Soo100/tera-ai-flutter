## 3. 온습도 데이터와 색상

### 3.1 날짜별 대표값

- 상세 날짜 범위는 현행처럼 해당 날짜 자정부터 다음 자정 직전까지. 밤 활동의 날짜 경계와 혼용하지 않는다.
- 오늘: 선택 사육장의 실시간 센서 A. 최신성은 기존 telemetry stale 기준을 재사용한다. 수신 전·오프라인의 마지막 버킷을 ‘실시간’처럼 대체하지 않는다. 미수신은 `--`, 마지막 수신값을 남긴다면 마지막 수신시각을 명시한다.
- 과거: `envDayBucketsProvider`와 같은 날짜의 유효 버킷을 사용한다. 일평균 전용 도메인 계산을 추가하고 차트 마지막 점 조회(`tempAt(1.0)`)를 대표값에서 제거한다.
- 기본 계산안은 `Σ(버킷 평균 × 유효 표본 수) / Σ(유효 표본 수)`. 현재 모델에는 공통 `sampleCount`만 있어 온도·습도별 유효 개수와 같은지 확인이 필요하다. 같다는 계약을 확인하지 못하면 정확한 원시 일평균으로 단정하지 않고, 서버에 지표별 count/sum 또는 일평균 제공을 요청한다. 임의로 ‘평균의 단순 평균’을 대신 넣지 않는다.
- 센티넬 0, null, 비정상 값, 표본 수 0을 제외한다. 온도·습도는 각각 유효 집합을 계산한다. 이 프로젝트의 센티넬 규칙을 적용하는 것이며 일반적인 모든 온도 데이터에서 0℃를 배제한다는 뜻은 아니다.
- 관측이 끊긴 구간은 보간해 채우지 않는다. 표본이 없으면 `--`; 로딩·조회 실패·유효 데이터 없음은 구별한다.
- 날짜 변경과 자정 경과 시 대표값·최고최저·차트·라벨의 날짜가 일치해야 한다. 선택 사육장이 바뀌면 이전 기기의 응답을 버린다.
- 평균/실시간을 구별하는 짧은 라벨을 권장한다. 스크러버의 특정 시각 값은 별개이며 평균 상태 자체를 바꾸지 않는다.

### 3.2 주간 막대

Figma `945:3428` 확인: 일반 막대 `#626262`, 최저 막대 `#B4AEAE`, 온도 강조 막대 `#D61619`, 습도 강조 막대 `#2E408C`. 목·금의 온도 최저값이 같은 예시에서 두 막대 모두 연회색이다. 하단 부록에 원본 화면을 연결했다.

- `DayMinMax.max` 중 주간 최고값에 해당하면 강조, `DayMinMax.min` 중 주간 최저값에 해당하면 연회색, 나머지는 일반 회색.
- 동률 최고·최저는 해당 요일 모두 적용한다. 동률 판단은 표시 정밀도와 일치하는 반올림값으로 통일하는 안을 권장한다.
- 한 막대가 최고와 최저를 모두 가지면 강조색 우선. 최저 수치는 별도로 보이게 해 의미를 보존한다. 모든 날 값이 같거나 유효 요일 하나뿐이면 일반 회색으로 표시하는 예외안을 둔다.
- 최고/최저 숫자·요일의 색도 역할에 맞춘다. 빈 요일은 축을 유지하고 가짜 막대를 만들지 않는다.
- 문자색과 그래프색은 역할이 다르다. `textSecondary`를 회색 막대 토큰으로 재사용하지 않고 그래프 전용 일반·최저 토큰을 둔다.
- Figma 샘플 습도 수치에는 축과 맞지 않는 값이 있다. 샘플 숫자는 데이터 계약으로 사용하지 않는다.

## 4. 카메라 목록·기간·캐시

### 4.1 조회와 표시 상태

- 필터 모델은 `전체 기간` 또는 `명시 범위(start, endExclusive)`. 초기값은 전체 기간이다. 단일 날짜를 고르면 하루 범위로 정규화한다.
- 기간 버튼은 **필터 상태만** 읽는다. 첫 클립 시각, 마지막 조회 시각, 자정 타이머로 자동 변경하지 않는다. 피커 취소는 상태를 바꾸지 않는다. 명시적으로 오늘을 골라도 날짜 라벨을 표시한다.
- 기본 목록은 현재 선택 카메라의 서버에 남아 있는 전체 영상이다. 보관 정책으로 삭제된 원본을 복구한다는 뜻은 아니다. 날짜를 넘길 때 날짜 머리글·구분선, 그 아래 시간대별 3열 그리드.
- 서버 조회는 `(started_at DESC, id DESC)`의 안정된 순서와 복합 커서 사용. 제안 페이지 크기 60. 다음 페이지는 마지막 키보다 오래된 항목, 마지막 페이지 판정은 `hasMore` 또는 1개 초과 조회로 처리한다.
- 동일 타임스탬프·중복 응답은 ID로 중복 제거. 페이지 경계에서 같은 시간대 그룹을 합친다. 오래된 영상이 하나도 빠지지 않아야 한다.
- 카메라·계정·기간을 조회키로 삼는다. 필터 변경 시 진행 중 응답을 새 목록에 섞지 않도록 요청 세대 식별자를 사용한다.
- 표시 상태: items / cursor / hasMore / initialLoading / refreshing / loadingMore / pageError. 추가 로드 실패는 기존 목록 아래 재시도만 표시한다.
- 최신 영상 도착은 사용자가 중간을 보는 동안 앞에 즉시 삽입하지 않는다. 상단 복귀 또는 명시 새로고침에서 반영한다. 카메라 전환 시에는 해당 카메라·필터에 보관한 위치를 복구하는 안을 권장한다.
- 시간대 클릭의 재생목록 범위는 현행 ‘그 시간대’ 유지. 페이지 경계로 시간대가 잘려 있으면 플레이어도 같은 시간대의 나머지 항목을 이어 조회해야 한다. 로드된 일부만 전체인 것처럼 표시하지 않는다.

### 4.2 스크롤 버그: 확인한 사실과 가설

확인한 코드 경로:

1. `camerasProvider`는 cameras 테이블 이벤트마다 전체 카메라 목록을 재조회한다.
2. `crecamResolvedDayProvider`와 `crecamHourGroupsProvider`는 `camerasProvider.future`에 의존한다.
3. `_HourClipSections`는 loading에서 기존 목록 대신 `_SectionsSkeleton`을 그린다.
4. 화면은 `SingleChildScrollView → Column`이며 별도 위치 보존 컨트롤러가 없다. 라이브 유지 목적 때문에 모든 영상 셀을 한꺼번에 구성한다.

**가설:** 카메라 갱신이 클립 목록 재계산으로 전파되고 스켈레톤으로 높이가 줄어들면 현재 offset이 작은 maxScrollExtent로 보정될 수 있다. 사용자에게 새로고침처럼 보이는 현상과 맞지만, 실기기 재현으로 확정하지 않았다. `RefreshIndicator`가 실제 발화했는지와 목록 높이 변경을 구분해야 한다.

구현 전 진단: refresh 콜백 횟수, offset/maxScrollExtent, provider 전이, cameras 이벤트, lifecycle resumed를 같은 타임라인으로 기록. 중간 위치에서 카메라 상태 이벤트·앞뒤 스크롤·탭 복귀를 각각 재현한다.

수정 방향: 클립 조회 의존성을 선택 cameraId·필터 중심으로 축소, 갱신 중 기존 items 유지. 지연 생성 Sliver 목록과 안정된 key/ScrollController를 사용한다. 라이브의 컨트롤러·renderer 수명은 목록 가상화와 분리하여 화면 밖으로 갔다 돌아와도 WebRTC를 다시 연결하지 않는다. 당김 새로고침은 최상단에서 시작한 세로 사용자 제스처에만 반응한다. 단순히 RefreshIndicator를 삭제하는 것으로 종료하지 않는다.

### 4.3 업데이트 문구

- 달력 날짜 차이를 기준으로 오늘 / 어제 / N일 전. 23:59에 갱신되어 00:01에 보면 ‘어제’다. 경과 시간 24시간 나눗셈을 쓰지 않는다.
- 엔트리 전용 formatter를 두어 다른 화면의 `timeAgo` 정책까지 바꾸지 않는다. 문구는 l10n으로 관리한다.
- 북마크는 마지막 추가 시각(`favoritedAt`), 하이라이트는 **묶음 도착 시각**. 촬영시각을 도착시각 대신 쓰지 않는다.
- Figma의 짧은 한 줄을 유지하려면 현재 붙어 있는 ‘어젯밤 활동 N분 ·’은 이 자리에서 제거한다. 활동 정보는 MyCre의 활동 화면에서 다룬다.
- 데이터 없음은 ‘아직 없어요’, 오류는 로드 실패, 로딩은 고정 높이 스켈레톤으로 구분한다.

### 4.4 썸네일 캐시

현재 `MotionClipThumb`는 `CachedNetworkImage(cacheKey: thumb_<clipId>)`를 쓰므로 캐시 자체는 존재한다. `motionThumbnailProvider` 완료 전에는 캐시 이미지도 렌더하지 못한다.

- Repository에서 파일 존재를 먼저 검사해 바로 반환한다. 미스일 때만 presign·다운로드. 동일 키 요청은 하나로 합친다.
- 키는 계정·카메라·clipId·썸네일 버전으로 구성한다. URL의 만료 서명은 키에 넣지 않는다. 버전이 없으면 원본 교체 시 무효화 계약이 필요하다.
- 화면 안과 바로 다음 화면 정도만 선행 로드한다. 전체 기간 영상을 처음부터 다운로드하지 않는다. 기존 동시 요청 제한을 재사용한다.
- 캐시 정책 제안: 최대 200MB, 최근 사용 우선 제거. 앱 재시작에도 남되 로그아웃·계정 전환 시 다른 계정 파일을 표시하지 않는다. 파일 삭제·오류·용량 부족이면 네트워크 폴백, 권한 오류/없는 썸네일을 영구 실패 캐시로 고정하지 않는다.
- 검증: 첫 조회 후 오프라인 재방문에서 같은 썸네일 표시, 캐시 히트 시 presign 0회, URL 만료 후에도 캐시 히트, 로그아웃 후 미노출.

## 5. 하이라이트 도착과 읽음

### 5.1 날짜 개념 분리

`촬영 구간(start/end)` / `밤 묶음 식별자` / `도착시각(publishedAt)` / `읽은 시각(readAt)`을 별개로 둔다.

사용자 요구는 **전날 밤~당일 아침 촬영분이 당일 도착**하는 것이다. 현재 서버 모델은 20:00 KST 경계의 day_key로 조회 시 대표를 계산하고, `/highlights/featured` 응답에는 확정된 도착시각이 없다. 현재 최신 대표의 `startedAt`을 읽음 키로 쓰면 대표 교체 시 같은 밤을 다시 신규로 보여줄 수 있다.

권장 계약:

- 서버가 `batchId`, `cameraId`, `captureStart`, `captureEnd`, `publishedAt`, `status=ready`, 대표 클립 목록을 반환한다.
- 밤 수집 구간은 현행 앱 리포트의 22:00~06:00을 출발안으로 삼되, 서버 20:00 경계와의 차이는 서버 담당과 합의해 확정한다. 앱 혼자 시각을 잘라 서버의 선정 결과를 재정의하지 않는다.
- 완료된 전날 밤 묶음만 ‘도착’ 대상으로 삼는다. 진행 중인 오늘 밤은 이 카드로 알리지 않는다. 아침 처리 지연 시 준비 완료 후 표시한다. 영상 없는 밤은 빈 도착 카드를 만들지 않는다.
- 정상 도착시간은 백엔드의 완료 기준이 결정한다. 앱의 특정 시각 타이머만으로 존재하지 않는 묶음을 만들어 표시하지 않는다.
- 현재 API의 최근 30일/상한 31일 제약은 하이라이트 이력 전기간 조회와 별개다. 요청 3-4의 일반 클립 전체 조회는 구현 가능하지만, 하이라이트도 전기간 조회로 확장하려면 별도 커서 API가 필요하다.

대안: 클라이언트만으로 끝난 밤을 걸러 임시 배치를 만드는 방법은 빠르지만 도착시각·대표 확정 여부가 부정확하다. **서버의 완료 묶음 계약을 권장**하며 이 부분만 계약 확정 후 구현한다. 나머지 앱 개선은 독립적으로 진행할 수 있다.

### 5.2 읽음 상태

- 상태: 준비 전 → ready+unread → 재생 시도 → 실제 재생 시작 → read.
- 사용자 확정에 따라 단순 카드 탭·플레이어 진입·컨트롤러 초기화만으로 읽음 처리하지 않는다. 준비된 영상의 첫 프레임과 재생 진행을 확인한 이벤트를 사용한다. 하이라이트 `playFromSec`이 있으므로 절대 position>0 검사만으로 판정하지 않는다.
- 읽음 키는 `(ownerId, cameraId, batchId)`. 다른 카메라·다른 밤을 읽음 처리하지 않는다. 해당 묶음의 어느 대표를 재생하든 읽음 처리하고, 뒤로 돌아오면 카드가 사라진다.
- 같은 배치 내 대표 교체는 읽음을 되돌리지 않는다. 새로운 밤 배치 도착은 새 카드다. 로컬 저장 후 필요하면 서버 읽음 저장소에 동기화한다. 다중 기기 동기화 지원 여부는 계약에서 명시한다.
- 여러 미확인 밤이 있으면 최신 한 카드를 표시하고 나머지 영상은 날짜 목록에 둔다. 오래된 것을 자동 읽음 처리하지 않으며, 새 카드를 읽었다고 즉시 더 오래된 도착 카드가 연달아 튀어나오지 않게 한다.
- Figma `NewHighlight`의 X는 읽음과 별개인 ‘카드 숨기기’로 유지하는 안이다. X를 눌러도 영상 시청 이력은 생기지 않는다. 숨김 키 역시 배치별로 저장한다.
- Figma의 날짜 샘플은 2~3일 범위지만 이번 요구에 맞춰 `9월 12일 밤–13일 아침`처럼 실제 수집 구간을 표기한다.

## 6. 플레이어와 북마크

### 6.1 화면 방향

- 모든 이번 작업 대상 확대 진입점은 세로 기본. `CameraLiveFullscreenScreen`의 init에서 가로 강제를 제거하고 세로/가로 보기 UI 상태를 분리한다.
- 클립은 Figma `941:1834` 세로, `941:1928` 가로를 기준으로 한다. 가로 진입은 전용 버튼 탭만 허용한다. 기기를 물리적으로 눕힌 것만으로 방향이 바뀌지 않는다.
- 회전 전후 현재 clipId·재생 위치·재생/일시정지·배속·북마크 상태를 보존한다. 라이브는 같은 세션을 유지한다. 가로에서 닫기/뒤로가기 시 이전 화면과 세로 방향·상태바를 복원한다.
- 화면 방향 전환과 카메라의 `rotate_180` 설정은 별개다. 가로 보기 버튼이 기기에 PATCH나 재부팅 명령을 보내면 안 된다.
- 라이브는 세로 전체화면의 영상 배치·닫기·가로 보기 조작을 적용하되, 녹화 영상 전용 타임라인·배속·썸네일 목록은 제공하지 않는다.
- Figma 추가 차이: 아래쪽 이전/다음 버튼, 다운로드→공유→북마크 순서, 하단 썸네일 스트립, 10초 이동 제스처, 영상 하단 시크 핸들, 닫기·삭제 SVG. 현행 코드의 `fast_rewind/fast_forward` 버튼 열과 하단 배치가 다르다.
- 좌우 더블 탭=10초 이동, 좌우 스와이프/이전다음 버튼=영상 이동으로 역할을 분리하는 안이다. 이로써 싱글 탭과 더블 탭 경합을 없앤다. 자동 다음 영상은 Figma 메모상 하이라이트에만 적용되므로 일반 시간대 플레이리스트의 현재 자동 다음 정책과 함께 검토한다.
- 삭제 버튼은 디자인만 맞춘다고 삭제 대상을 임의로 정하지 않는다. 원본 클립 삭제인지 북마크 해제인지 각 진입 문맥의 기존 권한·기능 계약을 확인하고 배선한다.

### 6.2 조용한 북마크

- 탭 즉시 북마크 아이콘을 선택 상태로, 진행/성공 토스트는 표시하지 않는다. 재생·탐색·다른 버튼을 공용 `_busy`로 잠그지 않는다.
- 클립별 저장 작업 상태와 낙관적 북마크 상태를 둔다. 빠른 연속 탭은 마지막 의도를 반영하고 추가/삭제 응답 순서가 뒤바뀌어도 상태가 역전되지 않게 직렬화한다.
- 현행 Repository가 수행하는 로컬 영상 저장·클라우드 동기화의 계약을 유지하면서 화면에서 진행을 떼어낸다. 화면 이탈 후에도 작업은 계속되며 완료 시 북마크 목록과 업데이트 날짜를 갱신한다.
- 실패를 성공으로 숨기지는 않는다. 일시 실패는 제한된 재시도, 최종 실패는 상태 복구와 아이콘 옆 짧은 재시도 표시를 제안한다. 기존 저장 실패 토스트는 이 동작에서 제거한다.
- 다운로드·공유는 북마크와 다른 동작이므로 이번 북마크 무토스트 정책을 무조건 전파하지 않는다.

## 7. 홈 팬과 일정

- 권장 UI는 바텀시트. 시간 선택이 필요하므로 일시적인 토스트보다 조작·취소가 명확하다.
- 꺼짐 타일 탭→시간 선택. 현행 선택지 10분/30분/1시간/2시간을 재사용한다. 직전 값은 선택 제안으로만 쓰고 자동 실행하지 않는다.
- 선택→`시작`의 명시 버튼으로 명령을 보낸다. 기존 ‘계속 켜기’는 별도 선택지로 유지하는 제안이며 기본으로 자동 실행되지 않는다. 시간 제한만 제공하려면 이 선택지 제거를 구현 전에 확정한다.
- 시트 열기·옵션 선택·닫기는 명령 0건. 시작 연타는 명령 1건. 시트가 열린 뒤 대상 기기가 바뀌거나 오프라인이 되면 원래 대상·가용성을 다시 확인한다.
- 작동 중 타일 탭은 현행처럼 `fan_off`로 즉시 정지. 타이머 변경은 시트에서 수행하고, 새 시작이 기존 타이머를 대체한다.
- `fan_on + duration_ms`와 펌웨어 자동 OFF, 명령 ACK/실패 처리, 알림 예약을 재사용한다. 앱 타이머가 나중에 OFF를 보내는 방식으로 바꾸지 않는다.
- `home_routine_settings` 표시를 `일정`으로 변경. 반복 일정 편집 기능과 현재 작동 중 타이머는 유지한다.

기기 연결 v3에서 도출한 요구: BLE 검색/빈 상태/재검색, 기기 1개·2개 선택, 네트워크 목록·직접 입력·비밀번호 기억·실패, 연결 중 취소, 완료 후 함께/따로 사용, 그룹 없음·있음 상태, 그룹명 중복·10자 검증, 그룹 구성원 선택·교체·제외, 기기 이름 변경·삭제. 베타는 사육장/카메라/개체 각 1개라는 Figma 메모가 있으나 두 개체를 그린 이전 화면도 있으므로 각 1개를 설계 기준안으로 삼는다.

그룹 관리의 ‘전원 켬/끔’은 카메라 네트워크 연결 상태와 다르다. 실제 전원 제어 API가 있는지 확인 후 구현하고 온라인 상태를 전원 명령처럼 흉내내지 않는다. 다기기 동시 등록·자동 그룹화·LCD 이름 동기화도 현재 BLE Wi-Fi 전용 계약을 넘어가는 부분이라 서버/펌웨어 계약을 함께 정리한다.

기기 연결 v1/v2, Color, ASIS, 버린 시안, Refer는 비교 기록으로 목록화했다. 같은 화면의 변형을 전부 별개 기능으로 구현하지 않는다. v3의 `입력필드` 등 미완성 개체 등록 문구는 확정 요구로 채택하지 않는다.

앱 구현 단계 공통 검증: `flutter analyze` 에러 0, 영향 범위 테스트, iOS/Android의 393pt 기준 및 작은 화면·글자 확대 비교. 실제 장치의 스크롤·재생·팬 ACK 검증을 정적 분석 통과로 대체하지 않는다. 대규모 변경은 기능별로 순차 처리하고 실패 수정 루프는 3회 이내로 제한한다.

### 설계 상태와 남은 확인

- 확정: 요청 1~8, 실제 하이라이트 재생 시작 시 읽음.
- 권장안: 기간 범위+전체 해제, 60개 커서 페이지, 200MB 캐시, 팬 시트의 선택 후 시작, 기존 계속 켜기 유지, X=숨김, 플레이어 제스처 역할 분리.
- 구현 전 계약 확인: 평균의 지표별 유효 표본 수, 밤 수집 구간·배치 ready/publishedAt, 하이라이트 장기 이력 API, 기기 연결 v3의 전원·그룹·다기기 연결 계약.
- 검증 한계: Figma 실조회 및 코드 대조 완료. 실기기 화면 캡처와 스크롤 버그 재현, 서버 새 계약 구현은 수행하지 않았다. 전체 페이지 화면 목록은 감사 문서에 있으며, 핵심 요청 화면은 PNG 시각 확인, 기기 연결 v3는 구조·텍스트·전체 흐름 수준의 조사다.

### 문서 검증 기록

- 요청 번호 전체와 후속 읽음 결정을 대조했다. 로컬 문서·PNG 링크의 누락 0건, 미작성 placeholder 0건.
- `flutter analyze --no-pub`: error 0, warning 0, 기존 info 7건으로 종료코드 1. 앱 코드는 변경하지 않았으며 이를 분석 전체 무경고 통과로 보고하지 않는다.
- 문서·참조 이미지 변경이므로 앱 기능 테스트/실기기 재현은 실행하지 않았다. 위 구현 검증 표는 후속 작업의 합격 기준이다.
