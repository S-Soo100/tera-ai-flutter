- 게코를 위한 스마트 사육장과, 소형 캠과 연동해서 사용하는 앱. 주요기능은 사육장의 온습도 조절 장치 원격 조정, 펫캠 확인.

- **통계**: 온습도 그래프, 크레 활동 통계 및 분석
- **마이크레**: 사용자가 크레 정보
- **커뮤니티**: 사육정보 공유
- **기타 기능**
  - 푸시: 주기적인 사육장 청소 알림, 온도 경고 알림

## 4. 세부 명세

**4.1 기간 선택 바** — `[일간] [주간] [월간]` 세그먼트
- 일간: 선택 날짜의 `07:00 ~ 익일 07:00` (**10분 단위** 포인트)
- 주간: 최근 7일 (일 단위) / 월간: 최근 30일 (일 단위)

**4.2 메트릭 필터 칩** — `[전체] [🌡온도] [💧습도] [🏃활동량]`, **다중 선택 가능**
- `[전체]` 선택 시 Y1(온습도 라인) + Y2(활동량 막대) + 동작 마커 복합 표기
- 단품 모드에서 미지원 메트릭은 Disabled

**4.3 메인 다축 차트**

| 구분 | 데이터 | 시각화 |
|---|---|---|
| Y1축 (좌) | 온도(℃), 습도(%) | **주황색(온도) / 파란색(습도)** 라인 |
| Y2축 (우) | 활동량(%) | **보라색 세로 막대** (AI Vision 움직임 비율) |
| 동작 마커 | 기기 제어 이벤트 | 분무💦·팬🌀·히터🔥·LED💡 가동 시점 아이콘 |
| 인터랙션 | 터치 & 드래그 | 임의 시점 터치 시 툴팁 팝업 |

**4.4 AI 인사이트 카드** — 주간 이상 데이터 누적 시 자동 생성
- 주요 요약 예: *"젤리는 평균 온도 24.5℃, 습도 65%에서 가장 왕성하게 활동해요."*
- 개선 제안 예: *"야간(22시 이후) 습도가 80% 이상으로 유지되는 경향이 있습니다. 팬 환기 일정을 조정하는 것을 권장합니다."*

**4.5 주간 행동 요약** — 활동/휴식 시간, 식사/물 마신 횟수를 요일별 **누적 막대**로. 요일 터치 시 해당 날짜 일간 차트로 재갱신.

**4.6 주간 온습도 범위 차트** — 요일별 Min-Max 범위 바. **개체 프로필의 적정 온·습도 구간을 초록 밴드로 레이어링**해 이탈 여부 시각화.

**4.7 공간 히트맵** — 펫캠 AI Vision 개체 좌표 추적. 사육장 그리드 위 체류 시간 색상 분포(Red 최고 ~ Blue 최저). 은신처·바스킹 존·쿨존 이용 비율 파악.

**4.8 기기 작동 이력 (Audit Log)** — **홈 탭에서 이관된** 작동 이력 전체 조회
- 필터: `[전체] [자동 일정] [수동 제어] [안전 가드 작동]`
- 표시: 타임스탬프(HH:mm:ss), 기기 아이콘·이름, 실행 주체(일정/타이머/수동), 상세 이유
- 페이징: 20건 단위 무한 스크롤 또는 `[더보기]`

## 7. 구현 결정 로그

> 위 §1~6은 노션 **원문 전사**라 손대지 않는다. 원문의 모순·공백을 구현이 어떻게 메웠는지는 여기에만 적는다.

### D1 — 하루 경계 = `07:00 ~ 익일 07:00` (Q9 해소)

- **결정일**: 2026-08-05 (구현), 2026-08-08 (문서화)
- **채택**: §5-1.2의 `07:00 ~ 익일 07:00`. §4-가의 `어제 19:00 ~ 오늘 07:00`은 **불채택**.
- **근거**: §4-가는 "간단 하루 통계"라는 좁은 맥락의 서술인 반면, §5-1.2는 화면 정책으로 명시된 시간 정책이다. 타임라인 날짜 스크롤러·요약 칩·당일 최고/최저가 전부 같은 창을 써야 해서 하나로 통일이 불가피했다.
- **구현**: `lib/features/home/domain/day_window.dart` (`DayWindow.of` / `DayWindow.forDate`). `06:59`는 전날 창에 속한다.
- **주의 — 혼동하기 쉬운 이웃 개념 2개**:
  - `DayWindow.chartRange` = **전날 19:00 ~ 현재**. §5-1.2의 "최근 24시간 차트" 전용이며 하루 창과 공유하지 않는다. §4-가의 19시가 여기서 살아 있는 셈이다.
  - 어젯밤 리포트의 `lastNightSince/lastNightEnd` = **22:00 ~ 06:00**. 마이크레 탭 전용으로 위 둘과 무관하다.
- **⚠️ 노션 원문 정정 필요**: 원문 §4-가의 "어제 오후 7시 ~ 오늘 오전 7시"는 여전히 모순 상태다. Notion MCP 인증 후 원문을 고쳐야 이 결정이 SOT에 반영된다.

### D4 — 라이브 아래 컴팩트 제어 바 (Figma 피드백 F1 해소)

- **결정일**: 2026-08-08 (사용자 결정)
- **문제**: PRD §3.3 서브탭은 `[사육장 제어]`와 `[타임라인]`을 **전환식**으로 두는데, Figma 피드백은 *"캠을 보면서 IoT 기능을 조작할 수 있도록 버튼이 캠 아래 작게"* — 라이브와 제어의 **동시 표시**를 요구한다.
- **채택**: 서브탭 구조를 **유지**하고, 라이브 바로 아래(`TopFixedArea`와 `HomeSubTabsBar` 사이)에 컴팩트 제어 바를 얹는다.
- **기각한 대안**:
  - *서브탭 폐지, 한 화면 세로 연결* — 타임라인이 무한 스크롤(Sliver)이라 제어가 계속 아래로 밀리고, `IndexedStack`의 지연 빌드 최적화(첫 방문 전까지 타임라인 조회·썸네일 요청을 미루는 장치)도 함께 버려야 한다.
  - *영상 위 반투명 오버레이* — 영상을 가려 "파충류 관찰"이라는 캠의 목적과 충돌한다.
- **노출 조건**: **통합 세트(`DeviceMode.integrated`)에서만.** 사육장 단품은 위에 라이브가 없어 "보면서 조작"이 성립하지 않고, 캠 단품은 제어할 기기 자체가 없다.
- **역할 분담**: 바는 **즉시 토글**(팬/히터/LED/분무), 서브탭의 2x2 그리드는 **상세**(LED 밝기 슬라이더, 상태 라벨). 시각적 중복은 감수한다.
- **⚠️ 안전 요구**: 제어 진입점이 둘이 되었으므로 명령 로직을 `home/presentation/cage_control_actions.dart` 하나로 추출했다. **히터는 과열 시 개체 폐사로 이어지는 유일한 액추에이터**라 두 진입점이 같은 2단 안전 확인(안전잠금 해제 → 조작 확인)을 공유해야 한다. 새 제어 진입점을 만들 때도 **반드시 이 모듈을 경유**할 것 — 위젯에 복붙하면 한쪽만 고쳐지고 다른 쪽이 안전장치 없이 남는다.
- **구현**: `widgets/live_control_bar.dart`, 테스트 `test/features/home/live_control_bar_test.dart`

### D5 — 통계 탭 24시간 온습도 그래프 (§4-나 일부 구현)

- **결정일**: 2026-08-08
- **범위**: Figma가 그려준 「온습도 그래프 - 24시」**만** 구현했다. 같은 섹션의 `주간` · `주간 온습도 분포` · `행동 분석`은 제목뿐이라 만들지 않았다. 피드백도 *"7일, 30일은 어떻게 봐야할지 감이 안 옴"*이라 명시하고 있어, 임의로 그리면 되돌릴 일만 생긴다. 화면에는 "준비 중인 통계" 카드로 대기 상태를 밝힌다.
- **차트 구간 = 홈 미니 차트와 동일**(`DayWindow.chartRange`, 전날 19:00~현재). PRD §3.4가 홈 차트를 터치하면 통계 탭으로 보내는데, 두 화면이 다른 구간을 보여주면 "방금 본 그래프"가 아니게 된다. 버킷 조회도 홈 provider를 재사용해 같은 질의를 두 번 만들지 않는다.
  - ⚠️ 단 **상단 요약 바의 최고/최저는 당일(07:00~) 기준**(`todayExtremesProvider`)이라 차트 구간과 창이 다르다. 의도된 차이다(D1의 세 시간 개념 참조).
- **듀얼 축 처리**: 온도(좌)·습도(우)는 단위가 달라 같은 Y축에 못 올린다. `StatsChartData`가 각자의 `AxisBounds`로 **0~1 정규화**해 그리고, 축 라벨만 실제 눈금을 보여준다. Figma도 Y축을 텍스트 6개 균등 배치 컬럼으로 그렸다 — 좌우 눈금 개수가 달라도 각 축이 자기 범위를 선형 분할하므로 균등 배치가 곧 정답이다.

### D6 — ⚠️ 미결: 사육장 : 개체 = 1:N 전환 (영향 범위 분석)

- **발단**: 원문 댓글 *"크레를 포함해서, 1:N(한개의 사육장, n마리의 도마뱀)이 되어야 할 거 같아요!"* (§5-C)
- **상태**: **결정 안 됨. 코드 미변경.** 현재 전 구조가 §2 전제("사육장 1 : 캠 1 : 개체 1") 위에 서 있다.
- **1:N이 확정되면 바뀌는 것**:

  | 대상 | 현재 | 필요 변경 |
  |---|---|---|
  | `EnclosureSet` | `Pet? pet` 단일 | `List<Pet> pets` |
  | `Pet.enclosureId` (Hive 13) | 개체 1 → 사육장 1 | 방향은 유지 가능(N:1이므로). **스키마 변경은 불필요할 가능성** |
  | `EnclosureSetRepository.listSets` | `_firstWhereOrNull(pets, ...)` — **첫 개체만 집는다** | 전체 수집 |
  | `EnclosureSet.displayLabel` | `젤리 (1번 사육장)` | 다개체 표기 규칙 필요 |
  | 헤더 드롭다운 / 상단 스와이프 | 세트 = 개체 1:1 가정 | 세트 안에서 개체를 또 고르는 축이 생긴다 |
  | `PetProfileCard` (사육장 단품) | 개체 1명 카드 | N명 표현 필요 |
  | 타임라인·어젯밤 리포트 | 세트당 개체 1 | 개체별 분리 or 합산 결정 필요 |

- **Figma 피드백과 연결됨**: *"다개체일 경우의 UX/UI 고민 필요"*, *"다개체 일때 UXUI — 스위치 or 한번에 보이게"* (`docs/figma-final-design-transcript.md` §2.1·§2.2). **화면 설계가 아직 없다.**
- **판단**: 도메인 근간이 바뀌는 변경이고 UX 설계도 없어, 확정 전에는 손대지 않는다. 지금 1:N으로 미리 열어두면 화면 설계가 나왔을 때 다시 뒤집힐 가능성이 높다.
