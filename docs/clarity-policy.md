# Clarity 운영·측정 정책 초안

작성일: 2026-09-12 · 대상: 비바나트 Android/iOS · 확인한 SDK: `clarity_flutter 1.10.0`

**상태: 목적 합의 완료 / 세부 정책 제안 / 앱·대시보드 적용 전.** 이 문서를 작성했다고 아래 규칙이 구현되거나 수집 설정이 바뀌는 것은 아니다. 코드에 확인된 사실과 제안 정책을 구분한다.

## 1. 합의된 목적과 접근

사용자가 합의한 목적은 두 가지다.

1. 사용 흐름에서 막히는 지점을 발견하고 개선한다.
2. 어떤 기능을 많이 사용하고 좋아하는지 파악한다.

**추천: 최소한의 명시적 이벤트 + 세션 단위 사용 비교 + 리플레이 검토.** 화면 조회만 비교하면 자동 진입·자동 재생을 사용 의도로 오해한다. 처음부터 별도 분석 플랫폼과 계정별 코호트를 만들면 구현·운영 범위가 커진다. 먼저 Clarity로 관찰하고, 반복 사용률이나 정밀 퍼널을 계산할 수 없을 때만 추가 도구를 검토한다.

| 알고 싶은 것 | 관찰 기준 | 해석하지 말아야 할 것 |
|---|---|---|
| 어디서 막히는가 | 시작 후 실패·재시도·뒤로가기, 단계별 대기, 리플레이의 실제 반응 | 미완료 세션을 전부 UX 실패로 단정 |
| 무엇을 많이 쓰는가 | 기능을 의도적으로 사용한 세션 수와 비율 | 탭 조회·반복 클릭·백그라운드 체류를 기능 사용으로 계산 |
| 무엇을 좋아하는가 | 자발적 재사용, 북마크·공유 같은 가치 신호, 사용자 피드백 | 사용량·체류 시간만으로 만족도 단정 |

북마크와 좋아요는 해당 **콘텐츠**에 대한 선호일 수 있다. 그것만으로 카메라·커뮤니티 기능 전체를 좋아한다고 결론 내리지 않는다. 좋아하는 기능은 행동에서 가설을 얻고, 사용자에게 유용했던 점을 직접 확인한다. 신규 설문 UI는 이번 범위에 포함하지 않는다.

## 2. 확인된 현재 상태와 SDK 경계

| 항목 | 현재 확인 | 후속 조치 |
|---|---|---|
| 초기화 | `lib/main.dart`에서 `ClarityWidget`으로 `App`을 감쌈 | 수집 허용 조건과 초기화 순서 설계 |
| 설정 | `lib/core/analytics/clarity_setup.dart`의 동일 프로젝트 ID 사용, 로그 수준만 빌드별 분리 | 내부 QA와 운영 프로젝트 분리 제안 |
| 앱 측 보호·측정 | 별도 마스킹, 화면명, 이벤트, 사용자 ID, 동의 연동 코드 없음 | 승인된 정책에 맞춰 후속 구현 |
| 대시보드 | 설정·실제 리플레이 미확인 | 소유자가 설정 확인 및 검증 증거 기록 |
| 기능 지원 | 사용자 정의 이벤트·화면명·태그·pause/resume·동의 API 제공 | 설치된 버전의 API 계약 사용 |
| 제약 | Flutter의 Smart Events·Funnels·Components 미지원 명시 | 자동 퍼널을 전제로 지표 제공을 약속하지 않음 |

SDK 지원 근거: [Microsoft 공식 패키지 1.10.0](https://pub.dev/packages/clarity_flutter/versions/1.10.0). SDK 호출의 성공 반환과 대시보드 도착은 별도로 검증한다.

모바일 대시보드의 Data Capture Rules는 공식 문서상 Flutter 미지원이다. 화면 제외나 네트워크 제한을 대시보드에서 설정하는 것만으로 해결됐다고 간주하지 않는다. [공식 수집 규칙 문서](https://learn.microsoft.com/en-us/clarity/mobile-sdk/sdk-data-capture-rules)

로컬 1.10.0 SDK의 `session_manager.dart`를 확인하면 `analyticsStorage=false`는 식별자 처리에도 관여한다. 따라서 **동의 API 호출 하나를 전체 수집·전송 중단으로 간주하지 않는다.** 미동의 시 초기화 방지, 철회 시 캡처 중지 및 대기 데이터 처리 범위를 별도로 검증한다.

## 3. 사용자 경험에서 출발한 관찰 시나리오

아래 감정은 검증할 가설이며 이벤트로 자동 판정하지 않는다. 기존 흐름을 관찰하는 설계이고 화면 변경 지시가 아니다.

### 카메라·사육장 연결

1. [화면] 연결할 기기 목록 → [조작] 기기 선택 → [반응] Wi-Fi 설정 단계 → [감정] 연결이 진행된다는 기대.
2. [화면] Wi-Fi 설정 → [조작] 네트워크 선택·연결 요청 → [반응] 진행 또는 오류 안내 → [감정] 기다릴 수 있는지, 다시 해야 하는지 판단.
3. [화면] 연결 결과 → [조작] 홈/카메라로 이동 → [반응] 기기 상태·라이브 확인 → [감정] 실제로 쓸 수 있다는 확신.

측정 경계: `WIFI_OK`는 Wi-Fi 설정 성공이다. 계정에 기기가 보이는 것, 온라인 상태, 라이브 재생 성공을 각각 별도 결과로 본다. 세션이 끊긴 경우 실패로 확정하지 않는다.

### 영상 탐색과 다시 보기

1. [화면] 클립·하이라이트 목록 → [조작] 보고 싶은 항목 선택 → [반응] 플레이어와 재생 → [감정] 관심과 기대 충족.
2. [화면] 재생 중인 영상 → [조작] 북마크 또는 공유 선택 → [반응] 저장 결과 또는 공유창 → [감정] 보관·전달할 가치가 있음.
3. [화면] 북마크 목록 → [조작] 저장한 영상 선택 → [반응] 다시 재생 → [감정] 저장 기능이 유용함.

측정 경계: 목록 자동 재생과 재생목록 자동 다음 재생은 사용자 선택 재생과 구분한다. 공유창을 열었다고 외부 전송이 완료된 것은 아니다.

### 사육장 제어

1. [화면] 현재 상태와 제어 버튼 → [조작] 원하는 동작 선택 → [반응] 앱 요청·결과 안내 → [감정] 요청이 받아들여졌는지 판단.
2. [화면] 상태 표시 → [조작] 기다림 또는 재시도 → [반응] 기기 상태 갱신 또는 실패 안내 → [감정] 확신 또는 불안.

측정 경계: 누름·서버 요청 접수·기기 ACK·실제 상태 변화는 다르다. Clarity를 기기의 실제 동작이나 안전성을 입증하는 로그로 사용하지 않는다.

## 4. 기능별 사용 정의

초기 비교 단위는 **계정 수가 아닌 수집된 세션 수**다. 이름은 고정된 기능 코드이며 개체·카메라·게시물 ID를 포함하지 않는다.

| 기능 코드 | 사용할 기회가 있었다는 조건(`exposed`) | 의도적 사용 조건(`used`) |
|---|---|---|
| `live` | 온라인 카메라의 라이브 영역 또는 진입 버튼이 보임 | 사용자가 라이브 확대/진입을 선택하고 첫 프레임 후 전경에서 10초 재생 |
| `clips` | 선택 가능한 클립이 화면에 표시됨 | 직접 고른 클립의 실제 재생이 전경에서 5초 또는 남은 재생 구간 끝에 먼저 도달 |
| `highlights` | 하이라이트 진입점과 사용 가능한 항목 존재 | 하이라이트 목록에서 직접 항목을 선택하고 클립 사용 조건 충족 |
| `bookmarks` | 북마크 목록 진입점 또는 저장 가능한 북마크 버튼 표시 | 북마크 추가 성공 또는 북마크 목록에서 선택한 클립이 사용 조건 충족 |
| `environment` | 온습도 요약 또는 상세 진입점 표시 | 온습도 상세를 직접 열고 데이터가 표시됨 |
| `control` | 지원되고 조작 가능한 제어 버튼 표시 | 사용자 조작으로 제어 요청 실행; 성공 여부는 별도 기록 |
| `routines` | 일정 설정 진입점 표시 | 일정 목록을 직접 열어 로딩이 끝남; 편집·저장은 별도 가치 신호 |
| `pets` | 마이크레의 개체 목록/추가 진입점 표시 | 개체 상세를 직접 열어 데이터 표시 또는 개체 저장 성공 |
| `reports` | 리포트 진입점 표시 | 리포트를 직접 열어 결과 표시 |
| `community` | 커뮤니티 탭 진입점 표시 | 직접 진입한 피드에서 스크롤·게시물 열기·좋아요·댓글·공유 중 하나 수행 |

10초·5초는 초기 운영 제안값이지 만족도를 입증하는 기준이 아니다. 홈의 자동 라이브 시청은 여기서 빠지므로 별도의 참고 지표 `live_passive_view`로 기록할 수 있다(첫 프레임 후 해당 영역이 보이는 전경에서 10초). 이를 의도적 사용 순위에 섞지 않는다.

`exposed`는 현재 화면에서 해당 진입점이 실제로 보일 때만 발생한다. 로딩·빈 데이터·미지원·오프라인을 가용 상태로 처리하지 않는다. 딥링크로 바로 사용하는 경우에도 동일한 가용 조건 확인 후 노출을 기록한다. 리포트처럼 빈 결과를 보여줄 수 있는 화면은 빈 상태 조회를 `used`에 포함하지 않는다.

## 5. 지표와 계산 규칙

집계 기간은 KST 월요일 00:00부터 다음 월요일 00:00 직전까지를 기본으로 한다. 같은 기간·앱 버전·측정 스키마·운영 환경을 비교하며, 날짜 경계에 걸친 세션은 세션 시작 시각으로 귀속한다. 대시보드가 이 경계를 제공하는지 확인하고 다르면 실제 기준을 명시한다.

`S` = 해당 기간 수집된 운영 세션 집합, `E_f` = 기능 f의 노출이 있는 세션 집합, `U_f` = 기능 f의 의도적 사용이 있는 세션 집합.

| 지표 | 정의 | 용도 |
|---|---|---|
| 사용 세션 수 | `count(U_f)` | 실제로 많이 사용된 기능 순위 |
| 전체 세션 사용률 | `count(U_f) / count(S)` | 앱 전체에서 기능의 도달 범위 |
| 노출 대비 사용률 | `count(U_f ∩ E_f) / count(E_f)` | 사용 기회가 있었는데 선택되지 않는 기능 탐색 |
| 문제 관찰 | 시작·실패·재시도 이벤트가 있는 세션과 리플레이 | 막힘의 유형과 개선 가설 |
| 선호 보조 신호 | 북마크 저장, 저장 영상 재생, 공유창 열기, 일정 저장, 커뮤니티 반응 | 사용자가 가치를 느낀 행동 탐색 |

`count`는 집합에 포함된 고유 세션 수다. 분모 0은 0%가 아니라 계산 불가다. 세션 하나에서 같은 기능을 20번 눌러도 사용 세션은 1개다. `used`가 있는데 `exposed`가 없는 사례는 계측 누락 여부를 먼저 조사한다. 세션 수는 실제 사람 수와 같지 않다. 기능끼리 중복 사용될 수 있어 사용률 합계는 100%를 넘을 수 있다.

선호 보조 신호는 행동별 세션 수와 관련 기능 사용 세션 중 해당 행동도 관찰된 비율을 나란히 적는다. 예를 들어 클립 사용 세션 중 공유창을 연 세션 비율을 보며, 서로 성격이 다른 기능을 하나의 “선호 점수”로 합산하지 않는다.

성공률은 **같은 시도에서 시작과 결과가 연결되는 경우에만** 계산한다. 초기에는 리플레이에서 순서를 확인한 표본으로 완료/오류/사용자 취소/관찰 중단을 분류하고 표본 수를 함께 적는다. 세션 단위의 시작 건수와 성공 건수를 단순히 나눠 시도 성공률이라 부르지 않는다. 강제 종료·오프라인·수집 철회로 결과가 없으면 관찰 중단이다.

첫 2주는 기준선 수집 기간으로 두고 목표 성공률·인기 점수를 임의로 설정하지 않는다. 노출 세션이 30개 미만인 기능은 순위보다 원시 건수와 사례를 보고한다(통계적 유의성을 보장하는 경계가 아닌 초기 운영 규칙). 재방문·7일 재사용률은 안정적 식별과 집계 기능을 검증하기 전에는 제공하지 않는다.

**집계 가능성 검증:** 대시보드에서 이벤트 필터별 고유 세션 수와 기간 기준을 확인한다. 교집합·중복 제거·전체 건수를 확인할 수 없는 지표는 “계산 불가”로 표기하고, 기록한 표본 범위의 관찰 결과만 보고한다. 이벤트 조회수나 제한된 리플레이 목록을 전체 세션 수로 바꾸어 쓰지 않는다. 별도 수집 서버·내보내기 API가 있다는 전제로 설계하지 않는다.

## 6. 이벤트·화면명 계약 제안

공통 이벤트는 `feature_<코드>_exposed`, `feature_<코드>_used`이며 §4의 고정 코드만 사용한다. 각 이벤트는 Clarity 세션마다 기능별 1회, 세션 변경 시 중복 방지 상태를 초기화한다. 세션 준비 이전에 발생한 행동은 버퍼로 소급 전송하지 않고 해당 세션의 관찰 범위 밖으로 둔다.

| 추가 이벤트 | 발생 시점 | 중복·해석 규칙 |
|---|---|---|
| `pair_<target>_started` | 카메라/사육장 페어링 화면에서 탐색 시도 시작 | target=`camera` 또는 `cage`, 시도당 1회 |
| `pair_<target>_device_selected` | BLE 기기를 직접 선택 | 시도당 단계 진입 1회, 기기 정보 제외 |
| `pair_<target>_wifi_submitted` | Wi-Fi 설정을 실제 전송 | 사용자 요청 1회당 1회 |
| `pair_<target>_wifi_succeeded` | `WIFI_OK` 확인 | 시도당 1회, 라이브 성공과 구분 |
| `pair_<target>_failed_<reason>` | 실패 상태 확정 | reason=`permission`, `ble`, `wifi`, `timeout`, `unknown`만 허용 |
| `pair_<target>_cancelled` | 사용자가 화면을 나가 미완료 시도를 명시적으로 중단 | 강제 종료·수집 중단에는 보내지 않음 |
| `live_open_requested` / `live_first_frame` / `live_failed` | 직접 진입 요청 / 첫 프레임 / 실패 안내 | 사용자 진입 시도당 각 상태 1회, 자동 재연결을 신규 요청으로 세지 않음 |
| `clip_play_requested` / `clip_play_started` / `clip_play_failed` | 직접 선택 / 실제 재생 시작 / 실패 | 자동 재생·자동 다음 제외, `started`는 `used`보다 이른 단계 |
| `bookmark_added` / `bookmark_removed` | 저장소 변경 성공 | 낙관적 UI 전환·저장 실패는 성공으로 세지 않음 |
| `bookmark_clip_played` | 저장 목록에서 직접 고른 영상이 클립 사용 조건 충족 | 다시 보기의 가치 신호 |
| `clip_share_opened` | 시스템 공유창 호출 성공 | 외부 전송 성공이라고 부르지 않음 |
| `control_<action>_requested` / `control_<action>_accepted` / `control_<action>_failed` | 명령 발행 / 서버 접수 / 해당 요청 오류 | action은 활성화된 제어의 사전 등록 코드만 사용, ACK·실제 동작과 구분 |
| `routine_saved` / `pet_saved` / `community_post_published` / `community_like_added` | 해당 저장 작업 성공 | 글·이름·ID를 이벤트에 넣지 않음 |

제어 action 허용 목록은 구현 전에 실제 활성 제어와 대조해 확정한다. 숨겨진 히터·미지원 냉각팬을 사용 가능 기능에 포함하지 않는다. 네트워크 오류 전문·HTTP URL·요청 본문을 reason 대신 넣지 않는다. 명시적 재시도는 새 시도로 보며 자동 재시도 콜백·위젯 rebuild가 이벤트를 중복 발생시키지 않게 한다.

현재 SDK의 `sendCustomEvent`는 이름 문자열을 받는다. 임의 속성 객체를 지원한다고 가정하지 않는다. 변경하는 값은 위에 허용한 고정 코드로만 조합한다. 세션 태그는 `environment`, `app_version`, `analytics_schema`로 시작하고, 세션 전체 필터에 사용한다. **세션 태그를 개별 이벤트의 속성으로 해석하지 않는다.**

화면명은 `home`, `camera`, `my_pets`, `my_pets_report`, `community`, `pair_camera`, `pair_cage`, `clip_player`, `highlights`, `bookmarks`, `environment_detail`, `routines`, `enclosure_settings`, `environment_settings`처럼 고정 사전을 쓴다. 전체 라우트·쿼리·개체 이름·ID는 보내지 않는다. 탭 전환, 뒤로가기, 중첩 라우트와 딥링크에서 실제 보이는 최상위 화면명으로 갱신한다. 화면별 허용 여부를 먼저 판단한다. [공식 화면명·이벤트 API](https://learn.microsoft.com/en-us/clarity/mobile-sdk/flutter-sdk)

## 7. 수집과 보호 정책 제안

### 시작·중단과 환경

- 운영 시작 기준은 사용자에게 질의 중이다. 추천안은 **분석 수집 동의 후 시작**이며, 대안은 내부 테스트에만 한정하고 운영 수집을 보류하는 것이다. 미응답은 승인으로 처리하지 않는다.
- 추천안에서 거부·철회는 앱 핵심 기능 이용을 막지 않는다. 동의 전 캡처/전송 방지, 재실행 시 선택 유지, 철회 후 새 캡처 중지, 대기 데이터 및 이미 전송된 데이터의 처리 차이를 구현 전에 명시한다. SDK의 pause가 기존 데이터 삭제를 보장한다고 쓰지 않는다.
- QA와 운영 프로젝트를 분리한다. debug/profile·디자인 랩은 운영 수집에서 제외하고 QA 수집은 명시적으로 켠 경우만 허용한다. 릴리즈 빌드라는 이유만으로 운영 사용자라고 간주하지 않는다.
- 계정 ID·이메일과의 연결은 초기 범위에서 제외한다. Clarity 자체 식별자는 존재할 수 있으므로 “완전 익명”이라고 표현하지 않는다. 로그인·로그아웃·계정 교체 시 세션 경계를 분리하고 이전 계정의 동의·태그를 다음 계정에 승계하지 않는다.
- SDK 실패·태그 전송 실패가 로그인·기기 제어·재생의 성공을 막지 않도록 한다. 배포용 전체 수집 비활성화 수단과 운영자의 중단 절차를 후속 구현에 포함한다. 원격 즉시 중단 가능 여부는 별도 검증 항목이다.

### 화면별 보호

| 화면·영역 | 제안 정책 | 관찰 가능한 정보 |
|---|---|---|
| 로그인·가입·이메일 인증·계정 관리 | 초기 분석 범위에서 수집 제외 | 해당 구간은 데이터 공백으로 표시 |
| 페어링 | 입력·SSID 목록·기기 식별 정보 명시적 마스킹 | 단계·고정 안내·성공/실패 이벤트 |
| 라이브·클립·하이라이트 | 영상·썸네일·카메라/세트 이름 보호 | 재생 조작·로드 결과·고정 버튼 |
| 개체·리포트 | 이름·사진·메모·날짜 등 사용자 데이터 보호 | 진입·고정 버튼·저장 결과 |
| 커뮤니티 | 사진·영상·프로필·본문·댓글·작성 입력 보호 | 피드 탐색·반응/게시 결과 |
| 사육장·일정·환경설정 | 기기명·LCD 문구·사용자 설정값 보호 | 조작·설정 흐름·저장 결과 |
| 알림·오류 안내 | 동적 내용·오류 전문 보호 | 고정 상태 코드와 안전한 안내 |
| `/design-test`, `/dev/*` | 운영 수집 제외 | QA 환경에서만 별도 확인 |

대시보드는 Strict를 기본 제안으로 두고, 읽어야 하는 **고정 UI 문구만** 검증 후 마스킹 해제한다. 화면 전체나 사용자 콘텐츠의 상위 컨테이너를 통째로 해제하지 않는다. 기본 입력 마스킹이나 네이티브 영상의 현재 녹화 제약만 믿지 않고 썸네일·비밀번호 표시 전환·오류 배너까지 검사한다.

마스킹은 이벤트·태그·화면명의 보호를 대신하지 않는다. 이메일, 토큰, SSID/비밀번호, 장치 주소, 실제 엔티티 ID, 자유 입력, 미디어 URL은 전송하지 않는다. 마스킹 설정 변경은 과거 기록에 소급 적용되지 않는다. [공식 마스킹 문서](https://learn.microsoft.com/en-us/clarity/mobile-sdk/clarity-sdk-masking)

## 8. 열람·보관·주간 운영

초기 소유자는 프로젝트 운영자(사용자)로 제안한다. 리플레이 접근은 운영자와 문제 수정에 필요한 담당자에게만 부여하고 공개 링크 공유·원본 다운로드는 기본 사용하지 않는다. 이슈 문서에는 개인 내용 없이 현상·재현 조건·개선안을 기록한다.

보관 기간은 임의의 앱 설정으로 단축할 수 있다고 약속하지 않는다. Microsoft의 현재 일반 안내는 재생 30일, 라벨/즐겨찾기 세션 및 집계 데이터에 더 긴 기간을 명시한다. **모바일 프로젝트에 실제 적용되는 기간·삭제 수단을 소유자가 확인한 뒤 고지에 반영**한다. 초안에서는 원본 장기 보관을 위한 라벨·즐겨찾기를 사용하지 않는 방향을 제안한다. [보관 정책 안내](https://learn.microsoft.com/en-us/clarity/setup-and-installation/data-retention)

문제 발견 시 운영자는 신규 수집을 중단하고 열람·공유를 제한한다. 노출 범위와 기존 기록 삭제 가능 경로를 확인하며, 앱에서 수집을 껐다고 서버 기록도 지워졌다고 보고하지 않는다. 고지 문안·스토어 데이터 공개·동의와 철회·삭제 안내는 운영 수집 전에 실제 동작과 맞춰 검토한다. 이 문서는 법적 적합성 판정이 아니다.

주간 검토는 다음 순서로 한다.

1. QA 혼입·버전·이벤트 누락·중복과 수집량부터 확인한다.
2. 기능별 사용 세션 수, 전체 사용률, 노출 대비 사용률을 함께 비교한다.
3. 실패/재시도 사례와 정상 성공 사례를 함께 본다. 의심 사례만 뽑은 표본으로 전체 실패율을 보고하지 않는다.
4. 가치 신호를 살펴보고 선호 가설을 적는다. 필요하면 별도 사용자 피드백으로 확인한다.
5. 개선할 문제를 선정하고 다음 주 또는 다음 버전의 같은 지표로 재확인한다.

보고 양식: `기간·버전·스키마 / 수집·표본 범위 / 기능별 사용표 / 막힘 사례 / 선호 가설과 근거 / 개선 결정 / 재확인 결과`. 전주 대비 변화에는 기기 보유·콘텐츠 공급·앱 버전·동의율 차이도 설명한다. 분석 대상은 수집 가능한 온라인 세션이며 전체 사용자 행동을 대표한다고 단정하지 않는다.

## 9. 적용 순서와 완료 기준

1. **정책 확정:** 수집 시작 기준, 마스킹 예외, 운영자·보관/삭제 기준을 확정한다.
2. **보호와 관측 가능성 검증:** QA 프로젝트에서 동의/중단·마스킹·화면명·대표 이벤트를 Android/iOS 각각 검증한다. 실제 집계 가능 범위를 확인한다.
3. **사용 지표 적용:** §4의 기능별 노출/사용과 §6의 필수 가치 신호를 연결한다. 지원하지 않는 기능이나 데이터 공백은 표시한다.
4. **막힘 분석 확장:** 페어링·라이브·클립·제어의 시작/결과를 순차 적용한다. 실제 데이터가 없는 단계에는 목표치를 붙이지 않는다.
5. **운영 시작:** 첫 2주 기준선을 검토하고 이후 필요한 계측만 추가한다.

| 검증 항목 | 합격 조건 | 현재 |
|---|---|---|
| 수집 허용 | 허용/거부/철회/재실행이 정책과 일치하고 전송 범위까지 확인 | 미구현·미검증 |
