## 1. 요청 1 — 히터·팬 on/off 명시 명령 ⚠️ 안전 문제

### PRD는 이렇습니다

§4.2.2 표에서 **히터·팬·LED는 "시작~종료" 구간**으로 예약합니다. (분무만 시점입니다.)

> | | 분무 | 히터 | 팬 | LED |
> |---|---|---|---|---|
> | **시간** | 회차별 시각 | **시작~종료** | **시작~종료** | **시작~종료** |

### 문서가 주는 것

`schedules`는 **시점 1개 + 명령 1개**입니다. 구간을 만들려면 예약을 2건으로 쪼개야 합니다.

```
20:00 heater_toggle   ← 켜기 의도
23:00 heater_toggle   ← 끄기 의도
```

### 왜 이게 위험한가

`heater_toggle`·`fan_toggle`은 **현재 상태를 뒤집는** 명령입니다. 절대 상태 명령이 아닙니다.

기기 상태가 예상과 한 번이라도 어긋나면 — 재부팅, 명령 유실, 사용자가 중간에 수동 조작, `error`(실DB 15건) — **23:00 예약이 끄는 게 아니라 켜버립니다.** 그리고 다음 예약까지 아무도 끄지 않습니다.

히터는 앱에서 유일하게 **2단 안전 확인**을 붙여둔 액추에이터입니다. 과열이 개체 폐사로 직결되기 때문입니다. 그 액추에이터를 상태 추측에 의존하는 방식으로 예약하게 둘 수 없습니다.

LED는 `led_on`/`led_off`가 이미 있어 이 문제가 없습니다. **히터·팬에도 같은 형태가 필요합니다.**

### 요청

```
action: heater_on | heater_off | fan_on | fan_off
```

- 멱등(idempotent)이어야 합니다 — 이미 켜져 있을 때 `heater_on`은 그대로 유지.
- `schedules`의 action 화이트리스트에도 추가.
- 기존 `heater_toggle`/`fan_toggle`은 수동 제어용으로 유지해도 무방합니다.

**대안이 있다면 그쪽도 좋습니다** — 예: `schedules`가 `end_time_of_day`를 받아 서버가 종료 명령까지 책임지는 방식. 요지는 *"구간의 종료를 앱의 상태 추측에 맡기지 않는 것"*입니다.

## 2. 요청 2 — 스마트 조건 (안전 가드) ⚠️ 안전 문제

### PRD는 이렇습니다

§4.2.2에 액추에이터별 조건이 명시돼 있고, PRD가 직접 이렇게 못박았습니다.

> **스마트 조건은 이 기능의 핵심이다.** 단순 예약이 아니라 *"조건이 어긋나면 알아서 멈춘다"*가 안전 장치다. 특히 히터는 과열이 개체 폐사로 이어진다.

| 액추에이터 | 조건 | 동작 |
|---|---|---|
| 분무 | 목표 습도 이상 (예: 80%↑) | 그 회차 **스킵** |
| 히터 | 목표 온도 도달 | **정지** |
| 팬 | 과건조 (예: 습도 50%↓) | **자동 정지** |

각 조건은 사용자가 on/off 할 수 있고, 히터는 정지 온도 슬라이더에 적정/위험 구간을 시각화합니다.

### 문서가 주는 것

`schedules` 스키마에 조건 필드가 **없습니다.**

```
id, device_id, owner_id, action, payload, kind,
time_of_day, days_of_week, enabled,
next_run_at, last_run_at, created_at, updated_at
```

### 왜 앱에서 못 하나

세 조건 모두 **명령 발행 시점 또는 실행 중**에 센서값을 봐야 합니다.

- 앱은 백그라운드에서 죽습니다. "22:00에 습도 확인하고 스킵"을 앱이 책임지면, 앱이 꺼져 있는 밤에는 동작하지 않습니다.
- 히터 "목표 온도 도달 시 정지"는 **가동 중 계속 감시**해야 합니다. 앱이 이걸 맡으면 화면을 켜둔 동안만 안전합니다.
- 실행 주체가 서버(브리지)인데 조건 판단만 앱이 하는 구조는 성립하지 않습니다.

**조건 판정은 서버 또는 펌웨어에 있어야 합니다.** 앱은 조건을 *설정*하고 *결과를 표시*할 뿐입니다.

### 요청

`schedules`에 조건을 담을 필드 (형태는 맡기겠습니다. 예시):

```json
{
  "action": "heater_on",
  "kind": "daily",
  "time_of_day": "20:00",
  "guard": {
    "type": "stop_when_temp_above",
    "value": 32.0,
    "enabled": true
  }
}
```

필요한 3종:
| type | 파라미터 | 동작 |
|---|---|---|
| `skip_when_humidity_above` | % | 발행 스킵 (분무) |
| `stop_when_temp_above` | ℃ | 가동 중 정지 (히터) |
| `stop_when_humidity_below` | % | 가동 중 정지 (팬) |

**가드가 작동했을 때 `commands`에 기록이 남아야 합니다** — PRD §4.3.8이 `16:20:05 팬 자동 정지 (목표 습도 50% 도달)` 같은 표시를 요구합니다. 요청 5와 함께 봐주세요.

## 3. 요청 3 — 일회성 타이머

### PRD는 이렇습니다

§4.2.1 — `schedules`(반복)와 **별개 기능**입니다.

- 대상: 팬 또는 히터
- 시간: 10분 / 30분 / 1시간 / 2시간
- `[타이머 시작]` → **즉시 기기 ON + 카운트다운 개시**
- 가동 즉시 홈 최상단에 진행 중 칩 (`팬 30분 타이머 가동 중 (18분 20초 남음)`, `[취소]` 포함)

### 앱 현재 상태

모델(`RunningTimer`)과 칩 위젯은 **이미 만들어져 있습니다.** 남은 시간 포맷·만료 처리·취소까지 구현·테스트 완료입니다.

조회처가 `device_timers` 테이블인데 이 테이블이 없어서, 쿼리가 실패하고 빈 목록으로 흡수됩니다. **결과적으로 칩이 영구히 안 뜹니다.** 실패를 조용히 삼키는 게 아니라, 백엔드가 생기면 바로 켜지도록 만들어 둔 상태입니다.

### 왜 앱에서 못 하나

`mist`와 같은 이유입니다. 앱이 "ON 보내고 30분 뒤 OFF 보내기"를 하면 **앱이 백그라운드로 가거나 종료되는 순간 히터가 계속 돕니다.** 이건 절대 하지 않는다고 코드 주석에 명시해 뒀습니다.

`mist`가 `duration_ms`로 이 문제를 푼 것과 정확히 같은 구조가 팬·히터에도 필요합니다.

### 요청 (택1)

**A안 — `duration_ms` 확장 (선호)**: `mist`와 같은 패턴. `fan_on`/`heater_on`이 `payload.duration_ms`를 받고 펌웨어가 자동 OFF.
- 장점: 새 테이블 불필요, `mist`와 계약이 통일됨
- 필요: 최대 2시간(7,200,000ms)까지 허용. `mist`의 5초 clamp와 다른 상한
- 조건: 앱이 남은 시간을 표시해야 하므로 **디바이스가 남은 시간을 telemetry로 올려주거나**, 앱이 발행 시각+duration으로 계산할 수 있어야 함

**B안 — `device_timers` 테이블**: 앱 코드가 이미 이 이름·스키마를 가정하고 있습니다.
```
id, device_id, actuator('fan'|'heater'|'led'|'relay'),
duration_minutes, ends_at, ...
```
- 장점: 취소·조회가 자연스럽고 여러 기기에서 동기화됨
- 단점: 새 테이블 + 만료 시 OFF 발행 로직

취소(`[취소]` 버튼)가 PRD 요구사항이라, **A안이면 "가동 중인 duration 명령을 중단하는 방법"이 함께 필요합니다.**

## 4. 요청 4 — LED 밝기 0~100%

### PRD는 이렇습니다

§4.1.4 퀵 제어 — `LED ON/OFF(밝기 0~100% 슬라이더)`
§4.2.2 일정 제어 옵션 — LED만 `밝기 0~100%`

### 앱 현재 상태

홈 퀵 제어에 밝기 슬라이더(0~100, 20단계)가 붙어 있고, `led_on` + `payload:{brightness: N}`으로 보냅니다. 0을 고르면 `led_off`.

### 확인된 사실 (실DB)

**`led_*` 명령 236건 전부 `payload = null`입니다.**

| action | payload | 건수 |
|---|---|---|
| `led_on` | null | 148 (+error 12, sent 10) |
| `led_off` | null | 40 |
| `led_toggle` | null | 18 |
| `led_up` | null | 18 (+`unknown_action` 3) |
| `led_down` | null | 6 |

즉 **밝기 payload가 실기기에 도달한 적이 한 번도 없습니다.** 앱의 밝기 UI는 개발 중인 브랜치에 있어 아직 실사용되지 않았습니다.

그리고 DB에 `led_up`/`led_down`이 있습니다 — **단계 조절 방식이 따로 있었던 것으로 보입니다.** 다만 `led_up` 3건이 `unknown_action`으로 거부됐습니다(2026-07-07).

### 질문

1. 펌웨어가 `led_on` + `payload.brightness`(0~100)를 **해석합니까?** 무시합니까?
2. 무시한다면 지원 계획이 있습니까? (PRD 요구사항입니다)
3. `led_up`/`led_down`은 **현재 유효한 명령입니까?** `unknown_action`으로 거부된 이력이 있어 폐기된 것으로 보입니다. 살아 있다면 0~100 대신 이 방식으로 갈지 검토하겠습니다.
4. `schedules`의 `payload`가 `mist`의 `duration_ms` 외 **다른 키도 통과시킵니까?** (문서 §2.1은 `mist`만 명시)

**지원 계획이 없다면 앱에서 슬라이더를 걷어내겠습니다.** 아무 효과 없는 컨트롤을 두는 게 더 나쁩니다.

## 5. 요청 5 — `commands` 실행 출처 구분

### PRD는 이렇습니다

§4.3.8 기기 작동 이력 (Audit Log)

- 필터: `전체 / 자동 일정 / 수동 제어 / 안전 가드 작동`
- 표시: 시각(HH:mm:ss), 기기, **실행 주체(일정·타이머·수동)**, **상세 이유**
- 예: `16:20:05 팬 자동 정지 (목표 습도 50% 도달)`

§4.2.3에도 *"작동 기록 — 실제로 작동했는지 안내하기 위한 확인, 안심용"*이 있습니다.

### 문서가 주는 것

예약이 실행되면 서버가 `commands`를 INSERT합니다. 앱은 기존 구독으로 감지합니다. 여기까지는 좋습니다.

문제는 **`commands`에 출처 컬럼이 없다**는 것입니다.

```
id, device_id, issued_by, action, payload, issued_at, ttl_sec, status, result, acked_at
```

`issued_by`(uuid) 하나뿐이라, 같은 `heater_on`이 **사용자가 누른 건지, 예약이 돈 건지, 안전 가드가 끈 건지** 구분할 수 없습니다.

### 요청

**A안 (선호)**: `commands`에 컬럼 추가
```sql
source     text   -- 'manual' | 'schedule' | 'timer' | 'guard'
source_id  uuid   -- schedules.id 등 (nullable)
reason     text   -- '목표 습도 50% 도달' (nullable, 가드 작동 시)
```

**B안**: 예약 발행 시 `issued_by`를 전용 서비스 계정 UUID로 고정하고 그 값을 알려주기. 다만 이러면 `guard`와 `schedule`을 구분할 수 없고 `reason`도 못 씁니다 — PRD 필터 4종 중 2종만 됩니다.

### 그리고 확인 질문 C

**현재 예약 발행 시 `issued_by`에 무엇이 들어갑니까?** (예약 소유자? 서버 계정?) A안으로 가더라도 이 값은 알아야 합니다.

## 6. 문서 ↔ 실DB 불일치 (앱이 고칩니다, 확인만 부탁)

### 6.1 질문 A — `result` 값 전체 목록

| §3 체크리스트 | `busy`/`rejected_unknown_action` |

**실DB 576건 전수 조회 결과 — `rejected_*`는 0건입니다.**

| 실제 `result` | 건수 | 기간 | 문서에 있나 |

| **`error`** | **15** | 06-23 ~ 07-14 | ❌ **문서에 없음** |
| **`locked`** | **4** | 06-08 | ❌ **문서에 없음** |
| `busy` | 0 | — | 문서에만 |
| `bad_request` | 0 | — | 문서에만 |

**§1.3 하단 주의가 맞고, 나머지 표기가 오타로 보입니다.** 확인 부탁드립니다.

추가로 **`error`(15건)와 `locked`(4건)는 문서 표에 없습니다.** `locked`는 히터 안전잠금으로 보이는데(`APP_INTEGRATION.md`의 `rejected_locked`에 대응?), 정확한 의미와 앱 표시 문구를 정해야 합니다. `error`는 의미가 불명확합니다.

> **앱 측 조치**: 앱 파서가 `rejected_locked`/`rejected_unknown_action`만 알고 있어 위 36건이 전부 "알 수 없음"으로 유실되고 있었습니다. 히터 잠금 안내 분기는 한 번도 실행된 적이 없습니다. 실값 기준으로 수정하겠습니다 — 문서 잘못이 아니라 앱 잘못입니다.

### 6.2 질문 B — `relay_toggle`의 향후 처리

앱은 지금까지 분무를 `relay_toggle`로 보냈습니다(**144건, 전부 `acked`/`ok`**). `relay_pulse` 계약이 없어서 택한 우회였고, 이번 `mist`가 정공법입니다.

전환 후:
- **과거 144건은 차트의 "분무 동작 마커"로 계속 그려야 합니다.** 앱이 `relay_toggle`·`mist` 둘 다 분무로 매핑하겠습니다.
- 질문: **`relay_toggle`은 앞으로도 유효합니까?** 폐기 예정이면 언제인지, 아니면 분무 외 다른 용도로 재정의되는지 알려주세요. 재정의되면 앱의 과거 이력 해석이 틀어집니다.

### 6.3 문서 예제 코드 오류 (참고)

§2.1의 KST 변환 예제가 Dart에서 잘못 동작합니다.

```dart
// 문서
final kst = DateTime.parse(s['next_run_at']).toUtc().add(const Duration(hours: 9));
```

결과가 `isUtc == true`인 채 +9시간이 되어, 이후 `toLocal()`을 한 번 더 부르면 **이중 변환**됩니다. Dart에서는 기기 타임존이 KST면 `.toLocal()` 한 번으로 끝납니다.

```dart
final kst = DateTime.parse(s['next_run_at']).toLocal();
```

앱은 후자로 구현합니다. 문서 수정만 부탁드립니다.

## 7. 확인된 사실 모음 (실DB, 2026-08-12 조회)

백엔드 쪽에서 재확인할 때 참고하시라고 남깁니다.

**`schedules` 테이블 — 실재 확인**
```
id uuid NOT NULL          device_id uuid NOT NULL     owner_id uuid NOT NULL
action text NOT NULL       payload jsonb              kind text NOT NULL
time_of_day time NOT NULL  days_of_week ARRAY         enabled bool NOT NULL
next_run_at timestamptz NOT NULL   last_run_at timestamptz
created_at timestamptz NOT NULL    updated_at timestamptz NOT NULL
```
RLS 정책 `own schedules all` (ALL). → 목록 조회·Realtime 구독은 Supabase 직결로도 가능. **쓰기는 문서대로 REST만 쓰겠습니다**(서버가 `next_run_at`을 계산하므로).

**`mist` 명령 — 이미 실동작 중**

| action | status | result | 건수 | 마지막 |
|---|---|---|---|---|
| `mist` | acked | ok | 7 | 2026-08-11 07:41 |

문서가 경고한 "펌웨어 미지원 시 거부"는 **이 기기(terra-iot-nano)에서는 해당되지 않습니다.** 웹 콘솔에서 발행된 것으로 보입니다.

**`commands` 스키마**
```
id, device_id, issued_by, action, payload, issued_at, ttl_sec, status, result, acked_at
```
→ 출처 컬럼 없음 (요청 5)
