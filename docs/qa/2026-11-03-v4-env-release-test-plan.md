# v4 온습도 — 스토어 배포 전 전체 테스트 계획

> 작성 2026-11-03 (앱 0.168.2). **원칙(사용자 지시 2026-11-03): 앱스토어 배포 전에 모든 기능이 테스트 완료되어야 한다.**
> 대상: v4 온습도 설정·보정·실시간 카드·푸시·일일/주간 분석·주간 그래프. 앱 전체 회귀는 범위 밖(필요하면 별도 문서).

## 0. 막혀 있는 것 — 순서가 거꾸로다

서버와 합의된 순서는 "앱 스토어 배포 → 앱이 '켜도 됨' 회신 → 서버가 2단계(푸시)·3단계(분석 카드) 켬"이다(서버 회신 §4·§6.1·§8). 이대로면 **푸시·분석 카드·습기 사이클은 배포 뒤에야 처음 실데이터로 동작**해서 배포 전 테스트가 불가능하다.

| 서버 스위치 | 지금 | 이게 꺼져 있으면 테스트 못 하는 것 |
|---|---|---|
| `ALERTS_V4_ENABLED`(1단계, 실시간 판정) | 꺼짐 — 켜 달라고 요청함 | 실시간 이탈 카드 4종 |
| `PUSH_ENV_ALERTS_ENABLED`(2단계) | 꺼짐 — 앱 배포 후 켜기로 합의 | 이탈 푸시 수신·탭 이동·수신 끄기 |
| `ENV_REPORTS_ENABLED`(3단계) | 꺼짐 — 앱 배포 후 켜기로 합의 | 일일·주간 분석 카드 |
| `HUMID_CYCLES_ENABLED`(Stage O) | 꺼짐 | 환기 지연·분무 필요 카드·푸시 |

**왜 배포 뒤로 미뤘나:** 2단계를 켜면 지금 테스터 폰에 깔린 옛 앱(끄기 화면 없음)에도 이탈 푸시가 나간다. 3단계·Stage O는 옛 앱이 읽지 않으므로(분석 테이블을 안 읽음, 모르는 kind는 버림) 켜도 테스터에게 보이는 변화가 없다 — **이 둘은 지금 켜도 된다**는 게 앱 쪽 판단이다(서버 확인 필요).

### 해결안 (추천 순)

| # | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A (추천)** | 서버에 **테스트 계정·기기 한정 켜기**(허용 목록) 요청 — 2단계 푸시는 허용 목록 사용자에게만 적재, 3단계·Stage O는 전체 켜도 무방하면 전체 | 실제 서버 경로 그대로 검증, 옛 앱 사용자 영향 없음 | 서버 작업 필요(허용 목록 분기) |
| B | 1단계·3단계·Stage O는 지금 전체 켜고, 2단계만 A | 서버 작업 최소 | 푸시는 여전히 A 필요 |
| C | 운영 DB에 **테스트 행 직접 넣기**(테스트 기기 한정: `alerts`, `notification_events`, `env_*_reports`) → 확인 후 삭제 | 서버 스위치 없이 앱 쪽 전부 확인, 시간 조건(6시간·15시간·주 단위) 없이 바로 | 서버 판정 로직 자체는 검증 못 함, 운영 DB 쓰기(사용자 승인 필요) |

실제로는 **A(또는 B) + C 병행**이 현실적이다 — 시간이 오래 걸리는 것(주간 분석은 켠 뒤 온전한 첫 주가 끝나야 생김, 환기 지연은 분무 후 6시간, 분무 필요는 건조 후 15시간)은 C로 화면을 먼저 확인하고, 서버 경로는 A로 실데이터가 생기는 대로 확인한다.

## 1. 테스트 환경

- **기기:** 사육장 테스트 기기 1대(신 펌웨어, `temp_offset_c` 보고) + 가능하면 구 펌웨어 1대(보정값 미보고) + 카메라 불필요.
- **폰:** 안드로이드 1대(푸시 필수 — **iOS는 앱 코드상 푸시를 받지 않는다**: `PushMessagingService.supported`가 Android만, §4 참고), iPhone 1대(화면·글자 크기).
- **계정:** 테스트 계정(위 기기 소유). 허용 목록(A)에 이 계정·기기를 올린다.
- **빌드:** 배포 후보 빌드(릴리스 모드). 디버그 빌드로 통과한 것은 완료로 치지 않는다.

## 2. 항목별 테스트

상태: ⬜ 미실시 / ✅ 통과 / ❌ 실패 / ⏸ 서버 대기. "근거"에는 캡처 파일·DB 조회 결과·시각을 적는다.

|---|---|---|---|---|

| A2 | 적정 온도 저장 | 18~26 → 20~27 저장 | DB `device_settings.target_temp_min/max` = 20/27, 화면·범위 바 반영 | ⬜ |

| A9 | 보정 — 구 펌웨어 | 보정값 미보고 기기에서 저장 | ack로 완료 판정(서버 회신 §2) | ⬜ (구 펌웨어 기기 있을 때) |

| A13 | 주간 그래프 | 지난주 | 최고·최저 날 강조색, 적정 범위 띠, 습도 축 ≤100%, 설정 로딩 중 튐 없음 | ⬜ |

## 3. 테스트 행 방식(C안) 절차 — 승인 받은 뒤에만

1. 대상: 테스트 계정·기기 하나. 넣는 행마다 `source_event_id`/`id`에 `qa-20261103-` 접두어.
2. `alerts`: v4 행 형식(`context.rule='v4'`, `level`, `message "[칩] 제목"`)으로 4종 + 사이클 2종 → 화면 확인 → `resolved_at` 채워 사라지는지 확인 → 삭제.
3. `notification_events`(type `env.alert.triggered`, payload `title`·`kind`·`device_id`·`device_name`) → 안드로이드 푸시·탭·목록 확인. 수신 끄기 조합 반복.
4. `env_daily_reports`·`env_weekly_reports`: 서버 문서의 카드 JSON 예시로 어제·지난주 행 → 화면 확인 → 삭제.
5. 끝나면 접두어로 전부 지웠는지 조회해 0건 확인, 결과를 이 문서에 기록.

## 4. 배포 전에 결정할 것

1. **푸시 테스트 방법:** A안(서버 허용 목록) 요청 / C안(테스트 행)만 / 둘 다.
2. **3단계·Stage O를 지금 전체 켜도 되는지** 서버에 확인(옛 앱 영향 없다는 앱 판단).
3. **iOS 푸시:** 앱이 iOS 푸시를 받지 않는다(`PushMessagingService.supported` = Android만). 앱스토어(iOS) 배포에서 v4 이탈 푸시가 없는 상태로 나갈지, 배포 전에 iOS 푸시(APNs 설정·권한·토큰 등록)를 붙일지.
4. **A6 보정 실기기 저장** 승인(테스트 기기 보정이 잠시 바뀜, 끝나면 되돌림).
5. 앱 전체 회귀(라이브·녹화·제어 등)도 같은 원칙으로 이번 배포 전에 할지.
