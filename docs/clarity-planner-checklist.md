# 기획자를 위한 Clarity 체크리스트

목적: **사용자가 막히는 곳을 찾고, 많이 쓰는 기능과 좋아할 가능성이 높은 기능을 발견한다.**

운영안: 매주 약 30분. 한 번에 한 흐름을 깊게 보고, 결과로 **개선할 문제 1개와 확인할 가설 1개**를 남긴다. 시간과 사례 수는 시작을 돕는 권장값이다.

이 문서는 [Clarity 운영 정책 초안](clarity-policy.md)을 쉽게 실행하기 위한 보조 문서다. 정책과 다르게 해석되면 정책 문서를 먼저 확인한다. **2026-09-12 현재 SDK 연결만 확인됐고 대시보드·마스킹·기능별 지표는 검증 전이다.** 아래 준비 항목을 실제로 확인한 뒤 체크한다. 운영 수집 시작 기준도 아직 미확정이다.

## 1. 처음 한 번: 분석할 준비가 되었는가

기획자는 아래 결과를 개발·운영 담당자에게 전달받는다. 설정이나 코드 수정 방법을 익힐 필요는 없다.

- [ ] 담당자가 운영 데이터 수집을 시작해도 되는 상태임을 확인했다.
- [ ] 내가 볼 프로젝트와 접근 권한을 받았고, 문의할 담당자를 안다.
- [ ] 내부 테스트와 실제 사용자 데이터를 구별하는 방법을 전달받았다.
- [ ] 담당자와 테스트 기록 하나를 함께 보며 화면과 조작이 읽히는지 확인했다.
- [ ] 이메일·Wi-Fi 정보·사용자 글·사진/영상이 보호되는지 확인한 결과를 받았다.
- [ ] 지금 볼 수 있는 지표와 아직 측정할 수 없는 지표를 구분했다.
- [ ] 날짜·앱 버전·기능을 선택하는 방법을 실제 대시보드에서 한 번 따라 해봤다.

**준비 확인 기록:** 확인일 / 기획자 / 개발·운영 담당자 / 사용 프로젝트 / 가능한 분석 범위.

마스킹이 확인되지 않은 운영 기록은 먼저 열어보지 말고 담당자에게 확인한다. 특정 지표가 없으면 0으로 적지 않는다. 해당 분석만 ‘측정 준비 필요’로 남기고 확인된 범위에서 진행한다.

## 2. 매주 시작: 오늘 확인할 질문 정하기 — 3분

- [ ] 분석 기간과 앱 버전을 적었다. 처음에는 지난 한 주를 기준으로 한다.
- [ ] 테스트 기록이 섞여 있지 않은지 확인했다.
- [ ] 오늘 볼 흐름 하나와 질문 하나를 정했다.
- [ ] 기록이 거의 없거나 중간에 수집이 끊겼다면 분석 범위에 표시했다.

| 볼 흐름 | 시작하기 좋은 질문 |
|---|---|
| 카메라·사육장 연결 | 기기를 찾는 단계와 Wi-Fi 연결 단계 중 어디서 멈추는가? |
| 라이브 보기 | 사용자가 영상을 보려고 한 뒤 실제 재생까지 도달하는가? |
| 클립·하이라이트 | 원하는 영상을 찾고 재생할 수 있는가? |
| 북마크 | 저장하고, 저장한 영상을 다시 찾아보는가? |
| 온습도·사육장 제어 | 상태를 확인하고 조작 결과를 이해하는가? |
| 일정·마이크레·리포트 | 기능에 진입한 뒤 조회나 저장을 끝내는가? |
| 커뮤니티 | 피드를 탐색한 뒤 게시물을 열거나 반응을 남기는가? |

## 3. 막히는 곳 찾기 — 10분

- [ ] 오늘 흐름의 리플레이를 봤다. 처음에는 의심 사례 3개와 정상 사례 3개를 권장한다. 부족하면 실제 본 수만 적는다.
- [ ] 사용자가 하려던 일과 실제 화면 반응을 따로 기록했다.
- [ ] 반복 누르기·긴 대기·뒤로가기·재시도가 있는 구간을 확인했다.
- [ ] 오류 안내가 있었는지, 안내 뒤 사용자가 다음 행동을 할 수 있었는지 봤다.
- [ ] 결과를 ‘완료 / 오류 / 직접 취소 / 관찰 중단’ 중 하나로 적었다.
- [ ] 같은 현상이 다른 기록에서도 보이는지 확인하고, 안 보이면 단일 사례로 남겼다.

리플레이는 **한 번의 앱 이용 기록**이며 한 사람과 같지 않다. 반복 누르기는 막힘의 후보이고, 기록 종료는 사용자 포기의 증거가 아니다. 의심 사례를 골라 본 비율을 전체 실패율로 발표하지 않는다.

기록 예시 — **가상의 사례:** “Wi-Fi 연결 요청 뒤 결과 안내가 보이지 않았고 사용자가 연결 버튼을 두 번 더 눌렀다.” 관찰은 여기까지다. “버튼을 이해하지 못했다”는 추가 확인이 필요한 해석이다.

## 4. 많이 쓰는 기능 찾기 — 5분

**기능별 측정이 준비된 후 사용한다.** 화면 조회만 가능한 단계에서는 ‘자주 방문한 화면’만 적고 ‘많이 사용한 기능’이라고 바꾸어 쓰지 않는다.

- [ ] 담당자가 확인한 집계 화면에서 기능을 사용한 이용 기록 수를 비교했다.
- [ ] 많이 쓰인 기능과 적게 쓰인 기능을 각각 적었다. 자료가 적으면 순위를 확정하지 않았다.
- [ ] 적게 쓰이는 이유가 진입점 미노출·기기 없음·영상 없음·오프라인 때문인지 확인했다.
- [ ] 같은 이용 기록의 반복 클릭이나 자동 재생을 여러 번의 의도적 사용으로 세지 않았다.
- [ ] 비교한 숫자에 기간·버전·대상 기록 수를 함께 적었다.

사용 기회를 가진 기록 수까지 확인된다면 ‘기능이 보였던 기록 중 실제 사용한 비율’을 함께 본다. 직접 계산할 근거가 없으면 ‘확인 불가’로 남긴다. 기능마다 이용 조건이 달라서 단순 건수 순위만으로 유지·삭제를 결정하지 않는다.

## 5. 좋아하는 기능의 단서 찾기 — 5분

- [ ] 북마크 저장·저장 영상 다시 보기·공유창 열기·일정 저장·커뮤니티 반응 중 확인 가능한 행동을 살폈다.
- [ ] 사용자가 스스로 선택한 행동인지, 자동으로 일어난 동작인지 구분했다.
- [ ] 기능이 편리했던 것인지, 특정 영상이나 게시물이 좋았던 것인지 구분해 가설을 적었다.
- [ ] 가설을 확인할 사용자 질문 하나를 남겼다. 예: “북마크한 영상을 어떤 때 다시 보셨나요?”

**많이 사용함과 좋아함은 다르다.** 오래 머무는 이유가 즐거움인지 로딩인지 리플레이로 확인한다. 공유창을 열었다고 전송을 완료한 것은 아니다. 여러 날 다시 사용하는지는 식별·집계가 확인되기 전에는 추측하지 않는다.

## 6. 회의에 가져갈 결론 남기기 — 7분

- [ ] 관찰 사실과 해석을 구분했다.
- [ ] 이번에 개선할 문제 하나를 골랐다. 반복 발생, 핵심 행동 방해, 영향 범위를 함께 고려했다.
- [ ] 무엇을 바꾸면 나아질지와 개선 후 확인할 결과를 적었다.
- [ ] 담당자와 재확인 날짜를 정했다.
- [ ] 자료가 부족한 가설은 확정 결론 대신 다음 관찰 질문으로 남겼다.

아래 양식을 주간 기획 기록에 복사한다. 빈칸은 실제 분석 후 채우며 예시 수치를 실측으로 쓰지 않는다.

```text
기간 / 앱 버전 / 작성자:
오늘의 질문:
분석 범위: 집계 대상 __건 / 직접 본 기록 __건 / 제외하거나 확인할 수 없었던 범위 __
관찰 사실: 사용자가 __하려고 했고, 화면에서는 __가 나타났다.
막힌 지점과 결과:
많이 사용한 기능과 근거: (미측정이면 ‘측정 준비 필요’)
선호 가설과 근거:
다른 가능한 설명:
이번 개선안:
담당자 / 재확인 날짜:
개선되었다고 판단할 관찰·지표:
근거 위치: 권한 있는 내부 기록의 참조와 리플레이 시간 구간
```

리플레이를 공개 링크·다운로드 파일로 회의 자료에 붙이지 않는다. 개인 내용 없이 문제와 시간 구간을 적고, 필요한 담당자만 권한 안에서 확인한다. 민감 정보가 노출되면 추가 공유를 멈추고 운영 담당자에게 알린다.

## 7. 개선 배포 후: 실제로 나아졌는가

- [ ] 변경 전후에 같은 행동 정의와 비교 가능한 기간을 사용했다.
- [ ] 앱 버전·대상 기록 수·기기/콘텐츠 이용 조건의 차이를 적었다.
- [ ] 기존 막힘이 줄었는지와 새로운 막힘이 생겼는지를 함께 확인했다.
- [ ] 결과를 ‘개선 확인 / 변화 없음 / 자료 부족’으로 남겼다.

**첫 운영 완료 기준:** 준비 확인 기록을 남기고, 확인 가능한 범위에서 주간 기록 한 장을 작성했으며, 개선 또는 추가 관찰의 담당자와 날짜가 정해졌다.
