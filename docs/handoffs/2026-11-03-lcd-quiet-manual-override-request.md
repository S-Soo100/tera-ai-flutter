# 요청 — LCD 꺼짐 예약 중 수동 전원 조작 (2026-11-03)

- 받는 분: 이관훈님 (terra-server · 펌웨어)
- 보내는 쪽: 앱팀
- 관련: `APP_GUIDE_LCD_SAVER_2026-11-03.md` §3-1·§6 (앱 사본 `docs/references/2026-11-03-lcd-saver-app-guide.md`), 앱 기획 `docs/superpowers/specs/2026-11-03-lcd-screen-settings-design.md`

## 1. 요약

가이드 감사합니다. 앱은 **지금 배포된 규칙 그대로** 먼저 붙입니다(급하지 않음). 다만 디자인이 기대하는 동작이 현재 규칙과 달라서, 바꿀 수 있는지 여쭙니다.

| | 지금 규칙 (가이드 §6) | 디자인이 기대하는 동작 |
|---|---|---|
| 꺼짐 예약 중 전원 켜기 | 효과 없음 — `화면 = 전원 ON AND NOT 예약 시간` | **켜진다** (그 예약 구간 동안만) |
| 꺼짐 예약 중 껐다가 예약 종료 | 계속 꺼짐 (끄기는 sticky, 켜기로만 풀림) | **종료 시각에 다시 켜진다** |
| 예약 없이 끄기 | 다시 켤 때까지 꺼짐 | 같음 |

디자이너 메모 원문 요약: "꺼짐 예약 실행 중에도 사용자가 전원을 켤 수 있으며 예약에 영향을 미치지 않음. 예) 21시에 전원을 켰다가 다시 껐다면 8시에 다시 켜짐."

## 2. 제안 규칙 — "수동 조작은 다음 예약 경계까지만"

꺼짐 예약이 설정돼 있을 때, 사용자의 켜기/끄기는 **다음 예약 경계(시작 또는 종료 시각)까지만** 우선하고, 경계를 지나면 예약 규칙으로 돌아갑니다. 예약이 없으면 지금처럼 sticky.

예약 20:00~08:00 기준:

| 시나리오 | 결과 |
|---|---|
| 21:00 켬 | 바로 켜짐 → 08:00 이후 계속 켜짐(원래 켜지는 시간) → 다음 날 20:00 꺼짐 |
| 21:00 켬 → 22:00 끔 | 22:00 꺼짐 → **08:00 켜짐** (디자이너 예시) |
| 23:00(원래 꺼진 상태) 다시 끔 | 변화 없음 → 08:00 켜짐 |
| 15:00(예약 밖) 끔 | 20:00 경계에서 예약 규칙(꺼짐) → 08:00 켜짐 — **앱팀이 디자이너와 확인 중**(낮에 끈 것을 다음 날 아침 자동으로 켜도 되는지). 결론 나면 바로 알려드리겠습니다 |

- 기기 시계가 아직 안 맞으면 지금처럼 켜 둠(안전 쪽) 유지.
- 재부팅해도 남은 수동 조작이 유지되면 좋겠습니다(NVS에 "무엇을, 다음 경계 몇 시까지").

## 3. 여쭙는 것

1. **가능 여부와 대략 일정** — 펌웨어 OTA가 필요한 일로 이해하고 있습니다. 어렵거나 다른 방식이 낫다면 그 의견도 부탁드립니다.
2. **API 형태** — 기존 `PUT /devices/{id}/lcd/power {on}`의 의미를 바꿀지, 필드를 추가할지(예: `{on, until_next_boundary: true}`). 앱은 어느 쪽이든 맞춥니다. 구 펌웨어와 섞이는 기간을 위해 `capabilities`에 별도 플래그(예: `lcd_override: true`)로 구분해 주시면 앱이 분기하겠습니다.
3. **실제 화면 상태 보고** — 앱 스위치가 "지금 화면이 켜져 있는지"를 그리려면 전원 설정값(`lcd_power`)만으로는 부족합니다. 기기가 실제 화면 상태(예: `lcd_screen_on`)와 수동 조작이 끝나는 시각(예: `lcd_override_until`)을 보고해 `devices`에 실어 주실 수 있을까요?

## 4. 그동안 앱의 동작 (현재 규칙 기준)

- 전원 스위치 = `lcd_power`. 끄면 "다시 켤 때까지 꺼져 있어요" 안내.
- 꺼짐 예약 시간 안이면 전원 줄 아래 "지금은 꺼짐 예약 시간이라 오전 8:00에 켜져요" 표시(폰 KST 시각 기준).
- 규칙이 바뀌면 위 2개 문구와 스위치 판정만 고칩니다.

## 5. 함께 확인 부탁 (짧게)

- 가이드 §8 "서버 재배포(`python-multipart`)" 예정 시점 — 앱 실기 확인을 그 뒤에 잡으려 합니다.
- `devices` Realtime UPDATE에 새 `lcd_*` 컬럼이 실려 오는지(가이드 §2-2) — 앱은 그렇다고 보고 구현합니다.
- **사진 명령 실패 시 `lcd_image_key`** — 기기는 받기 전에 이전 사진을 지운다고 하셨는데(가이드 §6), 실패(`dl_*`·`sha_mismatch`·`flash_write`·`no_ack`)하면 서버 key는 옛 값 그대로인지요? 그렇다면 앱은 옛 사진을 보여주는데 기기엔 사진이 없는 상태가 됩니다. 실패 시 key를 비우거나 기기가 실제 사진 유무를 보고해 주시면 좋겠습니다.
- **사진을 받는 중에 다른 LCD 명령**(`lcd_saver` 등)이 오면 어떻게 되는지 — 앱은 일단 사진 대기 중엔 보호기 설정을 막겠습니다.
- **LCD 없는 허브 빌드 구분** — `lcd_saver`가 없는 기기 중 '구 펌웨어'와 'LCD 자체가 없는 빌드'를 앱이 구분할 방법(`capabilities` 키 등)이 있을까요? 앱은 구 펌웨어에 "기기 업데이트 후 쓸 수 있어요"를 띄울 예정입니다.
- **시험 기기** — 앱 실기 확인용으로 `lcd_saver` 지원 기기를 앱 계정에서 쓸 수 있을지(운영 DB상 온라인 지원 기기는 `terra-d9feaaa2` 1대).
