# 이관훈님 추가 전달용 — 그룹 삭제 원자적 처리

상태: 앱 구현 및 격리 DB 검증 완료. **운영 서버·DB에는 적용하지 않았습니다.**

## 확정 동작

그룹 상세에서 ‘이 그룹 삭제’를 누르면 “이 그룹을 삭제할까요? 소속 기기와 개체는 삭제되지 않고 ‘그룹 없음’으로 이동합니다.”를 표시합니다. 취소는 쓰기0회입니다. 삭제 시 그룹만 제거하고 사육장·카메라·개체의 등록, 소유권, 이름, 개체 정보, 영상, 북마크, 로컬 메모를 보존합니다. 구성원 소속 해제와 그룹 삭제는 모두 성공하거나 모두 실패해야 합니다.

## 앱이 호출하는 계약

기존 재설계 그룹 저장소와 동일한 Supabase RPC 경로입니다.

- 함수: `redesign_delete_group_v1(p_group_id uuid, p_request_id uuid)`
- 인증: 현재 계정 JWT / `auth.uid()`로 소유자 결정. 클라이언트가 owner를 지정하지 않음.
- 응답: `{ "group_id": "요청한 그룹 UUID", "deleted": true }`
- 같은 계정·request_id·payload 재시도는 최초 성공 응답을 반환. 다른 payload나 다른 작업에 같은 키 사용은 거부.
- 다른 계정 그룹 또는 타 계정 구성원이 섞인 잘못된 그룹은 전체 거부.
- 실패 시 그룹·소속·활동 연결 이력·멱등 요청 기록이 모두 원래대로 유지.
- RPC가 없거나 미지원이면 앱은 오류를 표시하고 기존 그룹을 유지. 여러 구성원 제외 호출이나 직접 테이블 쓰기로 대체하지 않음.

이관훈님 기존 회신의 `DELETE /enclosures/{id}`는 FK `ON DELETE SET NULL`로 구성원을 보존합니다. 이번 앱의 공통 그룹 RPC·소유자 잠금·활동 이력 갱신과 동일한 계약으로 연결해야 합니다. 기존 REST를 계속 제공한다면 이 공통 트랜잭션을 호출하도록 통합해 주세요.

## 서버 반영 항목

1. 모든 그룹 관계 쓰기 경로가 동일한 소유자 잠금 및 활동 이력 helper를 사용하도록 통합.
2. 소유권 확인 → 구성원 행 잠금 → 모든 소속 해제 → `redesign_reconcile_assignments`로 현재 활동 연결 구간 종료 → 그룹 삭제 → 멱등 응답 저장을 한 트랜잭션으로 처리.
3. 실제 운영 FK/트리거 및 경쟁하는 writer를 점검. 그룹 삭제로 R2 파일이나 카메라/개체 레코드를 삭제하면 안 됨.
4. 기존 `motion_clips.enclosure_id`는 FK에 의해 NULL이 될 수 있지만 클립 레코드·camera_id·R2 key는 유지. 영상 조회는 계정/카메라 기준 유지.
5. 배포 후 RPC 이름·응답·오류 코드가 위와 일치함을 회신.

검토용 구현: [삭제 SQL](../../supabase/drafts/20260915_redesign_delete_group.sql). 자동 migration이 아닙니다. 기존 [공통 그룹 초안](../../supabase/drafts/20260915_redesign_groups.sql)과 [활동 이력 초안](../../supabase/drafts/20260915_assignment_history.sql)에 의존합니다. 기존 초안의 Unicode 이름 검증 등 운영 전제도 별도로 유지됩니다.

## 검증 근거

`python3 tools/verify_redesign_sql.py`를 외부 네트워크 없는 임시 PostgreSQL에서 실행했습니다. 타 계정 거부, 구성원 소속 해제 이후 삭제 직전 강제 오류의 전체 rollback, 성공 후 모든 구성원/영상/북마크/개체 이벤트/사진 유지, 활동 연결 이력 종료, 동일 요청 재시도, payload 충돌을 검증했습니다. 실행은 마지막에 ROLLBACK하며 운영 데이터는 사용하지 않았습니다.

담당: 앱 UI·저장소·오류 처리 및 초안 검증은 앱팀 완료. 공통 writer와 운영 API/DB 배포는 **이관훈님**. 이번 그룹 삭제만을 위해 petcam-lab에 R2 삭제 기능을 요청할 필요는 없습니다. 로컬 메모는 서버 작업 대상이 아닙니다.
