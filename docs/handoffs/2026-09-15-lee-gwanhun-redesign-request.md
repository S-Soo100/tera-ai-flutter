# 이관훈님 전달용 — 기기 등록·그룹·기록 보존·온습도 데이터 계약 확인

수신: 이관훈님 / terra-server

작성일: 2026-09-15

대상: 비바나트(vivanaut) 앱 디자인 개편

관훈님 안녕하세요. 앱 디자인 개편 기획이 확정되어, 기기 연결과 관리 화면에 필요한 서버 계약 확인을 요청드립니다.

**기존에 지원되는 항목은 사용 가능한 API·필드·권한을 알려주시고, 부족한 항목만 보완 방식과 예상 일정을 회신 부탁드립니다.** 앱 전용 Supabase 테이블·RLS·RPC와 Flutter 연동은 앱 팀이 맡겠습니다. terra-server와 웹도 사용하는 공통 데이터의 쓰기 경로·소유권 계약은 함께 맞추고자 합니다.

## 1. 기기 최초 등록·연결·등록 해제

### 1-1. 현재 지원하는 등록 계약

현재 보유한 BLE 문서는 앱에서 Wi-Fi를 전달하고 기기 token/owner는 사전 세팅하는 방식을 설명하고 있습니다. 일반 판매 기기의 최초 등록까지 지원하려면 아래 확인이 필요합니다.

1. 앱에서 사용할 수 있는 기기 등록·소유자 연결(claim)·등록 해제(unlink) endpoint와 요청/응답, 인증·권한
2. BLE에서 얻는 고유 식별자를 서버의 사육장·카메라 ID에 연결하는 방법
3. 사전 등록 베타 기기와 미등록 판매 기기의 지원 범위 및 성공 판정 조건
4. 재시도·중복 요청·이미 등록됨·다른 계정 소유·부분 실패의 응답과 복구 방법
5. Figma의 `viva-iot-…` 표기와 기존 `terra-iot` 광고 이름의 실제 지원 범위
6. 등록된 기기는 BLE 탐색에 다시 나타나지 않는다는 현재 동작의 적용 조건과 재등록 방법

앱에서 **`WIFI_OK`만으로 서버 소유자 연결까지 성공한 것으로 표시하지 않으려 합니다.** Wi-Fi 연결 완료와 계정 등록 완료를 구분할 수 있는 계약을 알려주세요.

사육장과 카메라를 함께 연결하다 하나만 성공한 경우 성공한 기기는 유지하고 실패한 기기만 재시도합니다. 이때 중복 기기·중복 그룹이 생기지 않도록 서버의 멱등 처리 기준도 필요합니다.

### 1-2. 삭제 버튼의 실제 동작과 기록 보존

기기 관리 화면의 삭제는 **기기 등록 해제와 그룹 연결 해제**입니다. 실제 R2 영상이나 과거 통계 원본을 삭제하는 기능이 아닙니다.

- 기존 계정은 해제 이전에 보이던 과거 영상·통계에 계속 접근할 수 있어야 합니다.
- 기기를 다른 계정에 재등록해도 이전 계정의 과거 영상이 새 소유자에게 노출되면 안 됩니다.
- 개체나 그룹 삭제도 기기·영상·통계 원본의 연쇄 삭제로 이어지면 안 됩니다.

현재 FK/cascade, clip 소유권, 조회 권한, 기기 인증 token과 재등록 처리에서 위 정책을 지원하는지 확인 부탁드립니다. 현재 owner를 바꾸면 모든 과거 데이터의 접근권도 따라 바뀌는 구조라면 보완 방법을 제안해주세요. 영상 조회 권한에 petcam-lab도 관여한다면 함께 계약을 맞추겠습니다.

## 2. 그룹·이름·연결 이력을 함께 바꾸는 공통 쓰기 경로

### 2-1. 확정된 그룹과 이름 규칙

| 항목 | 앱 기획 |
|---|---|
| 그룹 구성 | 사육장 최대 1대 + 카메라 최대 1대 + 도마뱀 최대 1마리. 한 종류만 있어도 그룹 생성 가능 |
| 그룹 이동 | 기존 그룹에서 구성원을 옮길 때 사용자 확인 후 이동 |
| 빈 그룹 | 마지막 구성원이 빠지면 빈 그룹 제거. 분리된 기기·개체 자체는 유지 |
| 자동 그룹화 | 같은 연결 흐름에서 함께 등록한 사육장·카메라는 자동 그룹화. 별도 추가 시 연결 후보가 여러 개면 사용자가 선택 |
| 기기 이름 | 같은 계정 내 중복 금지, 최대 10자. 사육장·카메라 전체를 대상으로 중복 확인 |
| 기본 기기 이름 | `사육장`, `사육장 2`, `사육장 3`… / `카메라`, `카메라 2`, `카메라 3`…. 사용 중인 이름은 건너뜀 |
| 그룹 이름 | 같은 계정 내 중복 금지, 최대 10자. 기본 이름 `마뱀이네 집`이 중복되면 번호 접미사로 구분 |
| 개체 이름 | 같은 계정 내 중복 금지, 최대 10자 |

LCD 표시 문구는 기기 이름과 별개이며 최대 20자·중복 허용입니다. 이름 유일성 제약에 포함하지 않습니다.

앱의 사전 중복 검사만으로는 동시 등록을 막을 수 없어, 이름 할당과 그룹 변경의 원자 처리가 필요합니다. 공백·표시 글자 수·중복 비교 방식도 앱과 서버에서 일치시키겠습니다.

### 2-2. MyCre 기록을 위한 개체–카메라 연결 이력

MyCre에서는 연결된 카메라의 활동 기록을 개체 기록으로 보여줍니다. 다음 정책을 지키기 위해 연결 변경과 이력 갱신을 한 번에 처리하려 합니다.

- 새 개체는 실제 연결 시작 이후의 활동만 보여줍니다.
- 같은 개체의 카메라가 변경되면 이전 연결 구간의 기록을 유지하고 새 구간을 이어 붙입니다.
- 신규 연결은 서버 시각의 `[시작, 종료)` 구간으로 기록해 경계의 이중 집계를 막습니다.
- 기존 사용자의 이미 보이던 과거 기록은 계속 보여줍니다. 개편 배포일 이후로 잘라내거나, 알 수 없는 과거 시작일을 임의 날짜로 만들지 않습니다.
- 개체 이동뿐 아니라 **카메라 자체의 그룹 이동·등록 해제**도 영향을 받는 연결 이력을 함께 갱신해야 합니다.

앱 팀은 `pet_camera_assignments`와 같은 연결 이력 구조 및 기존 조회 범위 승계를 설계할 예정입니다. 이는 제안 이름이며 이미 운영에 존재한다는 뜻은 아닙니다.

확인 부탁드리는 내용은 다음과 같습니다.

1. `devices` / `cameras` / `enclosures`와 개체 연결을 변경하는 앱·웹·서버의 모든 쓰기 경로
2. 기존 `assign_pet_to_enclosure` 등을 재사용하거나 공통 RPC/DB hook으로 관계 변경을 모을 수 있는지
3. 그룹 이동·자동 그룹화·연결 이력 종료/시작을 같은 transaction으로 처리하는 방식
4. 직접 UPDATE 등 우회 경로에서도 같은 제약과 이력을 보장할 방법
5. 오류 시 전체 원복, 동시 수정 충돌, 같은 요청 재시도의 계약

앱 팀이 SQL/RPC 초안을 작성하고, 공유 테이블과 terra-server·웹 호출 변경은 관훈님과 맞춰 적용하는 분장을 제안드립니다.

## 3. 정확한 과거 온습도 일평균을 위한 유효 표본 수

과거 날짜의 온도·습도 평균을 정확하게 계산하려 합니다. `telemetry_30m` 또는 동등한 API에 아래 정보가 있는지 확인 부탁드립니다.

- 온도와 습도 각각의 평균·최솟값·최댓값·**유효 표본 수**
- 각 지표의 평균과 유효 표본 수가 같은 결측·이상치 제외 규칙을 사용하는지
- 온도와 습도 중 한쪽만 유효한 표본을 각각 독립적으로 집계하는지
- 버킷 시작·종료 시각, UTC/KST 경계, 과거 데이터 지원 범위

예를 들어 평균 20·유효수 1인 구간과 평균 30·유효수 3인 구간의 일평균은 `(20×1 + 30×3) / 4 = 27.5`입니다. 평균값 두 개의 단순 평균인 25로 표시하면 안 됩니다.

기존 집계 API가 같은 의미의 정확한 일평균을 제공한다면 해당 API를 사용해도 됩니다. 과거 유효수를 복원할 수 없다면 null/미지원으로 남겨주세요. 전체 raw 개수를 지표별 유효수 대신 채우지 않습니다. 근거가 부족한 값은 앱에서 `--`로 처리하겠습니다.

**이번 요청에는 제어 시점의 정확한 온습도 snapshot이나 동작 전후 변화량을 새로 저장하는 기능은 포함하지 않습니다.** 제어 기록 화면은 기존 30분 평균 근사치를 사용하고 Figma 문구를 유지하기로 승인되었습니다. 이 정책과 과거 일평균의 유효수 요구는 별개입니다.

## 4. 카메라 수집 coverage 원천 확인 — petcam-lab과 협업

MyCre에서 ‘활동 0’과 ‘관측하지 못함’을 구분해야 합니다. 활동 구간과 분석 완료 계약은 petcam-lab에 요청했습니다.

terra-server가 카메라별 과거 가동·촬영·수집 성공/실패 원장을 갖고 있다면 제공 가능한 시각 범위·필드·조회 방법을 알려주세요. 현재 온라인 상태만으로 과거 날짜의 관측 완료를 판단하지 않으려 합니다. 필요한 원천 데이터는 petcam-lab과 합의하고, 최종 활동·coverage 조회 계약은 petcam-lab 요청과 연결하겠습니다.

## 5. 이번에 추가 개발을 요청하지 않는 항목

- 냉각팬 `fan2`: 전달받은 `APP_FAN2_2026-09-07.md` 계약대로 앱에서 연결합니다. 문서와 실기기 응답이 다른 경우에만 문의드리겠습니다.
- LED 밝기 20~100%·10% 단위, 분무 3초, LCD 20자와 기존 예약: 기존 명령·REST 계약을 사용합니다.
- 기기 관리의 전체 전원 버튼: 이번에는 ON 고정 표시이며 실제 전원 제어 기능을 요청하지 않습니다.
- 영상 메모: 로컬 저장입니다. 북마크 목록은 기존 `clip_favorites`를 사용합니다.
- 영상 삭제 버튼: 앱 팀이 사용자별 숨김을 구현합니다. R2 원본 삭제나 분석 통계 제외 기능은 요청하지 않습니다.
- 기존 FCM 예약·타이머 ACK 요청: 별도 전달 문서의 계약을 유지하며 이번 문서로 대체하지 않습니다.

## 6. 함께 확인할 검증 예시

| 예시 | 기대 결과 |
|---|---|
| Wi-Fi 성공 후 claim 실패 | 등록 완료로 표시되지 않고 재시도 가능 |
| 사육장·카메라 중 한 대만 등록 성공 | 성공 기기 유지, 실패 기기만 재시도, 중복 등록·그룹 없음 |
| 같은 계정에서 동시에 두 대 등록 | 이름이 중복되지 않고 그룹 유형별 최대 개수 유지 |
| 그룹 이동 중 오류·동일 요청 재시도 | 관계와 연결 이력이 함께 원복되거나 한 번만 완료 |
| 카메라 교체·기존 사용자 승계 | 이전 연결 기록과 기존에 보이던 과거 기록 유지 |
| 기기 해제 후 다른 계정에 등록 | 원본 유지, 기존 계정 과거 접근 유지, 새 계정의 이전 소유자 자료 접근 거부 |
| 평균 20/유효수 1 + 평균 30/유효수 3 | 일평균 27.5, 온도·습도 유효수 독립 적용 |
