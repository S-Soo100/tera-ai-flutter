# 카메라 라이브 안정화 — 펌웨어 개발자 협업 요청서

작성일: 2026-09-23

대상: ESP32-P4 카메라 펌웨어 개발자 / terra-server 담당자

상태: 전달용 요청서. 코드 조사와 사용자 제보에 기반하며, 이번 작업에서 실기기 재현·운영 로그 분석·펌웨어 수정은 하지 않았습니다. **2026-09-24 추가: 앱 실기기 시험에서 관측한 정지 4건과 클립 업로드 시각 대조를 [F1 실측 사례](#f1-실측-사례-2026-09-24-앱-측)에 붙였습니다 — 해당 시각의 카메라 로그 확인을 요청드립니다.**

## 1. 요청 요약

고객이 라이브캠을 처음 열 때 안정적으로 연결되고, 오래 시청해도 영상이 유지되도록 개선하려고 합니다. 단순히 오류 문구를 숨기거나 재접속을 반복하는 것으로 끝내지 않고, 실제 정지 횟수와 정지 시간을 줄이는 것이 목표입니다.

우선 요청드리는 작업은 다음 세 가지입니다.

1. 같은 Wi-Fi에서 장시간 시청하며 카메라의 영상 생성·전송, 메모리, 클립 업로드, 세션 상태를 함께 기록해 끊김 지점을 확인해 주세요.
2. 확인된 원인에 따라 라이브 송출 자원 보장, 세션 정리, 네트워크·인코더 복구를 수정해 주세요. 아래 가설을 모두 원인으로 간주해 일괄 수정하자는 요청은 아닙니다.
3. 현재 펌웨어의 ICE 후보 추가, 키프레임 요청, 가변 비트레이트, 동시 시청 지원 범위를 회신해 주세요. 앱은 지원이 확인된 기능만 사용하겠습니다.

앱 쪽도 병행 개선합니다. [펌웨어 수정 전 앱 개선 기획서](../superpowers/specs/2026-09-23-camera-live-pre-firmware-app-design.md)에서 중복 재접속 억제, 연결 상태 표시, 진단, 기존 펌웨어와의 호환 검증을 다룹니다.

## 2. 고객이 겪는 문제와 확인 범위

### 사용자 직접 제보

- 앱을 켜면 라이브가 연결되기 전에 먼저 끊겼다는 안내가 보여 불안합니다.
- 계속 시청하면 영상이 나왔다 끊겼다 반복하다가 복구되지 않는 경우가 많습니다.
- **카메라와 휴대폰이 같은 Wi-Fi에 있어도 발생합니다.**

### 아직 확인하지 못한 조건

- 제보 당시 앱 버전, OS·휴대폰 모델, 펌웨어 버전, 대상 카메라, 발생 시각.
- 첫 안내가 영상 영역의 연결 실패인지, 홈의 사육장 제어기 오프라인 배너인지.
- 실제 선택된 ICE 경로가 직접 연결인지 relay인지. 같은 SSID만으로 직접 연결을 단정하지 않습니다.
- 재생 시작부터 끊길 때까지 시간, 클립 녹화·업로드와의 상관관계, 단일/복수 시청 여부.
- 운영 TURN 배포 여부 및 실제 relay 연결 성공 여부.

현재 앱 소스 기준은 `f003cfb`, `0.132.2+328`입니다. 고객 설치 버전이 이 버전과 같다는 의미는 아닙니다. 서버는 제공된 `terra-server-main` 로컬 사본을 조사했으며 운영 배포본과 동일한지는 확인하지 않았습니다.

## 3. 현재 연결 구조

```text
앱 또는 웹
  ├─ 인증 후 terra-server에서 ICE 설정 수신
  ├─ offer → terra-server → MQTT → 카메라
  ├─ answer / ICE 후보 수신 및 교환
  └─ 카메라와 WebRTC 영상 수신 (선택된 경로에 따라 직접 또는 TURN 중계)
```

terra-server의 MQTT/ICE relay는 연결 정보를 전달하는 기능입니다. 이를 영상 자체를 중계하는 TURN 또는 미디어 서버와 구분해야 합니다.

### 앱에 이미 들어간 조치

- 연결 세대별로 비동기 작업을 분리해 이전 세션의 ICE 후보가 새 연결에 섞이지 않도록 처리.
- 백그라운드에서 연결 종료, 복귀 시 재연결.
- 네트워크 종류 변경 시 재연결.
- 카메라 오프라인 판정 시 자동 재시도 대기, 온라인 신호가 오면 재개.
- 첫 프레임 렌더링 콜백 또는 디코딩 통계로 영상 시작 확인.
- ICE 연결 후 첫 영상 대기 한도 30초.
- 재생 중 5초 주기로 디코딩 누적 프레임 확인, 3회 연속 증가가 없으면 재연결. 샘플 경계에 따라 실제 감지 지연은 달라지므로 정확히 15초의 관측값으로 취급하지 않습니다.
- 연결 `disconnected` 상태는 10초 유예 후 재연결 판단.
- 일반 실패는 3·6·12·24·48·60초 간격으로 재시도. 현재는 연결 성공 신호에서 간격을 초기화합니다.
- 앱이 더 이상 쓰지 않는 offer 응답의 세션에 close 요청.
- `webrtc_connect_logs`에 연결 결과, 단계별 시간, 경로 타입, 재요청 횟수, 재생 유지 시간을 기록하는 코드 추가.

이는 소스에 구현된 조치이며, 고객 환경 문제가 해결됐다는 뜻은 아닙니다.

### 웹과 앱의 중요한 차이

| 항목 | 앱 | 제공된 웹 |
|---|---|---|
| ICE 수집 | 최대 2초, srflx 후보 확보 시 조기 진행 | 완료 또는 최대 5초 대기 |
| 앱/웹 → 카메라 추가 후보 | offer 후에도 추가 전달 | offer에 수집한 후보 포함, 별도 송신 핸들러 없음 |
| 카메라 → 클라이언트 후보 폴링 | connected/failed/closed에서 중단 | connected 이후에도 유지, failed/closed에서 중단 |
| 영상 정지 감지·자동 복구 | 구현돼 있음 | 조사한 라이브 코드에는 앱과 동등한 감시·자동 복구가 확인되지 않음 |

웹이 더 안정적이라는 실측은 없습니다. 같은 폰·카메라·공유기에서 앱과 웹을 **번갈아** 비교하고, 차이가 재현되면 후보 수집·전달 및 복구 정책을 한 항목씩 비교하겠습니다. 동시에 열면 카메라 동시 세션 제한이 개입할 수 있습니다.

## 4. 기존 문서와 구분해야 하는 사실

| 항목 | 이번 요청의 기준 |

| 키프레임 대기 기준 | 같은 문서는 GOP 15 / 라이브 6fps에 따라 2.5초를 제시합니다. 이는 인코더 조건에 따른 기준으로, 네트워크·손실을 포함한 전체 연결 시간 보장이 아닙니다. |

| 앱 계측 | 9/22 요청서의 ‘디버그 로그만 존재’는 최신 앱 코드 상태와 다릅니다. 연결 결과 기록 코드가 추가됐으며 실제 적재·표본 충분성은 확인해야 합니다. |

9/22 [서버 요청서](2026-09-22-camera-live-stability-server-requests.md)는 당시 요청 이력입니다. 위 항목은 최신 조사와 구분해 읽어 주세요.

## 5. 펌웨어 조사·수정 요청

### F1. 영상 생성·전송과 자원 경합 — 최우선 조사

라이브 시청 중 아래 작업을 같은 시간축으로 기록해 주세요.

- 프레임 생성 수, 인코딩 완료 수, 전송 수·바이트, 송신 큐 길이 및 드롭 사유.
- 사용 가능 heap/PSRAM, 최대 연속 할당 가능 크기, 할당 실패, 재접속 전후 자원 회수.
- 클립 녹화·인코딩·업로드 시작/종료/동시 실행 수, 인코더 락 대기·처리 시간.
- Wi-Fi RSSI·재연결, 기기 uptime·재부팅 사유, WebRTC/ICE/DTLS 상태.

**원인이 경합이면:** 라이브에 필요한 메모리·처리 시간을 확보하고, 업로드 동시 실행 수·대역폭·큐를 제한하는 방향을 검토해 주세요. 녹화는 유지하는 방향을 우선하되, 불가피한 영향은 명시해 주세요. 무제한 큐나 업로드 연기로 저장 공간이 고갈되는 문제도 함께 검증해야 합니다.

**완료 증거:** 클립 업로드와 라이브를 동시에 수행한 전후 비교, 자원 추이, 영상 정지 시간, 녹화 누락·업로드 지연·AI 처리 지연 영향.

### F2. 세션 생명주기와 누적 자원

- 반복 접속·해제·앱 강제 종료 뒤 기존 peer, 인코더 참조, 큐, 소켓이 남는지 확인해 주세요.
- 허용하는 동시 시청자 수와 초과 시 동작을 알려 주세요. 새 offer가 기존 정상 시청자를 무조건 끊는 정책은 합의 없이 도입하지 않습니다.
- 같은 session_id의 offer 재발행, 지연 도착한 close, 이미 닫은 세션의 close에 대한 동작을 확인해 주세요. 이전 세션의 close가 새 세션을 종료해서는 안 됩니다.
- 앱이 close를 보낼 수 없는 상황의 자원 정리 기준을 알려 주세요. 서버 명령 `ttl_sec`와 영상 세션 수명을 구분해야 합니다.
- 서버는 offer 성공 시 `stream_until = 현재 + 5분`을 기록합니다. 이를 실제 영상 종료 조건으로 읽는 구성 요소가 있는지, 갱신이 필요한지 확인해 주세요. 현재 조사만으로 5분 뒤 끊김 원인이라고 판단하지 않습니다.

### F3. ICE 호환성과 네트워크 복구

- offer 이후 추가로 도착하는 host/srflx/relay 후보를 현재 펌웨어가 적용하는지, 후보 도착 순서의 제약을 알려 주세요.
- 앱 측 TURN relay 후보와 통신 가능한지 확인해 주세요. UDP뿐 아니라 제한된 망에서 사용할 TURN/TLS 경로도 인프라 담당자와 검증이 필요합니다.
- ICE restart 지원 여부, 필요한 SDP/세션 처리, 지원 버전을 알려 주세요. 확인 전에는 앱에서 사용하지 않습니다.
- 일시적인 Wi-Fi 단절 후 영상 송출이 스스로 복구되는지, 정상 연결에서도 주기적으로 끊기는 타이머가 있는지 확인해 주세요.

### F4. 첫 프레임과 디코더 복구

- 새 시청 세션 시작 시 필요한 SPS/PPS와 IDR이 적시에 전송되는지 확인해 주세요.
- RTCP PLI/FIR 등 키프레임 요청을 지원하고 인코더까지 전달하는지 알려 주세요. 손실 후 요청이 와도 무응답이거나 과도한 요청으로 인코더 부하가 늘지 않아야 합니다.
- 데이터는 수신되는데 디코딩이 멈추는 상황을 재현하면 전체 세션 재시작 없이 복구 가능한지 검증해 주세요.
- 과거 starvation 수정이 현장 펌웨어에 들어갔는지 버전/커밋 기준으로 알려 주세요.

### F5. 가변 전송량과 라이브 우선 정책

- 연결을 끊지 않고 비트레이트·fps를 바꿀 수 있는지, 해상도 변경은 재초기화가 필요한지 알려 주세요.
- 혼잡 피드백을 현재 송출 제어에 반영하는지, 제어 주체가 펌웨어 자체인지 앱 명령인지 정해 주세요.
- 제안 정책: 보수적인 송출량으로 시작 → 안정되면 천천히 증가 → 손실·지연 증가 시 빠르게 감소. 정확한 수치는 카메라 실측으로 정합니다.
- 라이브와 클립 업로드의 합산 대역폭을 관리하고, 녹화·AI 분석 품질에 미치는 영향을 분리해 주세요.
- 제어 API/신호와 지원 버전이 합의되기 전에는 앱에 화질 선택 UI나 미지원 명령을 넣지 않습니다.

## 7. 공동 재현과 검증 절차

### 기록할 환경

앱/웹 버전, OS·폰 모델, 펌웨어 빌드, 카메라 모델, AP·망 구성, RSSI, 선택 경로, 녹화/업로드 상태, 동시 시청 수를 기록합니다. 앱은 수신·디코딩·연결 전환, 펌웨어는 생성·송출·자원, 서버는 offer/answer·MQTT를 기록합니다. UTC 시각과 각 장치의 단조 증가 경과 시간을 함께 남겨 시계 오차를 고려합니다.

가능하면 서버 session_id로 대응시키고, offer 응답 전 실패는 카메라 ID·발생 시각·서버 msg_id로 대조합니다. SDP 원문, IP 후보 원문, JWT, TURN 자격 증명, Wi-Fi 비밀번호, 영상 내용은 진단 공유 자료에서 제외합니다.

### 실행 순서

1. 같은 Wi-Fi·시청자 1명에서 앱 60분, 웹 60분을 번갈아 실행합니다. 반복 순서를 바꿔 시간대 편향을 줄입니다.
2. 동일 조건에서 클립 업로드가 발생하는 구간을 포함합니다. 실험용 기기에서는 업로드 유무를 통제하되 고객 녹화를 임의 중단하지 않습니다.
3. 첫 연결/정상 종료 30회, 백그라운드 복귀 10회, 앱 강제 종료 후 재진입을 시험합니다.
4. 5초의 통제된 네트워크 단절 및 복구, Wi-Fi↔셀룰러 전환, 외부 Wi-Fi·LTE/5G를 시험합니다.
5. TURN 강제 경로 시험은 진단용 클라이언트에서 수행하고 실제 relay 후보 선택을 확인합니다. 운영 전체를 강제 relay로 바꾸지 않습니다.
6. 단일 시청 안정성 확인 후 지원 범위 내 동시 시청과 4시간 연속 시청을 별도 시험합니다.

### 관측 결과별 다음 조치

| 관측 | 우선 조사 |
|---|---|
| 카메라 프레임 생성/인코딩이 멈춤 | 인코더·메모리·락·작업 경합 |
| 카메라는 전송, 앱은 수신 바이트 증가 없음 | 손실·Wi-Fi·경로·ICE/DTLS·중계 |
| 앱 수신 바이트는 증가, 디코딩 프레임은 증가 없음 | 키프레임·손상 패킷·코덱/디코더 |
| 앱이 먼저 세션 종료 | 수명주기·네트워크 신호·재접속 처리 |
| 통계가 없음 | 진단 불가로 표기. 0 또는 정상으로 대체하지 않음 |

### 성공 기준

기본 시험에서 설명되지 않는 영상 정지·수동 복구·카메라 재부팅이 없어야 합니다. 전후의 첫 프레임 시간, 시청 시간당 정지 횟수, 총 정지 시간, 복구 시간, 재접속 횟수, 녹화 누락을 비교합니다. 자동 재접속 성공만으로 장시간 안정성을 통과시키지 않습니다.

30회 연결·60분 시험은 재현과 회귀 검증 표본이며 서비스 전체의 99% 성공률을 입증하지 않습니다. OS·망·펌웨어별 운영 표본을 따로 모읍니다.
