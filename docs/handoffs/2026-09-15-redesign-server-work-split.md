# 디자인 재설계 — 서버 작업 담당과 직접 수행 가능 여부

> 상태: **업무 분장·요청 내용 문서화 완료 / 외부 발송·신규 서버 변경 없음**.
> 2026-09-15 사용자가 확정 기획·구현계획 저장과 함께 담당 구분을 요청했다.
> [확정 기획](../superpowers/specs/2026-09-15-figma-redesign-approved-design.md) · [구현계획](../superpowers/plans/2026-09-15-figma-redesign-implementation.md)

## 1. 결론

**Supabase라고 전부 외부 요청 대상은 아니다.** 앱 전용 테이블·RLS·RPC·카탈로그·Flutter 연동은 우리가 작성·검증·배포를 담당할 수 있다. 반면 같은 프로젝트에 있어도 terra-server 또는 petcam-lab이 생산·소비하는 원본 데이터와 공통 계약은 해당 담당자와 맞춰야 한다.

| 구분 | 담당 |
|---|---|
| 우리 | Flutter, 로컬 Hive/보안 저장소, 앱 전용 Supabase 데이터·RLS·RPC·migration, 카탈로그 |
| petcam-lab 요청 | 영상 분석 결과·유효 활동 구간·하이라이트 후보/검수/공개 배치 계약 |
| 이관훈님 요청 | terra-server 기기 등록·소유권·텔레메트리·MQTT 명령·일정·펌웨어 계약 |

**직접 수행 가능 여부 확인 근거:** 로컬 Supabase CLI와 연결된 project ref가 존재하며, 이번 세션의 읽기 전용 `supabase projects list --output json`에서 대상 프로젝트 `slxjvzzfisxqwnghvrit` 접근을 확인했다. 앱 팀의 FCM migration·Edge Function 운영 배포 이력도 있다. 이 확인은 임의 DDL 실행권·모든 서버의 배포권을 검증한 것이 아니며, 이번 요청은 문서 저장까지다. 실제 적용 전 대상 schema·migration 이력·역할 권한·rollback을 다시 확인한다.

## 2. 항목별 분장표

‘바로 가능’은 **우리 코드·migration 작성과 검증에 바로 착수 가능**하다는 의미다. 운영 데이터 변경 완료를 뜻하지 않는다.

| ID | 작업 | 담당·직접 가능 여부 | 외부 의존·적용 조건 |
|---|---|---|---|
| A1 | SVG/PNG, 화면, 흰 상단, 입력 규칙, 메모·색상·Wi-Fi 보안 저장 | **우리, 바로 가능** | 서버 변경 없음 |
| A2 | 크레스티드 등록용 종·모프 카탈로그 통일 | **우리, 바로 가능** | 기존 DB·로컬 항목과 출처 대조. 다른 종 데이터 삭제 없음. 관리자 쓰기는 migration/관리 경로 사용 |
| A3 | 사용자별 영상 숨김 테이블·RLS·앱 목록 필터 | **우리, 바로 가능** | 앱 전용 추가 테이블로 분리. 공유 영상 RLS/분석 제외 정책을 수정하지 않음. API에서 숨김을 필터해야 할 때만 해당 API 소유자와 후속 협의 |
| A4 | 개체–카메라 연결 이력 테이블·기존 데이터 승계·MyCre 조회 | **우리 주도, schema·앱 구현 착수 가능** | 모든 연결 변경 경로를 포괄하려면 **T1 이관훈님 협의 후 통합 적용**. 현재 연결에서 과거 실제 시작일을 추정하지 않음 |

| T1 | 그룹 이동/교체·자동 그룹화의 원자 처리, 기기 이름 중복·자동 번호, 모든 쓰기 경로의 연결 이력 갱신 | **우리 SQL/RPC 설계 + 이관훈님 협의** | devices/cameras/enclosures를 웹·terra-server도 사용. 우리가 Supabase에 접근된다고 공통 write 계약을 단독 변경하지 않음 |
| T2 | 기기 삭제를 등록 해제로 전환, 영상·통계 원본 보존, 재등록 시 소유권 처리 | **이관훈님 주담당 요청, 우리 앱 연동** | DELETE/cascade/인증 token/재등록 정책 확인. petcam-lab도 영상 접근을 제공한다면 과거 clip owner 보존 계약을 공유 |
| T3 | 정확한 과거 온습도 일평균을 위한 지표별 유효 표본 수 | **이관훈님 확인·필요시 요청** | 기존 `telemetry_30m` 생산 로직·유효 count 지원 확인. 지원하면 앱만 연결, 없으면 보완 전 해당 평균 `--`. 제어 기록 근사치 승인과 별개 |

| P1 | MyCre의 유효 활동 구간·중복 제거·관측 완료 데이터 | **petcam-lab에 1차 요청** | `v_clip_effective_activity`가 petcam-lab migration에 존재. 현재 앱의 스칼라 초만으로 실제 구간·coverage를 확인할 수 없음. 충분한 기존 데이터 제공 여부부터 확인 |
| P2 | 불변 하이라이트 공개 배치 ID·공개 시각·검수 완료 목록 | **petcam-lab 요청** | 기존 FCM 하이라이트 요청과 통합. 별도 경쟁 batch 체계를 만들지 않음. 이관훈님께 검수 기능을 요청하지 않음 |
| N1 | 냉각팬 fan2 제어·타이머·예약·상태·기록 | **우리, 기존 계약에 앱 연결** | 전달 문서상 서버/펌웨어/DB 배포 완료. 신규 서버 개발 요청 불필요. 실기기 계약 불일치만 이관훈님 문의 |

| N3 | 제어 기록의 시점 온습도·변화량 | **우리, 서버 보완 요청 안 함** | 승인된 30분 평균 근사치·명령 시각 사용, 근거 없음 `--`, Figma 문구 유지 |

## 3. 우리가 직접 준비할 Supabase 변경

아래 이름은 **신규 설계 이름**이며 현재 운영에 존재한다고 주장하지 않는다. 실제 컬럼형과 기존 함수 정의는 migration 작성 전 introspection으로 맞춘다.

### A3. `user_clip_hidden`

- `(user_id, clip_id)` 고유 키, `hidden_at` 서버 시각.
- 인증된 사용자는 자신의 행만 읽고 추가/해제 가능. clip이 본인에게 접근 가능한 원본인지 서버에서 검증한다. 클라이언트가 임의 owner를 지정할 수 없게 한다.
- Camera·하이라이트·북마크·재생 큐의 사용자 표시 계층에만 적용한다. pagination은 숨김 제거 후 페이지가 비어도 다음 원본 cursor를 이어갈 수 있어야 한다.
- 원본 `motion_clips`, 기존 `clip_favorites`, 메모, 분석 데이터, R2 객체는 이 작업의 삭제 대상이 아니다.
- petcam-lab의 시스템 검수/격리 제외와 별개. **`fn_motion_clip_visible_to_owner` 또는 공유 `motion_clips` SELECT RLS에 사용자 숨김을 끼워 넣지 않는다.** 활동 view도 같은 RLS 영향을 받을 수 있어 ‘통계 유지’ 결정을 깨뜨리기 때문이다.

### A4. `pet_camera_assignments` + 승계 정책

- 식별자: account/pet/camera, 연결 시작·종료 시각, 실제 연결 이력인지 기존 데이터 승계인지 구분하는 origin.
- 새 연결은 서버 시각의 반열린 구간 `[start, end)`으로 기록한다. 활성 연결과 과거 이력을 분리해 조회하며 이동 경계의 이중 집계를 막는다.
- 기존 사용자는 migration 전 기존 조회 범위를 snapshot해 승계한다. 알 수 없는 시작일은 임의 날짜로 채우지 않고 별도 legacy 상태로 보존한다.
- 승계에 ‘가짜 오래된 날짜 한 개’를 넣어 신규 개체까지 과거 전체를 물려주지 않는다.
- 같은 개체의 이동은 기존 구간 종료+새 구간 생성을 하나의 작업으로 처리한다. 카메라만 그룹 이동해도 영향을 받는 개체 이력을 갱신한다.
- 앱 계정 이탈·오류 재시도·동시 기기 요청·웹 변경에 같은 불변 조건을 적용한다. 직접 UPDATE를 우회해 이력 없이 연결이 바뀌지 않게 T1과 합의한다.
- 개체 삭제가 카메라/클립 삭제로 cascade되지 않게 한다. 기기 등록 해제 후에도 기존 계정의 원본 접근권을 보존하는 T2 계약과 연결한다.

### A2/A5. 카탈로그·중복·그룹

- 모프는 DB 17/로컬 23 항목의 차이를 이름만으로 합치지 않는다. gene/morph/line-bred trait의 서로 다른 항목을 식별해 등록용 선택 ID와 이름을 정한다. 기존 pets.morph 문자열을 보존하는 변환 규칙을 함께 만든다.
- 개체/그룹/기기 이름은 공백 처리·표시 글자 수 검증과 동일 계정 중복 검사를 일치시킨다. SVG/LCD 표시 문구는 이 유일성 제약에 포함하지 않는다.
- `사육장`, `사육장 2`… 자동 이름 할당은 동시 등록에도 중복되지 않게 서버에서 처리한다.
- 그룹의 유형별 최대 1개, 이동 확인, 마지막 구성원 제외 시 빈 그룹 제거를 하나의 일관된 서버 작업으로 적용한다. 먼저 현재 `assign_pet_to_enclosure` RPC·unique index·FK·RLS를 읽어 재사용 범위를 결정한다.

## 4. 이관훈님 요청 묶음 — 아직 발송하지 않음

### T1/T2/T4: 등록·그룹·이름·기록 보존 계약

요청 목적: 사용자 승인된 기기 연결/관리 UI를 구현하기 위한 공통 write 경로를 확정한다.

회신 요청:

1. 현재 앱에 사용할 수 있는 기기 등록/claim/unlink endpoint와 권한·BLE 고유 ID 매핑. 사전 등록 베타 방식의 적용 범위.
2. devices/cameras/enclosures 변경의 웹·서버·앱 경로, 앱 팀이 작성한 그룹 RPC 또는 DB hook을 공통 경로로 쓸 수 있는지.
3. 동일 계정 기기 이름의 중복 금지·기본 번호 할당을 모든 경로에서 지킬 방법.
4. 기기 ‘삭제’를 등록 해제로 처리하면서 기존 clip owner·영상 접근·과거 통계를 보존하는 방법. 재등록 시 다른 사용자에게 과거 자료가 노출되지 않는지.
5. 자동 그룹화와 개체–카메라 이력 변경을 한 transaction으로 완료할 수 있는지. 실패 시 원복·멱등 재시도 계약.
6. Figma의 `viva-iot`와 실제 광고 이름 `terra-iot` 지원 범위, 기존 기기가 BLE에서 보이지 않는 동작 확인.

수락 기준: 동일 계정 동시 등록에서도 이름/그룹 중복 없음, 이동 중 오류에 반쪽 관계 없음, 최초 claim 실패를 등록 성공으로 표시하지 않음, 기기 해제 후 원본 유지·타 계정 접근 거부.

### T3: 일평균 데이터 확인

- `telemetry_30m`의 온도·습도 avg/min/max/valid_count가 각각 동일 유효 필터를 쓰는지 확인.
- 과거 count 복원이 불가능하면 null로 남긴다. raw 전체 개수로 대신 채우지 않는다.
- 예시: 평균 20/유효수 1, 평균 30/유효수 3 → 일평균 27.5. 온도와 습도 count가 다르면 독립 계산.
- 이번에는 **제어 시점 snapshot·정확한 동작 전후 변화량 기록을 새로 요청하지 않는다**. 해당 UI는 근사치 사용을 이미 승인받았다.

## 5. petcam-lab 요청 묶음 — 아직 발송하지 않음

### P1: 활동 집계 입력 계약

1. 기존 분석 산출물에서 camera별 활동 interval 또는 정확한 시간 버킷을 제공할 수 있는지. 스칼라 `effective_activity_sec`만 있는지 구분.
2. 겹침 제거·시간 경계 분할이 어느 계층에서 보장되는지와 policy/version.
3. 관측 완료한 0, 미수집, 미분석/진행 중을 구분할 필드·coverage 원장. 원천이 terra-server에 있으면 이관훈님과 필요한 범위를 합의.
4. UTC 시각 범위 조회·KST 자정/월요일 경계, camera별 cursor/pagination, 사용자 권한.
5. 구간 단위 개체–카메라 연결과 기존 기록 승계에 맞춰 과거 데이터를 계속 읽을 수 있는지.

수락 fixture:

- `23:59:50~00:00:10` 활동은 두 날짜에 10초씩.
- 겹치는 두 20초 구간을 단순 40초로 더하지 않음.
- 한 시간 최대 60분, 시간별 합=일간 합=주간 구성 일 합.
- 관측 완료일 10분·관측 완료일 0분·미수집일 → 일평균 5분, 분모 2.
- 사용자 영상 숨김은 해당 활동 산출물의 값을 바꾸지 않음.

이 요청은 확인 후 필요한 추가 개발 범위를 정하는 것이다. 현재 분석 뷰에 해당 능력이 이미 있는지 아직 운영 응답으로 검증하지 않았다. 기존 legacy 활동 표시는 보존하고, 새 정확도 계약을 충족하지 않은 값을 새 MyCre의 정확한 관측 통계로 조용히 표시하지 않는다.

### P2: 하이라이트 공개 배치

기존 [하이라이트 FCM 전달안](2026-09-15-petcam-lab-highlight-slack-script.md)에 이어 동일 배치 ID·검수 완료 snapshot·공개 시각을 앱 조회 응답에도 연결한다. 도착/읽음 UI와 푸시가 다른 배치 체계를 사용하지 않게 한다. 메타 미지원 동안 촬영시각을 공개 시각으로 대체하지 않는다.

FCM의 촬영/검수/발송 시간 정책과 MyCre의 00:00 일자 경계는 목적이 다르다. 이번 MyCre 결정을 이유로 승인된 FCM 촬영 창이나 발송 시각을 바꾸지 않는다.

## 6. 착수 순서와 병목

1. **우리 즉시 착수 가능:** 원본 에셋 연결, 공통 테마, Home/Camera 스타일, fan2·LED·분무·LCD·기존 일정, 메모/색상/Wi-Fi 저장, 카탈로그 대조, 앱 전용 숨김 migration 설계.
2. **우리 설계와 외부 회신을 함께 진행:** 그룹·이름 서버 규칙, 연결 이력·legacy 승계 schema, 기기 등록 해제. UI는 fixture로 검증하되 운영 성공으로 보고하지 않는다.
3. **실데이터 계약 회신 후 완료 판정:** MyCre 정확 집계(P1), 기존 신규 등록 방식(T4), 원본 보존 해제(T2), 일평균 count(T3), 하이라이트 공개 메타(P2).

외부 회신이 필요한 항목 때문에 독립적인 앱 작업을 모두 멈출 필요는 없다. 반대로 앱 목업이 동작한다고 서버 통합까지 완료됐다고 표시하지 않는다.
