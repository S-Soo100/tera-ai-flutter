## 1. 목표와 범위

사용자 제보는 ‘첫 연결 전에 끊김 안내가 나타남’, ‘시청 중 끊김과 복구를 반복하다 멈춤’이며 같은 Wi-Fi에서도 발생합니다.

이번 앱 개선의 목표는 다음과 같습니다.

1. 앱이 유발하는 불필요한 연결 종료와 중복 재접속을 줄입니다.
2. 연결·영상 상태를 구분해 복구하고, 실패 원인을 펌웨어·서버와 대조할 수 있게 합니다.
3. 처음의 상태 확인과 자동 복구를 정상적인 사용자 흐름으로 표현합니다.
4. 고객이 과거의 정지 화면을 현재의 라이브로 오해하지 않게 합니다.

**펌웨어 업데이트와 서버의 신규 API 없이 구현 가능한 항목을 먼저 진행합니다.** 기존 HTTP 계약·로그 스키마를 유지합니다. 이 작업만으로 카메라 인코더 중단이나 약한 Wi-Fi를 해결했다고 주장하지 않습니다.

### 범위 구분

| 구분 | 내용 |
|---|---|
| 우선 구현 기획 | 재연결 단일화, 상태 확인/실패 분리, 안정 재생 후 백오프 초기화, 타임아웃 관리, 기존 통계 기반 진단, 시청 중 정지 표시 |
| 앱 단독 검증 후 적용 | ICE 수집 정책 조정, 네트워크 변경 시 정상 영상 보존, 로컬 마지막 수신 사진 |
| 펌웨어/서버 회신 이후 | 동적 bitrate/fps, 키프레임 요청, ICE restart, 영상 세션 유지 신호, 신규 원격 진단 필드 |
| 이번에 하지 않음 | 웹뷰 전환, 미디어 서버 신설, 운영 TURN 변경, 가짜 LIVE, 녹화·AI 품질 변경 |

CAOF Standard의 기존 기능 개선 기획입니다. 이번 문서 작성은 구현 착수나 외부 발송을 뜻하지 않습니다.

## 2. 현재 상태와 개선 이유

| 현재 소스에서 확인한 사실 | 개선 이유 |
|---|---|
| 연결 세대 분리·자동 재시도·영상 정지 감시가 이미 존재 | 새로 중복 구현하지 않고 기존 안전장치를 보존 |
| 일반 실패 시 failed 화면으로 바꾼 뒤 자동 재시도 예약 | 자동 복구 중에도 고객에게 수동 해결을 요구하는 인상 |
| peer connected에서 재시도 간격 초기화 | 영상이 안정되지 않은 짧은 성공에도 재시도 간격이 짧아질 수 있음 |
| 네트워크 종류 변경 시 즉시 새 연결 시작 | 중복 이벤트, 겹치는 복귀·재시도 요청이 정상 영상에 미치는 영향 확인 필요 |
| 카메라 isOnline=false면 재시도 대기 | 실제 송출 상태와 목록 스냅샷을 구분해야 함 |
| 홈의 제어기 상태는 아직 데이터가 없어도 false 가능 | ‘미확인’이 ‘오프라인’ 안내로 이어지는 경로. 카메라 장애라고 단정 금지 |
| 앱 ICE 수집 최대 2초·srflx 조기 진행, 웹은 최대 5초 | 기존 펌웨어에서 늦은 후보 처리 차이를 비교할 필요 |
| framesDecoded 기반 감시, 통계 부재 시 판단하지 않음 | 데이터가 안 오는지 디코딩만 멈췄는지, 통계를 못 읽는지 구분 필요 |
| 연결 결과 원격 기록은 이미 구현 | 신규 로그 시스템으로 교체하지 않고 현재 적재·필드 확인부터 시작 |

서버 문서가 정정한 과거 18초 첫 프레임 지연을 현재 정상 대기시간으로 사용하지 않습니다. 그렇다고 펌웨어 빌드 확인 없이 첫 프레임 타임아웃을 2.5초로 줄이지도 않습니다.

## 3. 유저 체험 시뮬레이션

### A. 앱 최초 진입

1. [화면] 선택한 카메라의 마지막 수신 사진과 ‘라이브 연결 중’. 사진에는 마지막 수신 시각 표시. 사진이 없으면 어두운 스켈레톤.
2. [조작] 기다리거나 다른 화면으로 이동.
3. [반응] 연결을 자동 진행. 최초 상태 미확인을 끊김으로 표시하지 않음. 실제 프레임을 확인하면 영상으로 전환.
4. [감정] 연결이 준비되고 있음을 이해하며 고장으로 오인하지 않음.

### B. 정상 시청 중 네트워크 신호만 바뀜

1. [화면] 영상이 계속 재생됨.
2. [조작] 사용자는 그대로 시청.
3. [반응] 앱은 신호를 확인하되 영상이 정상 진행되는 연결을 불필요하게 철거하지 않음.
4. [감정] 연결 처리 자체를 의식하지 않음.

### C. 영상 정지와 자동 복구

1. [화면] 마지막 장면 위에 ‘영상이 잠시 멈췄어요 · 자동 연결 중’, 마지막 수신 시각. LIVE 표시 해제.
2. [조작] 별도 조작 불필요.
3. [반응] 중복 요청 없이 복구 진행. 실제 프레임 진행을 확인하면 안내 제거. 영상 영역 크기는 유지.
4. [감정] 앱이 문제를 처리하고 있음을 이해.

### D. 지속적인 연결 불가

1. [화면] ‘라이브에 연결하지 못했어요’와 ‘다시 연결’. 확인된 경우에만 휴대폰 네트워크 또는 카메라 연결 문제를 구체적으로 안내.
2. [조작] 다시 연결을 한 번 누름.
3. [반응] 이미 진행 중인 요청과 합쳐 한 연결 시도만 수행. 버튼 연타로 여러 offer가 나가지 않음.
4. [감정] 현재 상태와 가능한 행동을 이해.

### E. 사육장 제어기만 오프라인

1. [화면] 라이브는 정상 유지, 제어 영역에만 ‘사육장 제어기 연결 확인 중/연결 끊김’.
2. [조작] 라이브를 계속 시청.
3. [반응] 제어 가능 여부와 영상 상태를 각각 갱신.
4. [감정] 카메라까지 고장났다고 오인하지 않음.

## 4. 앱 연결 안정성 요구사항

### A1. 카메라별 연결 작업 단일화 — P0

- 같은 카메라의 홈·카메라 탭·확대 화면은 기존 family provider를 공유합니다. 화면별 컨트롤러를 새로 만들지 않습니다.
- 수동 재시도, 네트워크 변경, 앱 복귀, 정지 감지, 자동 타이머를 하나의 재연결 조정 경로로 모읍니다.
- 한 카메라에서 동시에 유효한 연결 시도는 하나입니다. 진행 중 요청은 병합하고, 명백히 다른 환경으로 바뀐 경우에만 기존 세대를 취소하고 새 시도를 시작합니다.
- 이전 세대의 상태 콜백·통계·offer 응답·ICE 폴링·첫 프레임 이벤트는 새 세대 상태를 바꾸지 않습니다.
- 같은 세션의 close는 중복 전송하지 않으며, 늦은 응답은 해당 세션만 정리합니다. close 대기가 무기한 새 시도를 막지 않도록 전체 시도 예산에 포함합니다.
- 백그라운드 전환 중 복귀가 겹쳐도 오래된 정리 작업이 새 renderer/state를 지우지 않습니다.
- 기존 세대 보호를 유지하면서 겹침 재현 테스트를 추가합니다. 코드에 잠재 경로가 있다는 사실과 고객 장애의 원인으로 재현됐다는 사실을 구분합니다.

### A2. 네트워크 변경 판단 — P0, 실기기 검증 필수

- connectivity_plus 결과는 ‘망 종류’ 신호이며 인터넷 도달성·실제 ICE 경로를 보장하지 않습니다. 같은 Wi-Fi 종류 안의 AP 변경도 놓칠 수 있습니다.
- 동일 신호 반복은 무시하고, 연속 변경은 1초 동안 합칩니다(검증 전 제안값).
- 신호 변경 후에도 프레임이 진행되면 기존 연결을 우선 유지합니다. 이전 경로가 실패했거나 신호 변경 이후 프레임 진행이 3초간 확인되지 않으면 한 번의 복구 절차로 진입합니다.
- 통계 자체를 못 읽는 경우 이를 ‘프레임 0’으로 바꾸지 않습니다. 실제 연결 상태·렌더러에서 관측 가능한 진행 정보를 사용하고 불명확하면 아래 기존 장기 정지 기준으로 보수적으로 판단합니다.
- 네트워크 없음이 확인되면 공격적인 offer 반복을 멈추고 복구 신호를 기다립니다. 카메라 전원 문제로 표시하지 않습니다.
- 백그라운드에서는 기존처럼 연결을 내리고, 복귀 시 한 번 연결합니다. 백그라운드 시청 기능은 이번 범위가 아닙니다.

### A3. 영상이 안정된 뒤 재시도 간격 초기화 — P0

- peer connected만으로 백오프를 초기화하지 않습니다.
- 실제 프레임이 30초 동안 계속 진행한 뒤 초기화합니다(제안값). ‘영상 있음 → 즉시 실패’는 같은 불안정 구간으로 계산합니다.
- 재시도 간격은 현행 3·6·12·24·48·60초 상한을 기본으로 유지하고 작은 무작위 편차를 검토합니다. 빠르게 반복해 카메라 세션과 메모리를 압박하지 않습니다.
- 사용자가 ‘다시 연결’을 누르면 대기 중 재시도를 앞당기되 진행 중인 offer를 복제하지 않습니다.
- 인증·권한 실패는 일반 네트워크 장애와 구분합니다. 기존 인증 갱신 이후에도 실패하면 무한 재시도하지 않습니다.

### A4. 관측과 복구 판단 분리 — P0

- 시청 중 영상 통계는 1초 주기로 샘플링하는 안을 검증합니다. getStats 호출은 겹치지 않게 하며, 배터리·처리 비용을 측정합니다. 비용이 크면 주기를 조절하고 실제 감지 지연을 보고합니다.
- 디코딩 프레임 진행이 3초간 없으면 ‘영상 지연/복구 중’ 표시로 전환합니다. 이 시점에 전체 연결을 즉시 끊지는 않습니다.
- 연결 자체가 실패하면 즉시 복구 절차로, 일시 disconnected는 현행 10초 유예를 기본으로 처리합니다.
- 재생 중 프레임이 15초간 진행하지 않으면 전체 재연결합니다. 횟수 곱셈 대신 마지막 진행을 확인한 단조 증가 시각으로 계산합니다.
- 첫 영상 대기 한도는 ICE 연결 후 현행 30초를 유지하며 전체 시도 예산을 넘지 않습니다.
- 수신 바이트 증가 여부로 ‘수신 중단’과 ‘디코딩 정지’를 진단상 구분합니다. 이번 단계에서는 둘 다 기존 지원 범위의 재연결을 사용합니다. PLI/FIR·ICE restart를 임의 호출하지 않습니다.
- SSRC 또는 통계 객체가 바뀌거나 누적 카운터가 감소하면 기준을 재설정합니다. 이전 카운터와 비교해 정지를 오판하지 않습니다.
- 통계가 10초간 계속 없고 렌더러 진행도 확인할 수 없으면 ‘영상 상태 확인 중’으로 표시합니다. 통계 부재만으로 연결을 종료하지 않고 LIVE 확신 표시는 보류합니다.

### A5. 단계별 시간 제한과 오래된 오프라인 상태 — P0

아래는 구현·실기기 검증 전 제안값입니다. 문구 변경과 네트워크 취소를 같은 타이머로 처리하지 않습니다.

| 항목 | 제안 정책 |
|---|---|
| 개별 연결 시도 전체 예산 | 설정 수신부터 정리 대기를 포함해 최대 60초. 단계별 기존 제한과 남은 예산 중 짧은 값 적용 |
| 시청 진입 후 최초 연결 / 정지 후 집중 복구 예산 | 전면에서 연결 가능한 네트워크가 있는 동안 최대 90초. 반복 시도에 남은 시간을 전달 |
| 집중 복구 실패 후 | 연결 불가 안내 + 수동 버튼. 권한 오류·백그라운드·네트워크 없음이 아니면 최대 60초 간격으로 저빈도 재시도 |
| 카메라 온라인 스냅샷 | 조회 중/조회 실패를 offline으로 치환하지 않음. 오래된 false 하나로 영구 대기하지 않음 |
| 카메라 offline 대기 | 전면·네트워크 연결 상태에서는 최대 60초 간격의 상태 재조회. 온라인 복귀 또는 사용자 명시 재시도 시 연결 시도 |

서버 offer는 최대 3×7초 대기할 수 있고 앱의 현재 HTTP 제한은 25초입니다. 앱 재시도까지 겹쳐 총 대기가 길어질 수 있으므로 전체 예산을 명시합니다. 취소 뒤 늦은 offer 응답을 받으면 해당 세션 close를 유지합니다. 응답을 끝내 받지 못한 세션의 확실한 원격 정리는 펌웨어·서버 의존으로 남습니다.

### A6. ICE 수집 정책 비교 — P1, 자동 채택 금지

- 현재 2초/srflx 조기 진행과 웹에 가까운 ‘수집 완료 또는 최대 5초’ 정책을 같은 조건에서 비교합니다.
- TURN 설정이 있다면 srflx 하나가 생겼다는 이유만으로 충분한 후보가 확보됐다고 간주하지 않는 안을 시험합니다.
- 완료 이벤트로 일찍 진행하고, 기존 추가 후보 전송은 유지합니다. 후보 값·자격 증명은 로그에 기록하지 않습니다.
- 같은 Wi-Fi·외부망에서 첫 프레임 시간과 연결 실패를 비교합니다. 후보가 부족한 실패가 줄거나 시간 분포가 개선된다는 증거가 있어야 채택합니다.
- 5초 대기 자체가 장시간 재생 끊김을 고친다고 주장하지 않습니다. 서버 config를 읽는 것과 TURN 경로가 실제 동작하는 것은 별개입니다.

## 5. 상태 표시와 마지막 수신 화면

### 표시 상태

| 상태 | 문구 예시 | LIVE | 주된 행동 |
|---|---|---|---|
| 상태 확인/최초 연결 | 라이브 연결 중 | 숨김 | 자동 진행 |
| 첫 프레임 대기 | 영상을 불러오고 있어요 | 숨김 | 자동 진행 |
| 프레임 진행 확인 | 필요 시 LIVE | 표시 | 시청 |
| 일시 정지/자동 복구 | 영상이 잠시 멈췄어요 · 자동 연결 중 | 숨김 | 자동 복구 |
| 관측 불가 | 영상 상태 확인 중 | 숨김 | 상태 재확인 |
| 지속 연결 불가 | 라이브에 연결하지 못했어요 | 숨김 | 다시 연결 |
| 제어기 상태 미확인 | 제어 영역만 연결 확인 중 | 라이브와 무관 | 제어 상태 확인 |

내부 config/offering/ICE 단계를 고객에게 차례로 나열하지 않습니다. 단계는 진단 로그에서 유지합니다. 사육장 제어기의 로딩·오류·오프라인을 분리하고, 해당 수정이 제어 권한을 느슨하게 만들지 않도록 미확인 동안 제어는 기존처럼 보수적으로 차단합니다.

### 마지막 수신 사진 — P1

- 실제로 수신한 라이브 프레임만 사용합니다. 하이라이트 썸네일이나 임의 이미지를 현재 카메라 사진으로 대체하지 않습니다.
- 표시는 ‘마지막 수신 HH:mm · 연결 중’입니다. 기기 촬영시각이 확인되지 않으므로 ‘촬영시각’이라고 쓰지 않습니다. 날짜가 다르면 날짜도 표시합니다.
- 재접속 때 renderer를 해제해도 사진은 별도 보관돼야 합니다. 프레임 캡처가 지원되지 않으면 스켈레톤으로 대체하며 사진 저장 실패가 영상 연결을 방해하지 않습니다.
- 앱 재실행 시 표시할 캐시는 계정 ID+카메라 ID별 1장, 전체 최대 5MB, 보존 24시간으로 제안합니다. 한도를 넘으면 오래된 사진부터 삭제합니다.
- 정상 재생 중 저장은 최대 30초에 한 번, 앱 비공개 캐시로 제한합니다. 일반 갤러리에 저장하지 않습니다. 보안 저장·OS 백업 제외 가능 여부를 구현 시 확인합니다.
- 로그아웃·계정 전환·카메라 접근 권한 상실·카메라 삭제 시 해당 사진을 제거합니다. 소유/접근 확인 전에는 사진을 노출하지 않습니다.
- 회전 설정을 저장된 사진에도 일관되게 적용합니다. 다른 카메라로 전환할 때 이전 사진이 한 프레임이라도 남지 않아야 합니다.
- 캐시는 실제 연결 안정성과 별도의 UX 개선 항목으로 평가합니다.

## 6. 계측과 펌웨어 수정 전 진단

### 기존 원격 로그 유지

`webrtc_connect_logs`의 현재 필드와 허용 outcome을 그대로 사용합니다. 서버에 아직 없는 필드를 INSERT해 전체 로그가 거절되지 않도록 합니다. 새 필드·새 outcome·원격 큐는 별도 서버 계약 이후입니다.

원격 로그는 실제 연결 성공/실패를 기록하며, 사용자 안내가 ‘복구 중’으로 바뀌어도 실패를 성공으로 바꾸지 않습니다. 네트워크 장애 중 원격 기록이 유실될 수 있다는 한계를 보고서에 명시합니다.

### 앱 단독으로 추가할 로컬 진단

- 시청 묶음 ID, 연결 시도 ID, session_id(응답 이후), 카메라 ID, 앱/OS 버전, UTC 시각·단조 증가 경과 시간.
- 전환 사유: 수동 재시도, 네트워크 변경, 앱 복귀, ICE 실패, 영상 정지, 정상 이탈. 이전 세대 콜백 무시와 요청 병합도 기록.
- 누적 수신 바이트·디코딩 프레임의 증분, 지원되는 경우 손실·jitter·왕복 시간·freeze 통계. 없는 값은 unavailable.
- 선택 후보의 타입만 저장하며 IP·SDP 원문·JWT·TURN 자격 증명은 저장하지 않음. 원본 영상은 진단 로그에 넣지 않음.
- 전면 시청 중 최근 5분을 메모리 순환 버퍼로 보관하고, 오류 전후 요약을 포함해 총 5MB 상한의 계정별 진단 파일로 내보낼 수 있게 함. 계정 종료 시 삭제. 자동 외부 발송 없음.
- 공유는 사용자가 명시적으로 실행하는 지원용 동작이며 일반 라이브 화면에 개발용 로그를 노출하지 않음.

원격 스키마를 바꾸지 않는 범위에서도 A/B 시험과 펌웨어 로그 대조는 가능해야 합니다. 강제 종료로 메모리 진단이 사라지는 한계는 별도 표시합니다.

## 7. 지표 정의와 성공 판정

| 지표 | 정의 |
|---|---|
| 첫 프레임 시간 | 카메라 시청 의도가 시작된 시점부터 첫 실제 프레임까지. 재시도를 포함한 사용자 대기와 개별 시도 시간을 별도 측정 |
| 정지 횟수 | 정상 재생 이후 프레임 진행이 3초 이상 멈춘 구간. 하나의 정지 중 재시도가 여러 번 있어도 한 정지 구간으로 계산 |
| 총 정지 시간 | 확인된 마지막 프레임 진행 시점부터 진행 재개까지의 추정 시간. 샘플 주기 오차를 함께 기록 |
| 복구 시간 | 장애 감지부터 실제 프레임 진행 재개까지 |
| 재접속 횟수 | 시청 시간당 새 peer/offer 수. 자동 복구 횟수가 많다는 것을 안정성 향상으로 해석하지 않음 |
| 관측 범위 | 통계 확보 시간/전체 시청 의도 시간. 통계가 없으면 정지 0으로 보고하지 않음 |

정지율의 분모는 연결 실패·재연결 시간을 포함한 전면 시청 의도 시간입니다. 정상 화면 이탈·백그라운드는 제외하며, 자연 발생 장애와 시험자가 유발한 단절은 따로 집계합니다. 기존 원격 로그만으로 모든 지표가 계산된다고 가정하지 않습니다.

**필수 회귀 기준:** 최초 미확인 상태에 실패 안내 없음, 정상 영상 중 중복 신호만으로 연결 종료 없음, 같은 카메라 동시 offer 없음, 지연 close/콜백이 새 연결에 영향 없음, 사진/계정 혼선 없음.

**실기기 판정:** 같은 조건의 전후 시험에서 설명되지 않는 정지·수동 복구가 없어야 합니다. 펌웨어 원인이 남아 불가능하면 미해결로 표시하고 앱 개선 완료와 제품 안정화 완료를 구분합니다. 첫 프레임 시간·정지 시간·배터리 비용이 악화된 정책은 기본값으로 채택하지 않습니다.

## 8. 구현 순서와 검증 시나리오

### 적용 순서

1. 현재 앱·펌웨어 버전과 기존 원격 로그 적재를 확인하고 전후 비교 기준을 확보.
2. A1~A5 및 로컬 진단을 구현. 기존 펌웨어와 API로 검증.
3. 고객 상태 표시 분리와 사육장 제어기 미확인 처리를 적용.
4. A6 ICE 정책을 비교해 채택 여부 결정. 마지막 수신 사진은 플랫폼 캡처 검증 후 적용.
5. 펌웨어 회신 후 별도 기획으로 키프레임·가변 화질·ICE restart·원격 진단 확장 검토.

### 자동화 검증

- 네트워크/수동/복귀/타이머가 겹칠 때 활성 시도 1개.
- 오래된 offer 응답·close·통계·첫 프레임 콜백 격리.
- connected만으로 백오프를 초기화하지 않으며, 안정 프레임 진행 후에만 초기화.
- stats 부재·카운터 리셋·SSRC 교체·정적 피사체(프레임은 계속 옴)에서 오탐 없음.
- 카메라/제어기 상태 loading/error를 offline으로 변환하지 않음.
- 전체 예산과 단계별 타임아웃·백그라운드 취소·수동 재시도 병합.
- 최초 연결/자동 복구/지속 실패 문구 및 LIVE 상태 전환.
- 사진 계정 격리·만료·삭제·카메라 전환·캡처 실패 대체.
- 기존 허용 필드만 원격 INSERT하며 진단 기록 실패가 연결에 영향을 주지 않음.

### 실기기 검증

Android/iOS 각각 같은 Wi-Fi 앱·웹 순차 60분, 첫 연결 30회, 백그라운드 복귀 10회, 네트워크 전환 10회, 5초 단절 후 복구, 클립 업로드 중 시청, 화면 확대/축소·카메라 전환을 시험합니다. 외부 Wi-Fi·LTE/5G와 가능하면 강제 relay도 별도로 검증합니다.

웹과 앱의 동시 접속은 초기 비교에서 피하고, 동시 시청 한도 확인 후 별도 시험합니다. 60분 회귀 통과 후 4시간 시험으로 자원 누적을 확인합니다. 측정 표본 수를 공개하며 적은 시험으로 99% 서비스 성공률을 주장하지 않습니다.

### 변경 검증·롤백

구현 시 `flutter analyze` 에러 0과 관련 테스트를 통과하고 실기기 결과를 첨부합니다. 연결 정책, ICE 정책, UX/캐시는 논리적으로 분리해 되돌릴 수 있게 합니다. 단계별 적용 후 악화된 정책만 되돌리고 진단 결과는 보존합니다. 앱 버전·빌드와 한글 CHANGELOG는 실제 구현 때 갱신합니다.

## 10. 구현 전 실측·회신으로 정할 항목

- 마지막 사진·상태 표시 개선은 실제 정지율 개선과 별도 결과로 보고합니다.

| 카메라 목록 조회 중/실패를 offline으로 치환하지 않음 | `_cameraOffline()`은 `cam != null && !cam.isOnline` — 이미 본문 A5 요구를 만족. **추가 작업 없음** |
| 제어기 미확인이 오프라인 안내로 이어짐 | `moduleOnlineProvider`의 `device?.isOnline ?? false` + `DeviceOfflineNotice`가 `false`를 곧장 "기기 연결이 끊겼어요"로 그림 |

### 11.2 본문에 없던 코드 결함 (계획서에 추가)

- **ICE 연결 단계에 시간 한도가 없다.** `connectingIce`에서 피어가 `connected`도 `failed`도 내지 않으면 아무 타이머도 없다(config 15초·offer 25초·첫 프레임 30초만 존재). A5의 "개별 시도 전체 예산 60초"가 이 구멍을 막는 실질적 근거다.
- **인증 실패가 무한 재시도된다.** `_authedRequest`가 401을 한 번 복구한 뒤에도 실패하면 `BackendException(401/403)`이 일반 `_fail`로 흘러 백오프 재시도가 영원히 돈다. A3 마지막 항목을 `statusCode 401/403 → failed 고정 + 자동 재시도 없음`으로 구체화한다.
- **`_reconnectNow`(네트워크 변경·카메라 온라인·앱 복귀)가 `_reconnectAttempt`를 0으로 되돌린다.** 흔들리는 망에서는 즉시 재시도가 무제한 반복된다. 백오프 초기화는 A3대로 **안정 재생 30초 뒤에만**(수동 "다시 연결"은 사용자 의도이므로 예외 유지).
- **분기 재시도 병합 지점.** `_restart()`는 세대를 먼저 올리므로 겹친 호출은 마지막 것만 살아남지만, `_cleanup` 대기 중 겹친 호출은 각각 정리 코드를 다시 밟는다. 병합은 "정리 중이면 무시(이미 새 세대가 온다)"로 구현한다. 연결 진행 중(config~waitingVideo) 도착한 **네트워크 변경·복귀**는 환경이 바뀐 것이므로 취소 후 재시작(force), 그 외는 병합.

### 11.4 상태 모델 확정 (계획서 기준)

`WebRtcLivePhase`에 `stalled`(재생 중 5초 무진행, renderer 유지)·`recovering`(집중 복구 90초 안의 자동 재시도)을 추가하고, `failed`는 **집중 복구 예산 소진·카메라 오프라인·인증 실패**에만 쓴다. `failed`에서만 "다시 연결" 버튼이 보이고 60초 저빈도 자동 재시도가 돈다. 원격 로그 outcome·fail_phase는 기존 허용값만 쓴다(`stalled` 종료 행의 fail_phase는 `streaming`).

### 11.5 P1 항목의 사전 확인 결과

- `flutter_webrtc 1.4.1`의 `MediaStreamTrack.captureFrame()`(native)이 존재한다 — 마지막 수신 사진(P1)의 캡처 경로 후보. 원격 트랙에서 플랫폼별로 실제 동작하는지는 실기기 검증 항목.
- ICE 수집 비교(A6)는 `kWebRtcIceGatherWait`·`_iceWaitProbe`(srflx 조기 진행) 두 지점만 바꾸면 되므로 별도 계획서 없이 실기기 비교 뒤 결정한다.
