# 분무(mist) 블랙아웃 펌웨어 검토 및 대응안

- 작성일: 2026-09-07
- 대상: `terra-iot-nano` 펌웨어, 전원/구동 회로, `terra-server`
- 원문: `backend-handoff-2026-09-07-mist-blackout.md`
- 검토 기준: 현재 로컬 `terra-iot-nano` 소스

## 1. 결론

실DB에서 확인된 분무 직후 25~26초 텔레메트리 공백과 그 구간의 명령 유실은
실제 장애로 판단한다. 다만 원문에서 추정한 **펌프 구동 코드의 블로킹**은 현재
펌웨어 구현과 일치하지 않는다.

현재 `mist` 명령은 `relay_pulse()`로 펌프를 켠 뒤 `esp_timer`에 자동 OFF를 예약하고
즉시 반환한다. 분무 지속시간 동안 MQTT 명령 처리 태스크나 텔레메트리 태스크를
대기시키는 코드는 없다.

따라서 우선순위가 높은 원인 후보는 다음과 같다.

1. 펌프 기동 또는 정지 순간 전압 강하에 따른 ESP32 브라운아웃/재부팅
2. DC 모터 역기전력이나 전원·GND 노이즈에 따른 WiFi/MQTT 단절
3. WiFi 또는 MQTT 단절 후 재연결 과정에서 발생하는 25초 안팎의 복구 지연
4. 실장 장치에 현재 로컬 소스와 다른 이전 펌웨어가 설치된 경우

원인을 확정하기 전 단순히 `mist`를 다시 비블로킹으로 고치는 작업은 효과가 없다.
분무 실행 순간의 시리얼 로그와 전원 측정이 먼저 필요하다.

## 2. 장애 데이터 요약

원문에 기록된 세 번의 장애는 다음 공통점을 갖는다.

| 항목 | 관측 결과 |
|---|---|
| 정상 텔레메트리 주기 | 약 3초 |
| 분무 지속시간 | 2~3초 |
| 분무 후 텔레메트리 공백 | 25~26초 |
| 공백 중 명령 | 브로커 발행 후 `sent`에 고정 |
| 실제 액추에이터 실행 | 실행되지 않음 |
| 단독 팬 명령 | 즉시 실행 및 ACK |

분무 지속시간과 관계없이 공백 길이가 거의 같으므로, 분무 함수가 설정된 시간만큼
대기한 결과라기보다는 재부팅 또는 네트워크 재연결에 걸리는 고정 비용일 가능성이
더 높다.

## 3. 현재 펌웨어 코드 대조

### 3.1 `mist` 명령 처리

`main/src/command_dispatch.c`의 `mist` 분기는 다음 순서로 실행된다.

1. `duration_ms`를 읽는다.
2. 값이 없거나 0이면 `bad_request`로 응답한다.
3. 최대 5초로 제한한다.
4. `relay_pulse()`를 호출한다.
5. 호출 결과를 바탕으로 ACK를 발행하고 반환한다.

분무 처리 경로에는 `vTaskDelay(duration_ms)`나 동기식 대기 루프가 없다.

### 3.2 펌프 자동 OFF

`main/src/actuators/relay.c`의 `relay_pulse()`는 다음과 같이 동작한다.

1. 펌프 GPIO를 ON으로 전환한다.
2. `esp_timer_start_once()`로 자동 OFF 시점을 예약한다.
3. 즉시 호출자에게 반환한다.
4. 시간이 지나면 `esp_timer` 콜백이 펌프 GPIO를 OFF로 전환한다.

따라서 펌프 ON 상태에서도 FreeRTOS 스케줄러, 센서 태스크, MQTT 이벤트 처리는
계속 실행될 수 있다.

### 3.3 텔레메트리 및 MQTT

- 텔레메트리는 별도 센서 태스크에서 약 3초마다 발행한다.
- MQTT 명령은 `MQTT_EVENT_DATA` 이벤트에서 파싱한 뒤 즉시 처리한다.
- `mist` ACK는 펌프 ON 및 타이머 예약 직후 발행한다.
- WiFi 단절 시 펌웨어는 1초부터 최대 30초까지 지수 백오프로 재연결한다.

현재 구조에서 분무만으로 텔레메트리가 25초간 멈춘다면, 코드 대기보다 시스템
리셋이나 통신 계층 단절을 먼저 의심해야 한다.

## 4. 명령 유실 원인

현재 MQTT 구성은 다음과 같다.

- 고정된 장치 ID를 MQTT client ID로 사용
- 명령 토픽 QoS 1 구독
- 서버 명령 발행은 `retain=false`
- MQTT Clean Session은 기본값인 `true`
- 연결 복구 후 명령 토픽 재구독

구독 QoS가 1이어도 Clean Session이 활성화된 장치가 오프라인인 동안 발행된
비보존 명령은 나중에 전달되지 않는다. 서버의 브로커 publish 성공은 장치 수신이나
액추에이터 실행 성공을 의미하지 않는다.

따라서 다음 흐름이 가능하다.

```text
서버 publish 성공
  → DB 상태 sent
  → 장치는 WiFi/MQTT 단절 상태
  → 브로커가 명령을 오프라인 큐에 보관하지 않음
  → 장치 재연결
  → 명령 재전달 없음
  → ACK 없음
  → DB는 영구적으로 sent
```

펌웨어에는 최근 8개 `msg_id`에 대한 RAM 기반 중복 방지가 있다. 이는 서버가
절대 상태 명령을 재전송할 때 중복 실행을 줄여주지만, 재부팅하면 목록이 사라지고
9개 이상 명령이 처리되면 이전 항목이 밀려난다.

## 5. 원인 확정을 위한 시험

### 5.1 시리얼 로그 동시 수집

분무 명령 전부터 복구 완료까지 시리얼 모니터를 유지하고 다음 로그를 확인한다.

| 관측 로그 | 판단 |
|---|---|
| ROM 부팅 메시지와 `app_main` 초기화가 다시 출력됨 | 전원 강하, 브라운아웃 또는 리셋 |
| `wifi_sta: disconnected` 출력 후 재연결 | WiFi 링크 단절 또는 전원/RF 노이즈 |
| WiFi는 유지되고 `MQTT DISCONNECTED`만 출력 | TLS, 소켓 또는 브로커 계층 문제 |
| 연결 오류 없이 텔레메트리만 멈춤 | 태스크 정지, 교착 또는 별도 코드 경로 조사 |

가능하면 다음 진단 정보도 부팅 로그와 텔레메트리에 추가한다.

- `esp_reset_reason()` 결과
- 부팅 횟수
- WiFi disconnect reason 및 직전 RSSI
- MQTT TLS/소켓 오류 코드
- 최소 free heap 및 태스크 stack high-water mark

### 5.2 부하 분리 시험

같은 펌웨어로 아래 순서를 각각 10회 이상 반복한다.

1. MOSFET 입력은 연결하고 실제 펌프 부하만 분리한 상태에서 `mist`
2. 펌프 대신 저전력 저항성 부하를 연결한 상태에서 `mist`
3. 펌프를 별도 12V 전원으로 구동한 상태에서 `mist`
4. 실제 구성 그대로 `mist`

펌프 부하를 분리했을 때만 장애가 사라진다면 펌웨어 블로킹이 아니라 전원 또는
모터 노이즈 문제로 판단할 수 있다.

### 5.3 전원 및 배선 확인

- 펌프 기동 순간 12V SMPS 출력과 ESP32 보드 입력 전압 측정
- 펌프 정격전류가 아니라 기동전류를 기준으로 SMPS와 DC-DC 여유 확인
- 펌프 단자 가까이에 역기전력 억제 소자가 실제로 있는지 확인
- 펌프 고전류 리턴 경로가 ESP32 신호 GND를 통과하지 않도록 스타 배선 적용
- ESP32 전원 입력부의 벌크 및 고주파 디커플링 상태 확인
- 펌프 전원선과 SPI, 센서, 안테나 주변 배선 간 거리 확보

## 6. 권장 개선안

### 6.1 Nano 펌웨어

우선 적용:

1. 부팅 시 reset reason을 반드시 출력한다.
2. WiFi disconnect reason, RSSI, MQTT 오류를 장애 분석용으로 보존한다.
3. MQTT persistent session 사용을 검토한다.
4. 장치가 재연결되면 마지막 처리 명령과 현재 출력 상태를 서버에 보고한다.

MQTT persistent session은 `disable_clean_session=true`로 설정할 수 있다. 다만
브로커가 오프라인 QoS 1 큐와 세션 수명을 지원하도록 함께 설정되어야 하며,
펌웨어 설정만 변경해서는 충분하지 않다.

현재 `mist`/`relay_pulse` 자체는 이미 비블로킹이므로, 시리얼 증거 없이 해당 부분을
다른 타이머 구조로 다시 작성할 필요는 없다.

### 6.2 하드웨어

전원 강하 또는 모터 노이즈가 확인되면 다음 순서로 개선한다.

1. 펌프 전원 경로와 ESP32 전원 경로 분리
2. 충분한 전류 여유를 가진 SMPS/DC-DC 적용
3. 펌프 단자 역기전력 및 EMI 억제
4. 고전류 GND와 로직 GND의 배선 경로 분리
5. 보드 입력부 디커플링 보강

브라운아웃 검출을 끄는 방법은 문제를 숨기고 플래시 손상이나 오동작 위험을 키울 수
있으므로 해결책으로 사용하지 않는다.

### 6.3 Terra Server

서버 변경은 펌웨어 원인 조사와 별개로 필요하다.

1. `sent` 이후 일정 시간(권장 30초) 안에 ACK가 없으면 `expired` 또는 `lost` 처리
2. TTL이 남은 절대 상태 명령(`*_on`, `*_off`)만 제한적으로 재전송
3. 브로커 publish 성공과 장치 ACK 성공을 별도 상태로 관리
4. 재전송 횟수와 마지막 전송 시각 기록
5. 장치 재연결 이벤트에서 미ACK 명령을 조회하되 TTL을 반드시 재검증

명령 토픽에 `retain=true`를 일괄 적용하는 것은 권장하지 않는다. 오래된 펌프 ON
명령이 재구독 시 실행될 수 있기 때문이다.

## 7. 완료 판정 기준

펌웨어/하드웨어 개선 완료는 다음 조건으로 검증한다.

- `mist` 1초, 2초, 3초를 각각 10회 이상 반복
- 모든 시험에서 텔레메트리 간격이 6초를 넘지 않음
- 분무 중 발행한 `fan_on`/`fan_off`가 3초 안에 ACK됨
- WiFi 및 MQTT disconnect 로그가 발생하지 않음
- 브라운아웃, watchdog, panic, 재부팅이 발생하지 않음
- ACK를 받지 못한 서버 명령은 설정된 시간 안에 `expired/lost`로 전환됨
- 재전송된 동일 `msg_id`가 액추에이터를 중복 실행하지 않음

추가로 펌프와 팬 두 개, 조명을 동시에 구동한 최악 부하 조건에서도 같은 시험을
반복해야 한다.

## 8. P4 카메라 이슈 분리

WebRTC 라이브가 약 20분 후 종료된 현상은 관찰 1회이고 mist 장애와 직접 연결되는
증거가 없다. Nano 분무 장애와 별도 티켓으로 관리하고 다음 자료를 수집한다.

- 카메라 펌웨어 로그
- WebRTC ICE/DTLS 상태 변화
- 시그널링 서버 세션 종료 로그
- NAT binding 및 TURN 세션 수명
- 연결 시작부터 종료까지의 정확한 시간

Nano 펌웨어 수정으로 P4 WebRTC 문제까지 해결된다고 가정해서는 안 된다.
